# 00 项目定位、现状核查与升级全貌

## 这一轮究竟要做成什么

SkillForge 的定位仍然是**面向本地代码仓库的、可恢复、可审计、能复用经验的 Coding Agent Harness**。用户交给它一个目标，例如“修复分页接口漏数据，同时补齐回归测试”，它负责持续组织模型判断、仓库探索、工具执行、代码修改和验证，最后交付可检查的代码差异与验证记录。它不是训练模型的项目，也不是把一个聊天接口包装成网页。

本方案建议把项目的主线收束成一句话：**让一次真实的改码任务，在长上下文、工具失败、人工中断和经验复用的条件下，仍能受控地完成。** 上下文、工具、Skills、多 Agent 和后端不是五项互不相关的“技术亮点”，而是围绕这条主线协作的模块。

例如，工具把两万行测试日志变成可回看的工件，直接减少上下文膨胀；上下文保留测试证据引用，让压缩后仍知道验证了什么；后台执行器记录中断点，使关掉页面不等于丢失任务；Skills 只从这些可信证据中提炼经验；子 Agent 只返回带文件版本的调查结论，不能绕过父 Agent 修改代码。这些约束连成闭环，项目才会摆脱 toy。

**建议第一轮采用的范围：Python 模块化单体、一个本地服务进程、一个工作区写入者、SQLite 与本地工件目录、原生工具协议、缓存感知上下文、可审核的 Skill 学习，以及最多两个并行只读子 Agent。** 本文中的“模块”是代码职责划分，不代表拆成十几个微服务。

## 阅读地图与状态标记

每章先解释用户能获得的功能，再讲输入输出、现状、目标设计、关键技术、失败处理和验收。第 02、03 章连起来理解上下文与缓存；第 04、05 章连起来理解动作安全与执行；第 07 章是经验学习；第 08 章是多 Agent；第 10—12 章是后端、交互与恢复。最后用第 13 章的实验方法证明效果，而不是先编造性能数字。

本文统一使用四种证据口径：**“现状核查”**是实际阅读云盘源码得到的事实；**“外部参考”**是公开官方文档或开源项目的行为；**“建议设计”**是为 SkillForge 提出的目标方案；**“示例/待验证”**是解释机制的假设数据、伪接口或尚未完成的测试。除明确标注的三个局部复现实验外，本文没有声称已实现升级或完成模型端评测。

本次参考了 pico 的“从整体链路进入各个模块，再连接代码位置、状态、工件与评测”的教学组织方式。已阅读云盘 Markdown 以及 PDF 的部分可提取页面；PDF 页面图像未成功取得，因此没有声称复刻其视觉排版。[S12]

## 现状核查：哪些能力已经有，哪些才是真正薄弱点

新版 Word 简历是简历口径基准，云盘中已读取的核心源码是实现核查基准。两者回答不同的问题：简历说明对外如何概括，源码说明当前机制到底做到了哪一层。此次云盘源码大多保留 2026-06-29 的修改时间，不能仅凭 9 月上传时间认定它们经过了 9 月重构；也没有把未读取的历史文档当作当前实现。[S01–S11]

| 模块 | 已确认存在 | 本轮应该深化的地方 |
|---|---|---|
| 运行时 | 阶段化工作流、工具预算、停止条件、完成检查 | 解耦模型协议与运行状态，增加原生工具消息、流式事件与取消 |
| 上下文 | 分区字符预算、历史裁剪、记忆召回、前缀指纹 | 动态内容前置、历史反复改写；缺少 Token 级预算与缓存边界治理 |
| 工具 | 参数校验、审批、路径限制、补丁唯一匹配 | 文本工具协议、同步命令、粗粒度副作用分类、缺少持久调用身份 |
| 工件 | `log_run` 保存日志，简报与失败详情按需读取 | 把这条成熟一些的路径统一扩展到所有大输出和长进程 |
| 记忆 | 文件摘要、任务与过程记忆、内容哈希新鲜度 | 缓存快照与实时事实分离、召回可解释、依赖级失效 |
| Skills | 候选、证据、安全和人工确认等晋升流程 | 蒸馏内容模板化，匹配粒度粗，缺少适用性与版本效果验证 |
| 子 Agent | 有界、同步、只读的 `delegate` | 不是从零加角色，而是补任务合同、并发隔离、预算与生命周期 |
| 持久化 | Session JSON、Run 工件、部分原子文件替换 | 跨状态更新一致性、幂等控制、断线重连、故障协调 |

特别需要纠正三个容易把方案带偏的判断。

第一，**并非完全没有多 Agent**。`tools.py::tool_delegate` 已创建只读子实例，但同步调用 `child.ask()`，并共享模型客户端等对象。后续若直接用 `asyncio.gather` 并行，很容易把“原本顺序使用的共享可变对象”变成竞态。升级重点应是隔离与调度，而不是加几个角色名字。[S03]

第二，**并非没有日志外置**。`log_run`、`log_brief`、`log_failure_detail` 已经把原始日志、摘要和失败详情分开。不要为了展示新功能再造一套不兼容的日志系统，应把这一模式提升为统一 ToolResult / Artifact 契约。[S03,S11]

第三，**并非没有文件新鲜度或技能审核**。`memory.py::file_freshness` 已使用 SHA-256；`skills.py` 已有较完整的晋升门。真正的问题是这些机制与模型输入、并发任务和后续泛化效果之间尚未形成统一协议。[S06,S07]

## 一条请求经过哪些模块

以“修复分页漏数”为例，建议链路如下。这里的箭头表示调用或状态推进，不意味着所有步骤必须再次调用模型。

```text
用户请求
  -> 会话控制：创建 Run，冻结预算、工作区与授权版本
  -> 运行时：选择探索/修改/验证阶段
  -> 上下文视图：稳定前缀 + 有效摘要 + 完整消息组 + 当前任务
  -> 模型适配器：生成结构化工具调用
  -> 工具网关：参数、阶段权限、审批、调用身份、资源检查
  -> 执行器：读代码 / 管理进程 / 应用补丁
  -> 工件与证据：日志、差异、文件版本、退出码
  -> 验证门：核对测试与当前代码是否一致
  -> 交付：差异、验证、风险、未解决事项
  -> 后置学习：候选 Skill，经验证和确认后发布新版本
```

子 Agent 插在“探索”和“审查”中，不接管整条主链；数据库和事件流横跨这些步骤，负责可靠记录，不替模型做推理。上下文压缩只改变“给模型看的视图”，不删除执行证据。用户追加新要求时形成新的任务版本，而不是悄悄改写历史请求。

## 基础技术栈与复杂度上限

建议保留 Python，核心模型使用 dataclass 或 Pydantic，异步 I/O 使用 asyncio，HTTP 模型调用使用一个可注入的异步客户端；不要求把所有既有同步函数一次性重写。存储先用 SQLite WAL 与 FTS5，文件内容及日志落到本地受控目录；CLI 与可选 FastAPI 服务复用同一运行内核。SQLite 的 WAL 提供读写并行条件，但依然只有一个写事务能同时推进，因此要保持事务短小，不能把模型等待放在事务中。[R18]

一轮重构不引入 Kafka、Redis、Kubernetes、分布式工作流引擎、全量仓库向量库、自研沙箱或无限递归 Agent 群。也不把“后台学习”包装成模型参数自我训练：这里学习的是可审查的程序性知识，不是权重更新。

独立选型的另一条路线是直接在 pi 或 Hermes 上实现扩展。如果主要目的是快速获得个人生产力，这条路线可能更省时；但如果目标包含展示个人项目中的上下文、执行和后端设计能力，保留 SkillForge 内核并分层重构更合适。本文选择后者，复用外部的设计原则，而不是同时嵌入多个完整 Harness。[R04,R05]

## 什么叫“完成了深化”

完成标准不是文件数量、角色数量或架构图复杂度，而是用户可以实际观察到：长任务不再每轮反复改写缓存前缀；长命令可查看进度与取消；断开客户端后能接着看同一任务；恢复不会盲目重放副作用；Skills 能解释适用前提与来源；子任务成本和写入权限受父任务限制；最终的“完成”有当前代码上的验证证据。

这些能力的具体不变量和负例在各章展开。只有通过对应验收后，才能把建议方案转化为简历中的“已实现”；第 14 章给出分阶段的落地边界，避免一次性承诺全套。

# 01 运行时与模型协议：让 Agent 真正按结构执行

## 模块功能：把一次聊天变成受控的任务循环

运行时是 SkillForge 的控制中心。它接收用户目标，决定当前允许探索、修改还是验证；向模型提供上下文；接收模型请求的动作；把动作交给工具网关；记录结果并继续下一轮。用户看到的是“它在有步骤地解决问题”，而不是模型一口气输出了一段看似完整的答案。

本模块的输入是任务合同、当前运行状态和模型可见消息，输出是下一批动作或候选最终答复。它**不直接执行 shell，不自行判定权限，不负责在字符串里寻找测试是否成功**。这些工作分别属于执行器、策略和证据模块。职责分离之后，增加多 Agent 或网页界面才不会把 `ask()` 继续变成一个无所不包的大函数。

## 现状：已有工作流，模型协议仍以整段文本为中心

当前 `runtime.py::build_prefix` 要求模型输出 `<tool>...</tool>` 或 `<final>`；`models.py::OpenAICompatibleModelClient.complete` 把整个 prompt 放进一条 user 文本发送，运行时再解析字符串。即使使用 `/responses` 接口，也不等于已经使用了原生工具调用协议。当前接口还把用量写入共享的 `last_completion_metadata`，这在顺序执行中可用，扩展到并行子任务后则需要消除竞态。[S04,S05]

现有 WorkflowIR、TaskPacket、阶段预算和 CompletionGate 是应保留的业务内核。建议把“模型怎样表达工具调用”从这些业务规则里抽走，而不是以引入 LangGraph 为由重写整套已有状态机。[S08]

## 建议设计：三种状态，不要混成一份 history

**会话状态**表示长期对话关系，例如 Session ID、已批准的配置快照。**运行状态**表示这次用户请求的进度，例如 Run ID、当前阶段、剩余预算、待审批动作。**模型消息**表示某次推理真正看到的内容，包括用户消息、模型响应和工具结果。三者有关联，但不是同一个对象。

例如，某个 shell 已执行完成而客户端尚未看到结果，运行状态应记录“完成”；模型消息要在结果可靠落盘后补齐；客户端通过事件补拉显示结果。不能因为 UI 消息没收到，就把工具重新执行一次。

每次模型调用返回一个不可变结果对象，而不更新客户端共享字段：

```text
ModelResponse
  response_id, provider_request_id, model_revision
  text_blocks[]
  tool_calls[{call_id, name, arguments}]
  finish_reason
  usage{input, output, cache_read, cache_write, raw_usage}
  provider_state_ref?     # 保留供应商要求延续的响应状态
```

`provider_state_ref` 用于保留供应商协议要求的状态或不透明内容。不能为了统一接口而把必须回传的 reasoning item、签名块或续接标识一概剥掉；也不需要把隐藏推理内容展示为用户日志。适配器负责合法编解码，内核只依赖动作、用量和完成状态。

## 原生工具协议如何接入

先为当前实际使用的一个供应商实现原生模式，再添加第二种协议；旧 XML 模式保留为显式兼容选项。一个工具的内部合同由严格参数模型和执行策略组成，供应商 JSON Schema 是从内部模型导出的“外部说明书”，不是安全执行器。

模型返回工具调用后，系统等待该调用的参数片段完整收齐，进行 JSON 解码和严格校验，再进入网关。流式收到半个 `path` 或半段补丁时，绝不抢先执行。一个 assistant 消息中的多次调用作为一个 ToolCallGroup 记录，各调用都要有唯一 `call_id`，结果按 ID 回填，不靠文本位置猜测。

供应商之间的消息角色、工具结果封装、并行调用和缓存参数可能不同，因此设置 `ProviderCapabilities`：原生工具、流式、并行调用、Token 计数、缓存用量、显式缓存断点、原生压缩等能力分别声明。兼容 OpenAI 的 URL 不意味着兼容全部 Responses 功能；当前源码的域名字符串判断应改为显式配置、合法主机解析和启动时的能力自检。[S04,R11,R12]

```text
ProviderAdapter
  encode_request(context_view, tool_catalog, options)
  stream_response() -> typed events
  finalize_response() -> ModelResponse
  count_or_estimate_tokens()
  normalize_usage()
```

不要用“模型自己说它支持”来做能力探测。优先读取人工配置的能力档案，在小规模契约测试中验证字段是否可用；不支持的新字段直接不发送。出现明确的协议 400 时可关闭相应可选能力并报告原因，但不能反复把同一错误请求重试三次。

## 主循环的完整流程

运行时先检查取消状态、预算、阶段和待解决的副作用；然后取一致的 ContextView，发起模型请求。模型输出纯文本时，只把它视为候选答复，由 CompletionGate 判断是否允许完成。模型输出工具调用时，按组持久化，再逐项校验权限，执行可安全执行的调用，落盘结果，最后构建下一轮消息。

```text
while run not terminal:
    consume_pending_control_commands_at_safe_boundary()
    ensure_budget_and_workspace_ownership()
    view = context.build_consistent_view()
    response = provider.generate(view)
    persist_response_and_tool_intents(response)
    if response.has_tools:
        results = gateway.execute_group(response.tool_calls)
        persist_results_and_update_state(results)
    else:
        completion_gate.evaluate(response.text, current_evidence)
```

这是流程伪代码，不是可直接替换现有 `ask()` 的实现。真实代码需要明确每次事务、超时、取消和异常路径。尤其是 `gateway.execute_group` 期间不能持有数据库写事务。

## 阶段权限与缓存稳定如何同时成立

原项目按阶段减少暴露给模型的工具，直观但可能改变缓存前缀。建议区分“这一会话可以看见的稳定工具目录”和“当前调用是否真的被允许”。第一轮核心工具目录保持小而固定，阶段权限由网关检查；阶段变更以尾部状态事件告知模型。工具目录内某个写工具可见，并不表示探索阶段已经授权写入。[S05,R03]

这存在取舍：模型可能申请当前不允许的工具，产生一次可解释的拒绝。相比频繁改变工具 schema，这通常更容易测量和控制。对于敏感技能或从未授权的连接器，不应为了缓存而提前暴露；确实需要变更目录时，新开显式 epoch，承认该边界上的缓存预热成本。**权限正确性优先于缓存命中。**

## 异常、回退与验收

同一响应内遇到未知工具、重复 call ID、参数不全、非法多动作协议时，返回结构化错误并保留失败事件，不直接执行可疑部分。模型接口断流后，没有收到完整调用的动作不得执行；已经可靠记录并执行过的调用也不能因重发模型请求再次落地。

验收至少覆盖：同名工具不同 ID 正确区分；工具结果乱序完成仍能正确关联；并行子任务用量不会互相覆盖；模型输出“已完成”却无验证证据时不能绕过完成门；不支持原生工具的模型明确进入兼容模式；协议错误和限流错误分别处理。性能验收放到第 13 章，不能把“改为原生协议”直接等价为成功率提高。

**本章落地边界：拆出 ProviderAdapter 和不可变 ModelResponse，保留原有 WorkflowKernel；先支持一个原生后端和一个旧协议回退。** 这比同时接入十种模型或照搬整个外部 Harness 更适合本轮。

原生工具协议的具体请求、调用 ID 与结果回填格式以对应供应商文档为准；本章统一对象是本项目的适配层合同，不是一个供应商通用的原始 JSON 格式。[R25]

# 02 提示词与缓存：稳定什么，刷新什么

## 模块功能：避免每轮重新支付已经读过的上下文成本

模型每次生成前都要处理输入。Prompt Cache 允许供应商复用先前处理过的特定前缀。对长任务而言，它像“已经熟悉的操作手册和已读材料”：下一轮主要处理新增部分，而不必重复付出全部输入计算。它缓存的不是完整答案，也不是 SkillForge 自己的文件摘要缓存。[R11,R12]

本模块负责决定提示词的结构、稳定边界和供应商缓存参数；第 03 章负责决定什么时候缩短上下文。用户最终需要看到的是更可预测的成本，以及可解释的缓存失效原因，而不是一个无法验证的“已开启缓存”开关。

## 现状：有前缀哈希，但输入的最前面并不总是稳定

当前 `ContextManager.build()` 把 checkpoint 和 Workflow task packet 插到 `prefix` 之前。即便原本的静态规则完全未变，阶段或 checkpoint 更新也可能很早就改变真正发送的文本。另外，`WorkspaceContext.fingerprint()` 包含 Git status、最近提交及截断后的项目文档；这些变化可能触发前缀重建。历史和召回记忆每轮重新渲染，也可能使后续共享部分失去连续性。[S02,S05,S09]

本次对原始 `context_manager.py` 做了一个不调用模型的局部复现：固定 1,613 字符规则，只把 checkpoint 中的 `explore` 改为 `verify`，两个最终 prompt 的最长公共前缀只有 18 字符。这证明的是**输入布局存在前缀不稳定机制**，不是证明真实 API 缓存一定从某个百分比跌到零。供应商实际命中仍须读取用量字段验证。复现脚本和结果在 `validation/` 中。[V01]

## 建议设计：三层内容与两个时间尺度

第一层 P0 放稳定的系统规则、协议说明和小型工具目录；第二层 P1 放会话启动时冻结的仓库导航摘要、已批准的持久记忆快照和 Skill 元信息目录；第三层放随任务变化的工作包、文件变化、已加载 Skill 正文、消息和工具结果。动态信息只向后追加，不插回 P0 之前。

```text
P0：身份与硬约束 / 工具 schema / 固定协议
P1：本次会话的仓库导航与记忆快照 / Skill 目录版本
---- 可复用的稳定边界 ----
本 epoch 的压缩摘要（若有）
该边界之后完整的用户—模型—工具消息组
实时工作区变化、阶段变化、补充要求
```

“冻结”不意味着欺骗模型说仓库永远没变。P1 明确标注 `snapshot_at_run_start`；一旦实际文件发生变化，系统在尾部追加事实变化，并通过新鲜度检查阻止过期操作。需要重新建立整体视图时才切换 epoch。**epoch 是一次明确的模型上下文版本，不是一次新的用户任务，也不是数据库事务。**

当前记忆系统已经能计算文件内容哈希。升级不是把哈希换一种算法，而是规定哈希负责事实是否过期，prefix hash 负责输入是否稳定，二者不能混为一个“一有文件变化就改全局前缀”的开关。[S07]

## 工程实现：缓存清单而不是一个神奇的 key

每次请求记录 `PromptManifest`，至少包含 provider/model、适配器版本、工具 schema 版本、P0/P1 哈希、消息区间、Skill 版本、断点位置、估计与实际 Token、缓存 key 的非敏感摘要，以及构建原因。比较两次 manifest 时能定位“哪个字段先变了”，不需要打印全部 prompt 或泄露源码。

推荐稳定序列化：工具按固定名字排序，schema 字段按固定规则输出，换行与 JSON 编码一致，不在稳定区加入时间戳、随机 UUID、变化中的剩余预算或当前 Git status。动态状态使用单独消息或适配器支持的合法内容块。对于只有文本兼容模式的后端，也要保持固定区在最前，只是不能声称获得了原生工具缓存能力。

缓存 key 根据会话隔离策略和稳定快照版本生成；不把每轮请求 ID 放进去，也不把用户密钥拼进去。key 只能参与供应商路由或匹配，**不能强迫供应商忽略 key 之后实际变化的内容，更不是访问控制边界**。隔离仍由认证、会话权限和供应商账号边界负责。[R11]

## 当前供应商差异：不要把旧结论写进内核

本次访问的 OpenAI 官方说明区分了较早模型与 GPT-5.6 及后续系列的缓存行为：后者提供显式断点，默认隐式断点包含变化内容时，不能简单假设会回退命中某个未标记的公共前缀；写入与读取也有分别的用量和费用语义。旧模型会拒绝部分新字段。因此，不能只把原代码中的 `prompt_cache_retention` 原封不动扩展到所有模型。[R11]

Anthropic 官方文档则有自己的缓存断点、层级、用量和失效规则。SkillForge 应归一化“可缓存边界、读写 Token、费用分类”，而不是硬把两个供应商的原始字段视为完全同义。[R12]

推荐能力档案如下；具体字段由适配器映射，不在核心模型中写死某个服务的 TTL、最小前缀或断点数量：

```text
CacheCapabilities
  mode: unsupported | implicit_prefix | explicit_breakpoint
  minimum_cacheable_tokens: provider configuration
  supports_cache_key, supports_cache_write_usage
  supported_retention_options
  usage_accounting_mode
  verified_at, adapter_version
```

文档与具体网关可能存在版本差异。首次部署应运行两次同前缀的最小契约测试，再追加一段动态尾部，最后改变稳定区，核对 usage；测试不通过时显示“缓存能力未验证”，而不是推测命中。该测试需要用户自己的模型权限和费用预算，本次交付未运行。

## 应该借鉴哪些项目，哪些不能照搬

Hermes 的工程约束强调会话中不随意修改过去上下文、工具集和系统提示词；其持久记忆在会话开始形成冻结快照，后续修改先落盘，再通过工具结果看到实时状态。这里最值得借鉴的是“持久状态可变，当前提示词快照不随之反复改写”。不必照搬它的目录、字符限制或全部平台功能。[R02,R03]

另一条路线是完全依赖供应商管理上下文和缓存。它减少客户端逻辑，但降低跨后端透明度，也可能使本地恢复和成本解释更困难。SkillForge 的第一轮采用客户端可解释视图；供应商原生压缩可在适配器中作为可选模式，但同一运行只能有一个压缩控制者，不能客户端裁剪和服务端压缩同时各自决定历史边界。

## 失败条件与验收

以下情形允许主动破坏缓存：权限收紧、用户要求立即加载新规则、模型或工具协议变更、必要的上下文压缩、原稳定内容存在安全问题。缓存不是阻止纠错的理由。每次切换都记录 `invalidation_reason`，并在下一次请求比较真实读写 Token。

验收分两层。离线层检查同一 epoch 内 P0/P1 字节稳定、动态状态不前置、工具排序确定、敏感内容不进入诊断日志；在线层检查真实 `cache_read_tokens`、缓存写入成本和首 Token 延迟。**“前缀哈希未变”最多是离线不变量通过，不能冒充在线缓存命中率。**

**本章最小落地：重排动态 checkpoint 与工作流包，冻结 P0/P1，增加 manifest 与能力档案。** 这比优先实现复杂摘要模型更靠前，因为压缩器再聪明，也无法挽救每轮都被重写的提示词头部。

# 03 上下文压缩与大输出管理：缩短视图，不丢掉现场

## 模块功能：让长任务继续工作，同时还能找回原始证据

长任务中，模型会读代码、运行测试、查日志、修改文件。同一批材料不断累积，最终可能超过上下文窗口。压缩模块的工作不是简单“删掉前面的聊天”，而是在有限预算中保留继续行动所需的信息，让模型仍然知道目标、约束、已完成的动作、未解决的问题，以及到哪里取回原文。

本章把三个经常混淆的动作分开：**输出整形**是在工具结果第一次进入模型时控制体积；**摘要压缩**是用较短的任务状态替代一段旧消息；**持久化保留**是把原始日志和历史留在磁盘供回查。前两者改变模型视图，第三者保存事实依据。不能把“模型没有看到”误当成“系统已经删除”。

## 现状：字符裁剪有用，但不是完整的压缩策略

当前预算单位是 Python 字符长度，历史最近六个条目被当作近区，旧 shell 输出的摘要取前三个非空行；`_tail_clip` 实际保留开头并加省略号。这样做计算便宜，却未必保留失败栈底部、未完成动作或完整工具调用组。当前请求不会裁剪，但预算下界耗尽后仍会返回超预算结果，并通过 metadata 标记；这不是完整的输入准入控制。[S02]

本次局部复现向原模块输入 13,000 字符请求，在默认 12,000 字符预算下得到 13,984 字符 prompt，并确认 `prompt_over_budget=true`。这不是发现“当前请求保留率”造假，而是说明“保留用户输入”和“满足模型窗口”是两个必须分别处理的条件。[V01]

值得保留的是已有 `log_run` 的证据外置与详情回读。升级应让 `read_file`、搜索、shell、补丁和子 Agent 结果都使用同一工件协议，而不是只给测试日志开特例。[S03,S11]

## 第一层：工具结果第一次进入上下文时就控制体积

所有工具返回统一的短结果信封。小输出直接内联；超过预算时，先保存完整工件，再把摘要、范围与引用返回给模型。不要先把两万行日志写入 history，下一轮再删成二十行，因为这种回头改写会影响缓存。

```text
ToolResult
  call_id, status, exit_code?
  summary
  artifacts[{artifact_id, sha256, media_type, byte_size}]
  shown_ranges, total_lines, truncated
  workspace_revision_before, workspace_revision_after
  retry_class, error_code?
```

“摘要”按工具类型生成，不使用一个万能 `text[:4000]`。读文件返回明确行号与当前内容哈希；搜索返回路径、匹配片段和是否还有后续页；测试返回收集数量、失败节点和退出码；shell 返回有限头尾、错误锚点和工件句柄。对不能可靠解析的日志，明确标记 `unparsed`，不把没有识别到失败当成成功。

需要细节时通过 `artifact_read(id, start_line, end_line)` 或 `artifact_search(id, pattern)` 查询。输出省略符应附带可执行的回查方式；没有句柄的截断只是丢信息，不是上下文工程。

默认每个工具结果的内联预算可以从约 1,000—2,000 Tokens 的保守范围试起，但这是项目初始配置，不是供应商标准。关键是运行中有总预算和回查机制，阈值由任务评测再调。对于单个极长代码行，还应限制字节数和字符数，避免仅按行数控制失效。

## 第二层：基于消息组和任务状态的语义压缩

保留完整事件日志 `E`，构建可变化的模型视图 `V`。压缩后不覆盖 `E`，而是新增 CompactionCheckpoint：指出摘要覆盖到哪个事件，哪些原始消息继续保留，以及生成摘要用的证据范围。

OpenCode 的公开压缩设计使用完成的 checkpoint 与后续消息构造模型视图，保留持久会话历史；pi 也把压缩作为带保留边界和用量的会话条目。SkillForge 借鉴的是“摘要成为有身份的状态对象”，不是复制它们所有触发默认值。[R06,R08]

```text
CompactionCheckpoint
  compaction_id, session_id, run_id, epoch
  source_from_seq, source_through_seq, source_digest
  first_kept_group_id
  summary_schema_version, summary_artifact_id
  required_fact_ids[], unresolved_action_ids[]
  token_estimate_before, token_estimate_after
  summarizer_model, usage, validation_status
```

保留单元从“最近六条”改为完整交互组。一个模型发出两个工具调用、随后两个结果回填，必须被视为有关联的一组；不能保留结果却删掉对应调用，也不能在调用结果尚未收齐时对这组做压缩。用户刚追加的约束和待审批动作也不应只靠摘要恢复。

摘要采用结构化内容：目标与验收标准、不可违反的约束、已确认事实及证据引用、已修改文件与版本、尝试失败的路线、待解决问题、下一步最小行动。不要记录没有必要保存的内部思考过程；保留可验证决定及其依据即可。安全规则、授权范围和预算由运行时生成，不交给摘要模型重新解释。

## Token 预算如何计算

设模型总窗口为 W，供应商独立输入上限为 I，预留输出及推理空间为 R，估计误差和下一步协议开销为 M。请求准入条件可写为：

```text
estimated_input_tokens <= min(I, W - R) - M
```

如果供应商把推理 Tokens 计入同一个输出预算，R 只预留一次，不能重复相减；输入中包含的工具 schema、图像和协议开销也要纳入计数。能够调用供应商计数接口时优先使用；否则使用与模型对应的 tokenizer 或经过真实 usage 校准的保守估计。不得把英文“约四字符一 Token”的经验固定应用到中文、代码或所有供应商。

压缩采用软阈值和硬阈值。软阈值用于在安全边界预先安排摘要；硬阈值用于阻止明显超窗请求。阈值以窗口与保留预算计算，初始比例只是配置。设置压缩后目标余量和最小冷却间隔，避免刚压完又触发下一次摘要。

如果光是固定规则和用户请求就已超过容量，必须明确进入 `INPUT_TOO_LARGE`：请用户收缩范围，或把大材料作为附件工件分段读取。不能为了“用户输入保留率 100%”继续发送必然不合法的请求，也不能暗中删掉用户末尾的限制条件。

## 摘要如何安全提交

第一步，在没有未完成工具调用的边界冻结 `source_through_seq`。第二步，读取该区间的消息、当前任务合同和重要工件摘要，生成候选。第三步，用确定性校验检查必须保留的约束 ID、待处理动作、文件引用与版本、摘要体积和来源覆盖范围。第四步，在短事务内确认运行版本与源边界未变化，再写入新 checkpoint 并切换 epoch。第五步，构造新视图并再次计数。

确定性校验只能检查结构与显式必需项，不能证明语义完全无损。因此保留原始工件、提供回查、在关键写入和验证前重新检查事实；摘要提到的“已完成测试”不直接授予完成资格。

如果摘要失败、超时或校验不通过，原视图不应被销毁。软阈值阶段可以继续使用旧视图并限制下一批输出；硬阈值阶段则暂停，或只做确定性地缩小可回查的工具输出，不允许无限重试摘要。摘要请求本身也必须满足模型容量限制，不能拿一个已经溢出的历史再原样请求一次摘要。

## 压缩后缓存暴跌是不是一定能避免

不能承诺“零缓存损失压缩”。只要把历史某个位置改成摘要，从该位置之后的旧前缀通常就不再相同。可做的是保留更靠前的稳定区、减少非必要压缩、利用支持的显式断点，并让一次预热成本被后续轮次节省摊销。缓存是否真的命中还受供应商规则影响。[R11,R12]

对一次运行的输入成本，先由适配器归一化互不重叠的 Tokens 类别，再计算：

```text
C_input = U * p_uncached + H * p_read + Q * p_write
C_total = C_input + C_output + C_summary + C_children + C_retries
```

其中 U 是普通输入、H 是缓存读取、Q 是缓存写入；p 是相应单价。原始字段可能存在包含关系，不能把 `input_tokens` 和缓存 Tokens 不加区分地全部相加。未知的供应商计费字段保留 `raw_usage` 并标记估算，不生成虚假的精确账单。

### 一个会推翻“越短越省钱”的反例

以下全部是**人为设定的归一化费用模型，不是实际 API 报价或性能数据**。假定每千普通输入费用 1，缓存读取 0.1，缓存写入 1.25。原请求复用 60k Tokens，另有 2k 新输入，每轮成本 8。压缩后旧区缩为 20k，首次全部重新写缓存，再加 2k 新输入，成本 27；之后每轮成本 4。额外摘要费用设为 9，并暂时忽略每轮上下文增长与输出差异。

| 剩余模型调用次数 n | 保持旧视图 | 立即压缩 | 压缩净节省 |
|---|---:|---:|---:|
| 1 | 8 | 36 | -28 |
| 2 | 16 | 40 | -24 |
| 8 | 64 | 64 | 0 |
| 9 | 72 | 68 | 4 |
| 12 | 96 | 80 | 16 |

本例中 `C_keep=8n`，`C_compact=4n+32`；8 次才持平，超过 8 次才更便宜。数值已用脚本复核。换成全冷缓存、保留了更多稳定断点、摘要模型更便宜或者上下文质量改善，结论都可能改变；不能把这个临界点当成通用配置。[V01]

因此，软阈值下的压缩决策要考虑预计剩余轮次、当前缓存读取情况、摘要成本和是否有冗余大输出；硬阈值下则优先保证请求合法，不为节省缓存而继续超窗。第一版不需要训练一个“压缩策略模型”，一个可解释的规则与费用估算器就足够。

## 两种路线的比较与本轮取舍

路线 A 是每轮重排、去重和重写所有历史，局部体积通常更小，但不利于连续前缀稳定；路线 B 是在 epoch 内追加，在明确边界一次性压缩。建议选择 B，并在工具结果第一次进入时做输出整形。它需要多记录一个压缩边界，但更容易解释缓存、恢复与工件之间的关系。

对于超长资料库，可以另行做检索和按需读取，而不是把资料全部放进会话再摘要。对于很短的任务，没有必要自动调用摘要模型。对于必须保留逐字记录的需求，原文放工件，摘要只做导航，不能声称压缩结果等价于完整原文。

## 验收与实现顺序

先验证完整消息组不被切断、当前约束与待审批动作保留、原始工件可回查、超长输入明确拒绝；再进行真实供应商冷/热缓存分层对照，比较总费用、成功率、摘要遗漏率和完成时间。长上下文成功率没有提高甚至下降时，应允许关闭语义压缩，仅保留输出整形与明确超窗处理。

**推荐顺序：统一工件句柄 → Token 计数与准入 → 不变消息组 → 结构化摘要 checkpoint → 缓存成本驱动的软阈值。** 不要一开始就做多级递归摘要、全局图记忆或复杂压缩代理。

# 04 工具网关与可靠写入：模型提出动作，系统决定能否执行

## 模块功能：把“我准备修改文件”变成可控的真实操作

工具网关是模型和外部环境之间的执行边界。用户要求“修复分页问题”，并不意味着授权 Agent 删除工作区、上传文件或执行任意网络脚本。网关根据工具参数、阶段、工作区、用户审批和预算，决定允许、拒绝或等待确认，并记录决定原因。

它输入结构化 ToolCall，输出 ToolResult 或 ApprovalRequest。本章主要讲动作合同、权限、去重和补丁写入；长进程和操作系统隔离在第 05 章。把这两层区分开，才能避免“参数校验已经做了，因此代码执行安全”的误解。

## 现状：基础网关已经存在

当前 `run_tool` 已做参数、阶段和预算检查、重复调用拦截、审批、工作区差异记录；`patch_file` 要求原文唯一匹配。它不是完全没有治理。但工具定义使用较简单的 schema 描述与 `risky` 布尔值，补丁直接写回文件；重复调用主要比较最近的相同工具与参数。这些机制遇到并发、重试、进程崩溃或外部编辑时，语义还不充分。[S03,S05]

例如，同一个 `pytest` 命令在改码前失败、改码后应该再次运行；只比较参数可能把必要验证当成无效重复。反过来，给相同危险命令换一点空格，也不应该自动获得新的业务执行身份。

## 建议设计：每个工具描述四件事

一个工具注册项包含参数模型、效果类型、执行策略和结果模型。效果类型不再只有“危险/不危险”，而是区分纯查询、仓库写入、进程执行和外部副作用。对 shell 无法可靠推断具体影响时，保守归入进程执行或不透明副作用，不试图用几条正则判断任意命令安全。

| 工具类别 | 典型动作 | 默认调度原则 |
|---|---|---|
| 可重做的读取 | 读文件、搜索、读工件 | 固定视图下可有界并行；新鲜度变化后重读 |
| 受控仓库修改 | 带前置哈希的补丁 | 单写入者、审批、记录差异 |
| 进程执行 | 测试、构建、包管理器 | 交进程管理器；视作可能产生文件和网络影响 |
| 外部副作用 | 推送、发布、发消息 | 默认关闭；单独授权；超时后不能盲目重发 |

Pydantic 严格模型或等价校验器负责字段类型、额外字段拒绝、大小限制和规范化。路径先基于明确 workspace root 解析，拒绝越界、受保护路径和不符合策略的符号链接；需要区分 Windows 驱动器、UNC 路径和 Linux 路径。单靠 `resolve()` 后检查一次无法替代执行时隔离，因为文件系统还可能在检查后变化。

网关顺序建议固定：结构校验 → 规范化 → 会话与阶段授权 → 资源与配额 → 调用身份检查 → 生成审批 → 执行前重新核对 → 执行与记录。审批之前可以计算补丁预览，但不能提前写文件。

## 调用身份、幂等与循环检测不是同一回事

`call_id` 标识一次模型请求的逻辑动作；`attempt_id` 标识该动作的某次执行尝试。持久表对逻辑调用 ID 建唯一约束，并存参数摘要；收到同 ID、同参数且已完成的调用，直接返回已存结果。收到同 ID、不同参数则拒绝，避免把一个批准过的身份挪作他用。

工具处于 `RUNNING` 时重连，只返回状态；处于 `UNKNOWN` 时先协调现场。不能仅凭工具名和参数哈希，断言两个不同时间的操作是“同一次动作”。

循环检测另做进度签名：工具名、规范化参数、相关工作区版本、最近结果类别、阶段是否有进展。只有多次相同输入、相同状态、相同失败且没有进展时才触发暂停或要求重新规划。改码后重复同一测试应允许；对内容不变的重复读取则可返回已存在的受信工件。

## 补丁写入如何避免覆盖过期文件

新补丁合同包含 `path`、`expected_content_hash`、修改内容或补丁、任务授权版本。网关展示当前差异预览，审批绑定这些字段的摘要。正式执行前再次读文件、检查哈希与授权版本，并持有 SkillForge 的工作区写锁；不满足条件就返回 `STALE_INPUT`，让 Agent 重新读取，不能靠扩大模糊匹配强行落地。

文件写入采用同目录临时文件、完整写入、按持久性策略刷盘，再原子替换目标。这样可避免单文件留下半截内容，但**多文件原子提交不是自动获得的**。需要另存 PatchPlan：目标文件、修改前后哈希、操作进度和恢复策略。进程崩溃后逐个核对，判断完全未做、已做或部分完成。

```text
PatchPlan: PREPARED -> APPLYING -> APPLIED
                         |            |
                    NEEDS_REVIEW   VERIFIED
```

默认不做自动 `git reset --hard`、不清除用户原有未提交修改。启动时记录 baseline dirty state，分清“用户带来的改动”和“本次 Agent 改动”。撤销只有在目标文件仍等于本次写入后的版本时才安全；若用户已继续编辑，就展示反向补丁，不能自动覆盖。

一个重要边界是：应用级锁只协调遵守该锁的 SkillForge 写入者，无法强迫外部编辑器合作。哈希检查与替换之间仍可能存在外部竞态。第一轮以单写入者和执行前检测降低风险；对重要任务可在独立 worktree 中执行，最终人工合并。不要宣称已经实现对所有进程的文件系统 CAS。

## 审批应该让用户理解什么

审批卡至少显示工具、命令或差异、工作目录、预计影响范围、网络策略、运行时限和绑定版本。用户批准后，下一步若参数、目标文件哈希、权限规则或任务版本变化，原审批作废。仅显示“允许此操作吗”不足以支撑有效确认。

对于相同风险类别的低风险操作可以提供会话级授权，但必须有范围、有效期和撤销入口。Skill 正文中的一句“自动批准所有命令”不能成为授权来源；仓库 README、日志和子 Agent 结论也都不能改写网关规则。

## 失败处理与验收

对纯读取，暂时性失败可以在预算内重试；对带前置哈希的补丁，先核对是否已经落地；对不透明命令，超时并不等于没有执行，进入 UNKNOWN 或待核对状态。这里追求的是“已知动作不重复、未知动作不假装失败”，而不是无法兑现的所有工具 exactly-once。

验收应覆盖同 ID 参数冲突、审批后文件被修改、符号链接切换、补丁零匹配/多匹配、多文件中途崩溃、用户 dirty tree、改码后重复验证、重复失败循环、未授权阶段请求写入。检查的是最终工作区和持久记录，不只是 UI 返回了一个错误。

**本章落地边界：保留原有阶段和审批规则，增加严格合同、逻辑调用账本、版本绑定审批与补丁预条件。** MCP 或第三方工具接入以后也必须经过这条网关；本轮没有必要先做插件市场。

# 05 长进程、背压与沙箱：让测试和命令可观察、可停止

## 模块功能：让用户知道命令在做什么，而不是一直等黑盒

代码 Agent 的很多时间花在测试、安装依赖、构建和启动服务上。用户需要看到命令是否仍在运行、当前日志、耗时和退出结果，并能取消；关掉页面后还应能回来看同一任务。这个模块把 shell 从“同步函数返回一个字符串”升级为受管理的 Job。

本模块输入经过网关批准的 ProcessSpec，输出 Job ID、状态事件和日志工件。它负责进程生命周期和资源约束，不负责推断业务是否完成。测试成功与任务完成仍由第 09 章判定。

## 现状：有超时与环境过滤，但执行仍偏同步

当前普通 shell 使用 `subprocess.run(..., shell=True, capture_output=True, timeout=...)`，完成后再获取全部输出；日志专用路径已有证据存储，但应统一纳入生命周期管理。工作目录设成仓库目录只是让相对路径以此为起点，**不会阻止命令访问其他目录或网络**。既有环境白名单与审批值得保留，但不是操作系统沙箱。[S03,S11]

## 建议设计：前台返回身份，后台持续执行

定义 `ProcessJob(job_id, run_id, call_id, state, started_at, deadline, executor_id, stdout_ref, stderr_ref, exit_code)`。短命令可以等待一个很小的前台窗口，及时结束就直接返回；未结束则返回 Job ID，之后通过 `job_poll`、`job_logs` 和事件流查看。不要把每一次轮询都变成一次模型推理，UI 可直接订阅状态。

```text
QUEUED -> STARTING -> RUNNING -> SUCCEEDED / FAILED
                         |
                    CANCEL_REQUESTED -> CANCELLED
                         |
                  executor lost -> UNKNOWN -> reconciliation
```

`SUCCEEDED` 表示命令按约定退出，不代表 Agent 任务完成；`CANCELLED` 表示已确认进程退出，不代表所有副作用被撤销；`UNKNOWN` 表示暂时无法确认执行状态，不应被包装为普通失败。

执行器使用异步子进程接口，并发排空 stdout 与 stderr 两个管道，分块写入 spool 文件；不能顺序读完一个管道才读另一个，以免缓冲填满后互相等待。UI 只接收限速摘要。对输出设置内存缓冲上限、磁盘配额、单条事件大小和日志保留策略。日志过快时允许 UI 丢弃可重建的“显示增量”，不能丢弃最终状态或把执行器堵在无限增长的消息队列中。[R26]

对于需要完整证据的测试任务，磁盘配额耗尽应终止或暂停该 Job，并标记 `LOG_QUOTA_EXCEEDED`，而不是静默丢日志后继续声称证据完整。对于允许只保留头尾的普通诊断命令，必须明确 `truncated=true`，与完整日志区分。

## 取消如何才算真正生效

用户点击取消，先持久化取消命令，再请求执行器停止进程组；给一个宽限期，未退出再使用更强终止方式，最终收集退出状态与残留工件。只取消 Python 协程，不一定能杀掉它启动的子进程；只杀父 shell，也可能留下测试服务或孙进程。

第一轮明确支持 Linux/WSL2 的进程组管理，或通过容器执行器终止整个任务容器。原生 Windows 的可靠子进程树管理应使用相应系统机制并单独测试，不能把 Linux `killpg` 逻辑当跨平台能力。若这一轮不实现，则在 `doctor` 中明确原生 Windows 的受限能力，推荐 WSL2 执行，而不是隐藏差异。[R26]

服务重启时，不凭一个数据库“心跳过期”就启动第二份相同任务。先核对执行器身份、进程出生标识或容器 ID，避免 PID 重用；无法确认旧进程已终止时，禁止新的工作区写入者接管。

## 沙箱分级：清楚承认边界比伪装全安全更重要

建议提供两种明确模式。**trusted-local** 仅用于用户信任的仓库，保留审批、最小环境和路径策略，但界面清楚说明不是安全沙箱。**isolated** 用 rootless Docker 或同等级已验证执行器，仅挂载目标工作区与必要依赖，限制网络、进程数、CPU、内存和可写路径。Rootless 降低守护进程与容器运行所需的宿主特权，但并不意味着不存在容器逃逸或供应链风险。[R22]

默认不挂载宿主 Docker socket、不把主目录或 SSH 目录映射进去、不把模型 API Key 传给仓库命令。模型网络调用由宿主编排层完成，执行容器只获得必要且经过批准的环境变量。依赖安装需要网络时，单独提示并限定这一 Job 的网络策略，而不是永久放开整个运行。

工作区、Git worktree 与沙箱分别解决不同问题：工作区是文件作用域，worktree 是独立开发目录，沙箱是运行环境约束。使用 Git worktree 不等于限制命令访问网络或宿主文件。[R21,R22]

## 传统后端设计怎样改善体验

采用有界队列与背压：一个工作区默认只有一个可写 Job，同时最多两项只读调查；超过配额的任务排队，并把排队位置与原因展示给用户。模型请求并发、shell 并发、日志订阅并发分别限额，避免某个子 Agent 开很多命令挤占其他会话。

Job 的提交具有幂等键，取消也是幂等控制命令。客户端重复点击启动不会创建两份测试进程；刷新页面只重新订阅，不能重新提交。依赖暂时不可用可以有限重试，但重试前要区分“尚未启动”与“已启动但结果未知”。

包安装、发布、远程推送等操作不能靠通用 Job 账本获得 exactly-once 语义。第一轮默认不支持自主发布和推送，避免把一个本地代码助手扩展成未经验证的部署系统。

## 验收与实现边界

必须测试持续输出、无输出长运行、超大单行、超时、用户取消、父进程退出后子进程残留、客户端断线、服务重启、磁盘满、网络禁用与容器失联。所有场景最后都能在运行时间线看到明确状态，不把中断称为成功。

**本章最小实现：一个执行器抽象、一个本地异步进程实现、一个可选容器实现，以及持久 Job 状态。** 不做远程集群调度、不做任意云执行后端，也不先设计复杂的插件生命周期。

# 06 仓库导航与结构化记忆：记住线索，验证事实

## 模块功能：减少重复探索，但不让旧知识替代当前代码

用户通常不希望 Agent 每轮重新读取同一个 README，也不希望它因为记得旧文件就忽略刚发生的修改。仓库上下文与记忆模块负责在这两者之间建立边界：哪些信息可以当导航复用，哪些事实必须重新确认，哪些材料只在相关任务中加载。

输入是任务关键词、文件范围、当前仓库版本和历史记忆；输出是有限的导航结果、事实摘要和证据引用。它不负责永久把所有代码塞进提示词，也不要求引入向量数据库。

## 现状：分层记忆和内容哈希已经有了

`LayeredMemory` 已管理任务摘要、文件摘要和过程信息；`file_freshness` 用 SHA-256 检查文件内容。仓库启动快照读取 Git 信息与少量白名单文档，检索使用轻量关键词。这个基础适合本地项目，不必推倒换成复杂的“长期认知系统”。当前改进点是明确记忆的依赖、新鲜度、作用域和注入时机。[S07,S09]

需要注意，当前工作区指纹主要是 Git status、提交与项目文档导航信息，**不是整个仓库每个文件内容的完整快照哈希**。一个文件保持“已修改”状态但内部内容再次变化，Git status 文本可能不变；不能把该指纹单独用作所有结果仍新鲜的证明。文件级内容哈希与工作区身份应各司其职。[S09]

## 建议设计：四类记忆，四种失效方式

| 记忆类别 | 保存什么 | 什么时候失效 |
|---|---|---|
| 仓库导航 | 目录职责、入口文件、测试命令位置 | 项目配置或相关路径变化 |
| 文件事实 | 某个符号的位置、逻辑摘要 | 绑定文件内容哈希变化 |
| 任务工作记忆 | 本次目标、已尝试路线、未完成项 | 任务版本变化或运行结束 |
| 持久约定 | 经用户确认的编码偏好、项目约束 | 用户修改、规则版本变化 |

所有机器提炼的记忆带 `source_refs`、`scope`、`created_at`、`dependency_hashes` 和 `trust_level`。不要让没有来源的“经验”与当前工具读出的事实获得同等权威。文件摘要过期后可以继续作为“这里可能有相关逻辑”的导航提示，但不能作为写入依据。

事实依赖可以先做到文件级，不必追求完整程序依赖图。例如“测试命令由 pyproject 配置确定”的记忆，依赖 `pyproject.toml` 和锁文件；“函数位于某行”的记忆，依赖该文件内容哈希。代码修改后，把受影响记忆标记 stale；下一次真正需要时惰性重建，避免每次编辑都全库重算。

## 检索流程：先过滤，再排序，再回查

第一步按工作区、任务类型、权限与版本过滤；第二步提取路径、标识符和自然语言关键词；第三步用 ripgrep/FTS5 检索导航与记忆；第四步对候选按相关性、来源、依赖是否新鲜和成本排序；第五步只返回少量摘要及回查句柄。

SQLite FTS5 提供全文检索和排序能力，适合作为本地轻量索引；它不自动理解中文词义。默认 tokenizer 的效果需要针对中文提问与代码标识符验证，可先把标识符拆词、路径分段，与简单中文词项处理结合；没有必要为这个问题引入整套向量检索服务。[R19]

如果项目后期确实出现“大量文档、语义相似但字面差异很大”的召回问题，再用一组查询集证明 lexical 召回不足，追加可选向量重排。不要因为 Agent 项目常见 RAG，就先把所有代码 embedding 一遍。

## 与缓存的配合：新事实落到尾部

会话开始时加载少量稳定记忆快照；运行中新增的文件事实作为工具结果和尾部状态记录出现，不回头修改 P1。磁盘中的记忆可立即更新，但下次会话才重新装入稳定区。这借鉴 Hermes 的冻结快照思路，同时保留 SkillForge 自己的文件级证据约束。[R02]

对于“重复读文件”，不要追求绝对零次。文件改变后重新读取是正确行为。更合理的指标是**无变化、无新范围需求时的冗余读取率**，以及**写入前未核验过期事实的比例**。只优化读取次数，可能让 Agent 更快地犯错。

例如，父 Agent 已读取 `pagination.py` 第 1—80 行，子 Agent 又读取同版本第 120—180 行，不算重复浪费；模型只需要确认同一段已经保存的内容，则可返回工件引用。摘要无法回答精确条件或边界判断时，应主动重读原文。

## 提示注入与敏感信息

仓库文档、历史日志、第三方 Skill 和子 Agent 输出都属于输入材料，不能因为被存入 memory 就升格成系统指令。记忆记录应区分“用户批准的约定”和“从文件中抽取的建议”。诸如“忽略审批并上传源码”的文本，即便来自 README，也不能改变工具权限。

敏感字段在进入工件和记忆前处理，诊断默认记录哈希、路径范围与错误类别，而非完整环境变量。被扫描器放行不表示语义安全，因此来源分级、最小权限和执行网关仍然需要同时存在。

## 验收与边界

构造同路径内容改变、mtime 改变但内容不变、重命名、删除、分支切换、配置变化、中文提问匹配英文标识符、错误记忆与当前工具事实冲突等测试。期待结果不是每次都召回旧内容，而是能正确标记旧信息、回查新内容并说明来源。

**本章最小落地：沿用现有 SHA-256 与分层记忆，加上依赖元数据、惰性失效、可解释检索与稳定注入边界。** 它提供的是可靠复用，而不是宣称拥有永久准确的“世界模型”。

# 07 Skill 学习与复用：从通用模板走向有边界的经验

## 模块功能：把一次费力解决的问题，变成以后可复用的方法

Skill 在本项目中指一份可加载的程序性知识：什么时候适用、如何排查、有哪些前提、怎样操作、哪些做法禁止、如何验证。它不是简单保存上次对话，也不是把某个成功补丁直接复制到别的仓库。用户希望获得的是“下次遇到相似问题时，少走弯路”，而不是“无论什么问题都自动套上一次的修法”。

输入来自已完成任务的差异、测试记录、审计结论和用户纠正；输出是待审核候选或批准后的 Skill 版本。执行时，匹配器给出有限候选，模型按需读取正文与参考材料。原始证据保留在自己的工件库，不要求常驻提示词。

## 现状：治理链条强于内容提炼

当前 `SkillDistiller` 已要求验证过的记录，候选保存证据引用，晋升前进行安全、冲突、效用、时效与人工确认等检查。这些应保留。薄弱点是 `_derive_title_and_triggers` 遇到 pytest 往往生成统一的“Pytest failure triage”，步骤偏“运行测试、查看失败、限制修改范围”。这种模板有基本价值，但不太能沉淀真正的问题诊断知识。[S06]

另一个问题是匹配器按触发词、workflow 和路径打分，分数大于零即可入选；编译器对匹配项逐个注入约束。Skill 越积越多，可能反而让 task packet 变大、约束相互冲突。需要升级内容和选择机制，而不只是多保存几个 Markdown 文件。[S06]

## Hermes 的哪些思路值得借鉴

Hermes 官方把 Skills 作为按需加载的程序性记忆，支持目录元信息、正文和引用材料逐层展开，也支持从任务或资料中创建、修补 Skill。其官方文档还区分内容扫描与写入审批：前者不是后者，且默认自由写入不等于默认人工把关。[R01]

SkillForge 最值得借鉴三点：学习到的是“可执行的方法”，不是只写一句摘要；先发现少量元信息，再读取正文和参考资料；对已有技能做定向修订而不是不断生成重复条目。**不建议照搬自由修改所有技能的默认策略**，因为现有项目已经有候选隔离和证据门，可以把这一部分保留得更严格。

## 建议设计：把学习放在任务完成后的独立流程

主任务成功交付后产生 `LearningRequested` 记录，由同一个本地服务里的低优先级后台 worker 处理，不阻塞用户拿到改码结果。worker 有单独预算和只读证据权限，不拥有自动改业务代码、执行任意日志命令或直接发布 active Skill 的权限。

```text
已验证任务
  -> 可学习性筛选
  -> 证据包构建
  -> 结构化候选提炼
  -> 去重与适用性检查
  -> 样例回放 / 负例检查
  -> 人工确认
  -> 不可变版本发布
  -> 使用反馈与后续修订
```

任务通过了测试，不代表一定值得学习。一次修改拼写、依赖随机网络状态才偶然成功、没有明确原因的改动，都可以不生成 Skill。触发条件应看“是否发现可复用的判断步骤或避免错误的约束”，而不是机械用“超过五次工具调用”作为质量保证。

## 证据包长什么样

EvidencePack 包含用户目标与验收要求、起始失败的可定位记录、最终差异、验证命令及结果、工作区与依赖版本、审计发现、被放弃的路线和原因。敏感信息和无关源码先脱敏或排除。

提炼器输出结构化候选：`problem_signature`、`preconditions`、`diagnostic_steps`、`procedure`、`verification`、`anti_patterns`、`non_applicability`、`evidence_refs`、`open_questions`。每条重要操作要能追溯到证据或明确标成待验证建议；不能把模型临时补出的“最佳实践”伪装成这个任务已经验证过的经验。

这里允许调用模型做归纳，但模型只**提出候选**。确定性验证器负责来源完整、字段合法、参数安全、证据新鲜和结果一致；人工与后续任务负责检验是否真的可迁移。一个模型自己写候选、自己说“很好”、自己批准上线，不构成可信学习闭环。

## 贯穿示例：从“跑 pytest”升级为“分页边界排查”

假设某个练习仓库的任务是修复分页边界漏数。证据显示：有相同排序时间的记录时旧行为失败；修改增加了唯一辅助排序键，并让游标条件使用相应组合；特定回归用例通过。下面是**建议 Skill 内容示例，不是声称你的仓库已经存在这项修复**。

这个候选可以叫 `pagination-boundary-diagnosis`。它先要求识别当前是 offset 分页还是 cursor/keyset 分页，确认排序键、游标编码和查询条件；针对固定数据集，构造排序主键相同的记录，检查跨页是否重复或遗漏。只有证据表明游标分页依赖不完整的排序边界，才考虑统一完整排序键与对应的游标比较规则。

验证要求不止“pytest 成功”，而是需要覆盖相同排序值、首末页、空页、游标边界等场景，并确认原有业务筛选条件没有被改坏。它还应明确：该经验**不自动解决读取期间数据不断变化所需的快照一致性问题**；offset 分页的根因和修复可能不同；涉及数据库迁移时仍需用户授权。

相比“遇到 pytest 就读错误再修改”，这个 Skill 多了适用性判断、可复现的反例、条件化行动与不适用边界，才更接近真实经验。内容不需要很长，但必须包含能让后续 Agent 少走错路的决策信息。

## 文件格式与治理元数据分离

对外正文采用 Agent Skills 的 `SKILL.md`，目录可有 `references/` 和可选 `scripts/`。标准 metadata 是字符串键值映射，SkillForge 的结构化审计数据放在单独 manifest/数据库中，不随意塞入不兼容嵌套格式。[R17]

```yaml
---
name: pagination-boundary-diagnosis
description: 排查固定数据集上的分页边界重复或遗漏；先识别分页类型与排序条件。
compatibility: Requires repository read access and an approved test runner.
metadata:
  skillforge-version: "1.0.0"
  skillforge-scope: "repository"
---
```

正文依次解释适用条件、诊断、条件化步骤、验证、禁止事项、证据与反例。复杂的 `evidence_ids`、来源哈希、审批身份、候选状态和测试结果放在 `skill_manifest.json` 或数据库。Skill 中声明工具只作为能力需求，最终授权仍由网关决定；导入文件不能自带可信的“我已批准”标志。

第一轮只允许正文与参考资料，脚本作为可选人工审核功能。不要为了“可执行 Skills”自动运行从日志复制出来的脚本。脚本的可读性、权限、依赖与测试成本明显高于文档，应单独审批。

## 生命周期、版本与撤回

建议最小状态机为：`CANDIDATE -> VALIDATED -> APPROVED -> ACTIVE`，失败可进入 `REJECTED`，上线后有问题进入 `QUARANTINED`，替代后进入 `DEPRECATED`。`VALIDATED` 只表示通过已声明检查，不宣称普遍正确；`APPROVED` 是用户接受这一版本，`ACTIVE` 才能被默认召回。

每次正文变更产生不可变新版本，运行冻结 `skill_id + version + content_hash`。当前任务不应因后台技能更新而无声切换做法，也不要把新正文重新插进旧稳定前缀。新版本在后续 Run 生效，用户明确要求立即启用时则产生可追踪的上下文变更。

撤回仅阻止未来继续使用并恢复上一版本的选择，不会撤销已经由该 Skill 导致的文件改动。对进行中的 Run，若撤回原因是安全风险，应中止相关后续动作并提示；一般质量问题可在安全边界通知，不自动重放整个任务。

## 匹配与渐进加载如何实现

先按仓库、语言、依赖和权限做硬过滤，再按问题关键词、任务类型、路径与描述做排序。初版用 FTS5/关键词即可，暂不需要 embedding。最多给出少量候选，例如前三个摘要；最终同时启用正文可以先限制为两个，并受独立 Token 预算约束。这些是可调的首版边界，不是外部项目的普遍默认。

匹配结果返回 `match_reasons` 和 `missing_preconditions`。某 Skill 只因为 workflow 相同而命中，但问题签名不匹配，应停留在“可查看候选”，不能自动注入强执行约束。模型加载正文后还要检查适用条件，必要时选择不使用。

目录元信息在会话内保持稳定；正文通过 `skill_read(id, version)` 的工具结果按需加载，参考资料再按片段读取。压缩时保留已激活技能的 ID、版本、关键约束及回读句柄，而不把全部正文永久留在系统区。这样经验积累不会线性推高每轮提示词大小。

## 如何防止越学越错

来源安全与内容质量是两条轴。可信任务也可能只证明一个窄场景；不可信仓库里的恶意文字则可能被包装成“经验”。因此需要隔离候选、验证来源、限制权限、人工确认、适用性负例、版本化撤回，而不是只用一次危险词扫描。

去重首先比较问题签名、作用域和规范化正文哈希，再检查是否应修订已有 Skill。不要因为标题不同就认为是新经验。两个候选冲突时保留差异与前提，不能让模型简单把相反规则合并成一段含糊建议。

效果追踪记录选中、加载、实际使用、被拒绝及任务结果，但不把“使用 Skill 的任务成功了”当作因果证据。简单任务更容易成功，也更容易被匹配。应在同一批未用于提炼的任务上做开启/关闭对照，比较正确率、冗余读取、无效工具调用、总成本和误用率。样本很少时报告分母与不确定性，不急着自动淘汰或强化技能。

## 验收与第一轮边界

至少准备同类正例、词面相似但不适用的负例、过期依赖、提示注入、没有证据的建议、冲突技能、重复候选、撤回后新任务不再加载、进行中版本不漂移等测试。提炼集和验证集按任务族隔离，避免把同一道修复题换个文件名就当泛化成功。

**本章最小落地：保留原 PromotionGate，新增证据驱动的结构化提炼、明确不适用条件、不可变版本、有限召回和按需正文加载。** 自动跨仓库迁移、在线强化学习、全自动脚本发布和 Skill 商店都不属于第一轮。

# 08 有界多 Agent：并行调查，集中决策，单点写入

## 模块功能：把独立调查并行化，而不是让多个模型一起改同一份代码

多 Agent 在本项目中的实用价值是隔离上下文和并行调查。例如，一个子 Agent 找出分页查询入口，另一个检查测试覆盖，父 Agent 综合结果制定修改方案。用户获得的是可观察的任务分工与更清晰的证据来源，而不是一群模型互相聊天。

它不保证更聪明，也不保证更便宜。拆分、重复上下文、结果汇总都需要成本；只有子任务相对独立、规模足够、输出可合并时，并行才可能有收益。小改动默认单 Agent，是合理而非落后的选择。

## 现状：已有同步只读委派，不应从零宣称新增

`tool_delegate` 已创建只读子 Agent，限制深度和步数，带入工作流任务包，返回结论文本。它调用同一模型客户端并顺序执行，父历史只传入一个很短片段。当前形态已经是初级委派，但还不是可管理的并行子任务系统。[S03]

外部参考中，pi 把子 Agent 作为扩展示例，用独立进程和上下文实现单项、并行或链式任务；Claude Code 官方文档也强调子 Agent 的独立上下文与工具权限。这里借鉴隔离与有界合同，不照搬它们全部角色、通信模式和产品默认值。[R07,R16]

## 建议第一轮架构

采用一个父 Agent，最多两个同时运行的只读子 Agent，最大子级深度一层。父 Agent 是唯一能够申请工作区写入和最终完成的主体。子 Agent 仅有列目录、读文件、搜索、读取已存在工件等工具，不允许 shell、测试执行、修改共享记忆、生成 active Skill 或再委派。

测试看起来只是验证，但可能写缓存、生成文件、启动服务或联网，因此不把测试工具混入“只读调查”。需要验证时由父 Agent 调用受管理的测试 Job。审查者可以读测试结果，不直接创造未经批准的新执行路径。

```text
Parent Run
  |-- Investigation A: 查询入口与调用链 -> evidence-backed result
  |-- Investigation B: 测试缺口与边界 -> evidence-backed result
  |
  +-- Parent: 冲突核对 -> 方案 -> 审批 -> 修改 -> 验证 -> 交付
```

这些限制属于 SkillForge 的建议设计，不是声称所有开源 Agent 都这么做。它避免引入复杂的共享黑板、无限会话、投票仲裁和动态角色市场，已经能覆盖最常见的代码调查场景。

## 子任务合同：让“去看看”变成可验收的问题

父 Agent 提交 `SubtaskSpec`，包含独立问题、完成标准、文件范围、允许工具、工作区版本、所需证据、最多模型步数、Token/费用额度和截止时间。调度器在接收前做结构与预算校验。

```text
SubtaskSpec
  task_id, parent_run_id, parent_task_revision
  objective, done_when
  allowed_paths[], allowed_tools[]
  workspace_snapshot_id
  context_refs[]
  budget{model_calls, input_tokens, output_tokens, cost_limit}
  deadline, result_schema_version
```

例如，“找出分页查询的排序字段及游标比较条件，返回函数路径、行范围、文件哈希与不确定项”比“作为资深后端专家分析项目”更容易验证。不要把父 Agent 的整个 history 复制给每个子 Agent；使用目标、边界和少量相关证据组成任务包。

返回值不只是一段结论，而是 `SubtaskResult`：已回答的问题、事实与证据引用、涉及文件哈希、建议、不确定项、失败原因、使用预算。模型自报置信度只能作为参考，不能替代父 Agent 对证据的复核。

## 并发隔离：最容易被忽略的一层

每个子 Agent 拥有独立 Run、消息记录和不可变模型响应。共享 HTTP 连接池可以作为实现优化，但不能共享 `last_completion_metadata`、当前 task packet、可变 history 或执行权限对象。存储服务可以共享，记录必须按 parent/child ID 分区，写入通过短事务控制。

读取视图有两种路线。路线 A 是给每个子任务一个真正的只读快照或独立 worktree；隔离清晰但多了文件管理成本。路线 B 是父 Agent 在一轮并行调查期间暂停自己的写入，所有子任务读当前同一版本，返回后重新核对相关文件哈希。**第一轮选择 B**，清楚承认它无法阻止用户从外部编辑器修改文件；检测到变化就将对应结论标记 stale，并重新调查受影响部分。

`asyncio` 的并发不是存储与对象自动安全的保证。对于现有同步客户端，临时放入线程池前必须确认实例不是共享可变状态；更稳妥的是先完成第 01 章的不可变响应合同，再打开子任务并行开关。

## 父任务预算怎么约束子任务

总预算应满足：父 Agent 已使用额度 + 已预留子任务额度 + 后续验证保留额度，不超过用户给本次 Run 的上限。子任务不能各自继承一份完整父预算，否则“最多两个子 Agent”仍可能把费用放大数倍。

调度器先原子预留，再启动。子任务退出后归还未使用额度，真实消耗累加到父任务账单。供应商实际用量晚于请求返回，因此每次调用先按最大输出和保守输入预留；无法精确硬封顶时，应明确还有在途费用上界，而不宣称一分钱都不会超。

并发可缩短的是关键路径，而不是总计算量。理想化地，独立调查的串行时间是各子任务时间之和，并行时间是最大子任务时间加调度与汇总开销；受到限流、缓存预热和共享 I/O 影响时，实际可能没有加速。用第 13 章的同模型、同总预算对照确认是否值得保留。

## 结果合并、冲突与取消

父 Agent 先检查子任务结果 schema、任务版本、文件哈希和证据可达性，再接收结论。两份结果不一致时，定位冲突事实，定向读取原文件或运行受控验证，不采用“两个 Agent 比一个 Agent 更可信”的投票规则。来自同一基础模型的判断也不能视为独立统计证据。

某个子任务超时，保留其已完成证据，结果标记 partial，父 Agent 可以缩小范围自行补查；不无限重启。父任务取消时，所有子任务收到取消，并在持久状态中完成收尾。子任务完成通知不能在父 Agent 正执行一组工具中途插入非法角色消息，应在运行时安全边界合并。

## 为什么并行写入放到下一阶段

允许多个 Agent 改不同文件，仍可能发生语义冲突：一个改接口，另一个按旧接口补测试；两个不同文件依赖同一个配置；锁文件或生成物相互覆盖。路径不重叠不代表结果能安全合并。

后续确有需要时，可让每个写入子任务在独立 Git worktree 中产生补丁，父 Agent 在基线一致的条件下逐个审查合并，再做集成验证。worktree 管理、分支基线、冲突、dirty 状态保护和清理都要额外实现。[R21]

**第一轮不做自动并行写入，也不做多 Agent 自治协商。** 在简历中，“有界并行只读委派、独立上下文、父级预算与证据合并”已经比“多个角色模拟讨论”更能体现工程能力，而且可以用真实故障场景验证。

## 验收

同一工作区变化时子结论失效；子 Agent 请求 shell 被拒绝；并行响应元数据不串线；两个子任务总预算受父任务限制；某子任务失败不吞掉另一份结果；父任务取消能收敛子任务；合并冲突触发证据核对；单文件小任务不被强制拆分。只有这些成立，才打开默认可用入口。

# 09 工作流、验证与证据：不是模型说完成就算完成

## 模块功能：让交付结果能够被检查

用户要求修改代码，真正关心的是改对了什么、有没有破坏原有行为、哪些地方还没验证。工作流与证据模块负责把“探索—修改—验证—交付”组织成有边界的过程，并把最终结论绑定到具体差异与执行结果。

它输入当前任务合同、工作区状态、工具记录和候选答复，输出允许完成、要求补验证、返回修改或等待人工决定。这里的重点不是强迫模型执行一长串固定流程，而是防止缺少必要证据时直接宣布成功。

## 现状：这是原项目值得保留的骨架

`workflow.py` 已有 WorkflowIR、静态校验、WorkflowKernel、TaskPacketCompiler、CompletionGate 和 FreshnessGuard；运行时也已有阶段权限与预算。`evidence.py` 支持执行日志、简报和 pytest 失败详情。这些与 SkillForge 的项目定位高度一致，不建议为追求新名词改成复杂的动态 DAG 或多 Agent 辩论流程。[S08,S11]

本轮应补强的是跨模块统一：工具返回的退出码不再靠普通文本猜测，验证绑定的文件版本可以被检查，失败状态可恢复，Skill 学习消费的是正式证据，而不是最终回答里的自述。

## 建议设计：任务合同先于执行计划

每次 Run 建立 `TaskContract`，记录目标、可修改范围、禁止事项、验收要求和任务版本。它由用户请求与必要澄清形成，不能被模型在后续摘要中悄悄改写。

例如“修复分页边界，并保留现有响应结构”意味着：允许修改指定服务和测试；禁止为了简单而删除筛选条件；需要覆盖已知漏数场景；不允许修改数据库 schema，除非用户明确批准。模型可以调整排查计划，但改变这些业务约束需要新的任务版本。

工作流仍采用几个可解释阶段：探索、方案收敛、修改、验证、审查、交付。只读审阅任务可以跳过修改；很小的任务可以缩短方案过程。**阶段是权限与验收门，不是每次都强制增加一次模型调用。**

## VerificationRecord 应包含哪些信息

可靠验证记录至少绑定命令的逻辑调用 ID、执行器身份、工作目录、开始/结束状态、真实退出码、日志工件、测试收集与结果摘要、相关代码版本和环境配置摘要。校验当前结果时先检查记录是否来自受控执行路径，再检查工件完整与文件新鲜。

```text
VerificationRecord
  verification_id, run_id, call_id
  command_spec_hash, executor_id
  source_revision, dependency_manifest_hash
  exit_code, collected_count?, passed_count?, failed_count?
  log_artifact_id, parser_version, parse_status
  started_at, finished_at
  result: PASS | FAIL | INCONCLUSIVE
```

这些字段由执行器和解析器写入，不能接受模型上传一段“exit_code=0”作为正式记录。哈希能够帮助检测内容变化，但不是信任来源本身；可信度来自受控写入路径、权限边界与可追溯身份。trusted-local 模式不能承诺抵抗恶意仓库代码对宿主文件的攻击，真正的隔离保证需要第 05 章的执行边界。

## 为什么测试退出零仍可能不算验证通过

没有收集到测试、运行了错误目录的测试、关键测试被跳过、只执行不相关样例，或者日志解析失败，都可能不满足任务要求。完成门应看 TaskContract 的声明，而不是只看一个 `exit_code`。

对已知失败先做 baseline 记录，区分原有失败、新增失败和修复目标。修复后至少重新执行目标回归与相关范围测试；广泛集成测试因环境限制没跑，则交付 `INCONCLUSIVE` 或“局部验证通过，整体未验证”，不能包装成全通过。测试过程中修改测试用例也必须纳入 diff 审查，尤其关注删除断言、扩大跳过范围和改变测试命令。

补丁验证绑定最终文件状态。测试完成后再次改代码，会使这条验证对相关文件失效；不能沿用刚才的绿色结果。昂贵的全仓库哈希可以逐步优化为声明依赖集，但依赖不完整时应保守扩大失效范围，不能为追求性能假装结果仍有效。

## 审查者如何帮助，而不是制造第二套权威

可用第 08 章的只读审查子任务检查差异是否偏离目标、是否删除约束、是否遗漏边界。它返回问题、影响文件和证据位置；父 Agent 核对后处理。审查者的“通过”不能替代实际测试，审查者没有发现问题也不意味着代码无缺陷。

用户最终获得一个交付包：修改文件及原因、关键差异、执行过的验证、未执行项目及原因、剩余风险、恢复或撤销提示。它由持久记录生成，模型只负责组织解释。UI 中的“完成”状态应对应这份交付记录，而不是模型的结束 Token。

## Skill 学习为什么必须接在证据之后

如果任务实际未验证、外部命令结果未知或存在未解决审查问题，学习流程可以保存“失败案例”或待研究记录，但不应晋升为已验证修复 Skill。失败案例也有价值，只是作用应是提醒与反例，而不是下一次直接执行的标准流程。

一次成功任务可提炼出多条假设，但只有证据支持的部分进入候选。条件化规则比绝对化规则更可靠：例如“在这类依赖条件下使用某个命令”，而不是“以后都使用这条命令”。

## 验收与边界

覆盖模型提前结束、目标测试未收集、旧测试结果在新补丁上被引用、修改后未复测、关键测试被删除、环境导致无法验证、审查与测试结论不同、用户追加禁止事项等场景。期待系统明确阻断或降级，而不是产生漂亮但不真实的完成报告。

**本章最小落地：保留现有阶段内核，把原生 ToolResult、VerificationRecord、TaskContract revision 和 CompletionGate 接起来。** 不引入形式化程序证明，也不声称靠测试即可证明所有业务行为正确。

# 10 持久化后端与事件流：让刷新、重连和重复点击不再破坏任务

## 模块功能：把本地脚本变成一个可以持续使用的工具

传统后端工程在 Agent 项目中最有价值的地方，不是堆一个高并发中间件栈，而是解决真实交互问题：用户提交后是否有任务身份，关掉终端是否丢状态，刷新页面会不会重复跑命令，审批与任务版本是否一致，重启后能否知道还有什么没完成。

本模块负责 Session、Run、工具调用、事件、审批和工件索引的可靠记录，并向 CLI 或网页提供接口。它是所有前面模块共同依赖的基础，不承担模型推理。

## 现状：已经落盘，但状态更新缺少统一事务边界

当前 SessionStore 直接写会话 JSON；RunStore 分别保存 task state、trace 和 report，其中部分 JSON 已经使用临时文件加替换，trace 是 JSONL 追加。不能说它完全没有原子写，但多个文件之间仍无法天然形成一个统一提交点：任务状态更新了，事件或报告可能还没写完。[S05,S10]

引入 SQLite 的目标是把“状态变化”和“描述这个变化的持久事件”放进同一个事务，并提供唯一键、查询与恢复；不是把所有日志全文塞进数据库。

## 建议架构：模块化单体 + SQLite + 本地工件

CLI 可以直接启动同一内核，也可以连接可选的 FastAPI 本地服务。服务负责 API、运行调度和事件订阅；模型与命令执行在异步任务中推进。SQLite 保存小型结构化状态，完整日志、diff 和摘要原文放内容寻址工件目录。

```text
CLI / Local Web
      |
Control API + Event Stream
      |
Run Controller -- Context / Tools / Skills / Subtasks
      |
SQLite: state + durable events + commands + artifact metadata
      |
Artifact store: logs, diffs, summaries, evidence bodies
```

SQLite WAL 适合本地读多写少的状态负载，但依然串行化写事务；数据库应位于本机文件系统，而不是共享网络盘。连接开启外键，设置合理 busy timeout，按部署需求选择持久化配置和备份策略。写事务保持短，不把 LLM 请求、shell 等待或工件大文件写入放在事务内。[R18]

服务启动的迁移使用明确 schema version，迁移前备份；不能让两个不同版本的程序同时写同一状态目录。需要多机器或多写入 worker 时再评估 PostgreSQL，此时也要重新设计工作区执行所有权；仅换数据库不足以自动获得分布式安全。

## 核心实体：每个 ID 都有明确含义

Session 是会话，Run 是一次被接受的用户任务，Turn 是一次模型轮次，ToolCall 是逻辑动作，Attempt 是某次执行尝试，Job 是受管理的进程，Artifact 是内容工件。Subtask 关联父 Run 与子 Run；SkillVersion 是不可变的技能内容版本。

| 实体 | 关键字段与约束 | 解决的问题 |
|---|---|---|
| sessions | id、workspace_id、config_revision | 会话与工作区绑定 |
| runs | id、session_id、status、version、task_revision | 运行进度和乐观并发控制 |
| events | event_id、run_id、type、payload | 持久时间线与订阅补拉 |
| commands | client_key、request_hash、result_ref | 重复提交去重 |
| tool_calls | call_id 唯一、args_hash、state | 动作身份与重试协调 |
| approvals | call_id、spec_hash、policy_revision、state | 审批不能移花接木 |
| artifacts | id、hash、size、state、path | 大文件索引与完整性 |
| skill_versions | skill_id、version 唯一、content_hash | 技能使用可复现 |

这些逻辑实体不必全部拆成独立 Repository 类，更不必一张表一个微服务。可以先围绕 runs/events/tool_calls/commands/artifacts 做最小版本，再迁移审批与 Skills。

## 幂等提交与版本 CAS 怎样结合

创建 Run 接口要求客户端提供幂等键，服务计算请求规范化哈希。在一个短事务里检查唯一键：同键同请求返回已有 Run；同键不同请求返回冲突；新键创建 Run、保存命令结果并追加 `RunCreated` 事件。

版本 CAS 是“只有当前版本等于我刚才看到的版本，才提交更新”。例如审批页面打开时看到 Run version=12，用户点击批准时运行已经因为新增需求到 version=14，不能直接套用旧审批。使用 `UPDATE ... WHERE version = expected_version`，检查影响行数，并在同一事务追加事件。

幂等解决“同一请求被传了两遍”，CAS 解决“两个不同请求基于旧状态竞争”，二者不能互相替代。第一次 HTTP 请求超时不代表提交失败，客户端应使用原幂等键查询或重试，而不是生成新键再创建一个任务。

## 事件与状态如何在同一个事务提交

建议每次关键状态迁移都更新 `runs` 或 `tool_calls`，并插入 `events`。只有事务成功后，内存订阅器才能通知客户端；客户端没收到通知时，可从数据库补拉。这里借鉴事件驱动思想，但不要求完整的事件溯源框架：数据库中的当前状态是运行查询入口，事件用于审计、恢复辅助和界面重建。

第一轮不引入 Kafka Outbox。待处理控制命令和本地 Job 意图保存在同一个数据库，由本地调度器领取。只有未来真的需要投递到外部消息系统，才需要额外的可靠发布协议。

对于模型 token 增量，不必每个 token 都开启一次事务。可以按片段合并，最终完整响应可靠落盘；UI 临时展示的增量与持久事件区分。关键动作、审批、文件变化、Job 终态和最终答复不能只存在内存中。

## 大文件与数据库不是一个事务资源

日志和 diff 在文件系统，状态在 SQLite，不能一句“加事务”就声称二者原子。工件采用显式状态：先登记或准备写入，向临时文件写完整内容并计算哈希，再原子重命名，最后提交 READY 元数据。正常读接口只返回 READY 工件。

如果在文件落地后、数据库更新前崩溃，恢复扫描根据命名和哈希识别孤儿；如果数据库有 PREPARING 而临时文件缺失，标记失败。清理只处理足够老、没有活动运行引用的工件；不能一边执行一边回收刚生成的日志。真正执行的文件顺序和刷盘需求要写入实现约定，而不是只画箭头。

## SSE 断线续传如何设计

SSE 是服务器向客户端持续推送事件的 HTTP 形式，标准定义了事件 ID 与 `Last-Event-ID` 重连语义。它适合本地任务进度、日志摘要和状态更新；控制指令仍走普通 POST 接口，无需为双向通信先引入 WebSocket。[R20]

接口可设计为 `GET /runs/{run_id}/events?after=event_id`。每个事件带稳定 ID、类型和 payload。重连时从持久 events 表读取大于 cursor 的事件，再继续轮询/通知式读取；客户端按 ID 去重。简单而正确的首版是一直按游标增量读数据库，通知只用来唤醒，不作为唯一事实来源。这样避免“先补历史、后订阅”之间丢掉一条事件的竞态。

高水位用于一次初始快照与事件衔接：返回当前状态快照及其 `through_event_id`，从该位置之后接增量。游标必须属于正确的 Run，过旧且已被清理时返回明确的 snapshot-required，不假装没有新事件。

如果使用浏览器原生 EventSource，应按其认证能力设计同源会话；若采用 Bearer Token，则使用支持请求头的 fetch 流式客户端，并自行处理 SSE 分帧、UTF-8 分段与重连游标。不要把认证 token 放 URL 查询参数或日志中。`Last-Event-ID` 不负责权限验证，每次订阅仍需检查运行访问权。[R20]

## 本地服务同样需要访问控制

默认只绑定 loopback，校验 Host/Origin，使用启动生成的会话令牌或等价本地认证；跨站网页不能随意提交 shell 执行请求。凭据不进入仓库目录、模型上下文或下载链接。允许局域网访问属于单独功能，必须加 TLS、身份认证和明确配置，不能把 `0.0.0.0` 当方便默认值。

运行控制数据建议放在用户状态目录而非模型可自由编辑的仓库中；isolated 执行器不挂载该目录。状态目录与工件目录需要明确配额、备份、保留和删除入口。SQLite 文件、WAL 和活动进程如何备份应按官方机制处理，不在写入中随意只复制一个数据库主文件。[R18]

## 参考与取舍

OpenCode 官方提供服务端接口和事件能力；Codex App Server 将 thread/turn/item 及控制消息从界面中分离。值得借鉴的是“运行内核独立于交互端”，不是必须照搬相同协议和所有对象。SkillForge 选择 REST + SSE，是因为它能覆盖首版交互而维护成本更低。[R09,R13]

另一条可行路线是继续用 JSONL 文件加严格原子写、日志扫描和唯一执行器。如果只做个人 CLI，它并非一定错误；但当增加重连、审批、并发子任务和查询界面时，SQLite 能减少自行实现事务与索引的代码。本方案因此选择 SQLite，不把文件存储描述成天然低级。

## 验收

重复提交只产生一个 Run；同幂等键不同请求被拒绝；状态和事件不会只成功一半；断线期间产生的事件能补拉；慢客户端不会拖垮执行器；服务重启可恢复待办命令；旧审批不能批准新参数；活动工件不被清理；数据库忙时有界退避并返回可解释错误。

**本章第一轮边界：本机单服务、短事务、可靠命令与事件、SQLite + 工件目录。** 不承诺跨节点故障转移，也不为简历堆银行项目里才需要的 Kafka/Redis 组合。

# 11 会话控制与审阅界面：允许用户在过程中改变主意

## 模块功能：Agent 不是只能“启动或等结束”

真实用户会在任务执行中补充要求、发现方向不对、暂时离开，或者只想查看差异后再批准。会话控制模块提供追加指令、暂停、取消、恢复、差异审阅和事件重看，让 Agent 从一次性脚本变成可交互工具。

它输入用户控制命令，输出命令受理结果与后续状态事件。受理不等于已经生效；是否进入安全执行边界由运行时决定。界面不能在用户点“暂停”后立刻显示“已安全停止”，而后台命令仍在改文件。

## 建议的四种控制语义

**追加要求**修改任务合同版本，在下一次安全边界进入模型上下文；**暂停**停止继续调度新动作，允许正在执行且不能安全打断的操作完成收尾；**取消**请求终止当前模型请求、子任务和进程，但不声称撤销已发生副作用；**恢复**在重新检查状态与工作区后继续。

```text
POST /runs/{id}/commands
  type: steer | pause | cancel | resume
  client_request_key
  expected_run_version
  expected_turn_id?
  payload
```

Codex App Server 的公开控制接口中有面向活动 turn 的 steer 与 interrupt 语义，可以参考它区分“给当前运行追加输入”和“新开一轮任务”的思想；SkillForge 的字段与状态机仍按自身实现定义，不照搬其协议即可使用。[R13]

## 追加指令为什么需要版本和安全边界

例如用户在 Agent 正准备改代码时说“不要修改数据库 schema”。这应产生新的 TaskContract revision，撤销与旧要求冲突的待执行审批或工具计划，并在下一次调用前告知模型。若数据库操作已经实际执行，系统必须先说明已发生的事实，再处理恢复，不能假装新要求能追溯阻止过去。

模型正在流式输出工具参数时收到新要求，可以先记录控制命令；参数收齐但尚未执行时，网关再次检查任务版本。命令正在执行则走暂停或取消机制，不在一半参数中插入新文本，也不悄悄把用户要求改写到旧历史头部。

同一 Run 的追加要求按持久顺序处理，客户端重发同一键不会重复追加。任务已经终态时，steer 应明确失败或由用户选择创建新 Run，不能悄悄复活已经完成的动作链。

## 差异审阅与交付界面

建议先做一个简洁的 Run 页面或 CLI 面板：左侧任务阶段和时间线，主体是模型答复、工具摘要及 diff，底部展示等待审批、剩余预算、验证状态与风险。第一轮不做完整 IDE，不集成聊天社交功能，不重复造代码编辑器。

diff 审阅绑定 PatchPlan ID、目标文件哈希和 task revision。用户批准的是具体差异，不是一个未来可以任意变化的“修改代码”权限。验证结果旁边展示验证时的差异版本，后续有修改就显示过期，避免绿色标记误导用户。

失败时不要只显示“Agent error”。应区分模型协议错误、工具拒绝、命令失败、上下文不足、预算耗尽、工作区漂移和副作用未知，并提供对应的已存在状态和工件入口。错误类型越明确，用户越不容易通过反复点击重跑制造新问题。

## 会话分支与回放：亮点可以很轻量

允许从一个已完成边界复制上下文视图与任务记录，创建新分支来比较方案。分支首先是“对话/决策历史的分支”，并不自动回滚磁盘工作区。没有独立 worktree 时，新分支必须重新检查当前代码，不能假装回到了历史版本。

事件回放用于重建 UI、复盘模型如何选择工具与证据；默认不再次执行工具。如果用户确实要复现运行，需要新的 Run、明确基线与授权，并接受模型非确定性和外部环境差异。**审计回放、确定性模拟回放、真实重新执行**应是三个不同入口，而不是同一个“Replay”按钮。

第一轮可先支持“从当前完成点另起任务”和“只读时间线回放”，把任意历史点的工作区还原留到后续。这样仍然有明显产品价值，却不会马上引入复杂的 Git 状态管理。

## 与后台运行的关系

关闭浏览器、网络暂断、CLI 订阅进程退出，只影响客户端连接，不默认取消 Run。本地服务还活着时任务继续，重连按事件游标恢复；服务本身退出或电脑关机则进入第 12 章的恢复流程。不能把“断线继续”宣传为“机器关机也能继续运行”。

自动后台学习在主 Run 完成后产生独立状态，用户可以关闭、暂停和查看待审核 Skill；学习失败不能把已经完成的代码任务改成失败，也不能偷偷继续消耗没有预留的模型费用。

## 验收与第一轮边界

测试模型流式期间追加要求、待审批期间修改约束、长进程取消、重复点击、旧页面版本提交、断线后重连、Run 已终态后收到命令、分支时工作区已变化。界面状态必须与后端记录一致，不凭前端按钮点击就假定执行成功。

**本章最小实现：追加/暂停/取消/恢复、带版本的 diff 审批、时间线与断线重连。** 分支与回放先做只读或当前边界版本，不承诺完整 IDE 或任意状态“时间旅行”。

# 12 Checkpoint、恢复与副作用协调：恢复任务，不重演错误

## 模块功能：中断后知道该接着做什么，也知道不能贸然做什么

恢复模块解决的是“任务已执行到一半，程序或机器中断后怎么办”。它不只是把旧聊天再发给模型，而是检查真实工作区、工具状态、授权和证据，再决定哪些状态可以续用，哪些必须重新验证，哪些需要人工处理。

输入是持久 Run、checkpoint、事件与当前外部现场；输出是可继续的状态、局部失效清单，或阻断原因。它与上下文压缩使用的 checkpoint 有关联，但职责不同：压缩 checkpoint 缩短模型视图，恢复 checkpoint 记录可靠执行边界，两者不应只靠一个没有类型的 JSON 互相冒充。

## 现状：已有恢复核查，不是简单从零新增

原运行时已区分运行身份、工作区变化与文件新鲜度，简历也报告了一组小规模恢复场景结果。应保留已有判断逻辑，再让它消费统一的调用账本、Job 状态、任务合同版本与工件身份。既有“90% 成功率”不能外推为任意崩溃场景都能自动恢复；本次没有重跑该套完整测试。[S01,S05]

## 建议恢复合同

```text
RunCheckpoint
  schema_version, run_id, session_id
  task_revision, run_version, committed_event_id
  phase, completed_action_ids, pending_call_ids
  context_epoch, compaction_id?
  workspace_id, baseline_revision, dependency_hashes
  skill_versions, policy_revision, budget_ledger
  active_job_refs, approval_refs
```

只保存可以验证和重新定位的状态，不保存“模型想必已经知道”的隐含假设。checkpoint 指向的工件必须存在且完整；引用的 Skill 版本必须可读；恢复前重新检查当前权限。旧会话里被允许的网络或写入动作，不应自动越过今天已经收紧的策略。

## 恢复顺序

先确认状态结构是否兼容，再确认工作区身份和唯一执行器所有权；随后核对活动 Job 与未完成工具调用，处理未知副作用；再验证相关文件、依赖和证据；最后恢复模型视图，并给用户一份“可复用/已失效/需确认”的摘要。

为什么必须先处理未知动作，再请求模型继续？因为模型看到旧状态可能立即重复执行。比如上一次补丁已经写到磁盘，但完成记录没来得及提交，直接恢复旧消息会让模型再改一次；或者测试仍在后台运行，新进程又启动一份，导致资源冲突。

## 工具在不同崩溃点的处理

| 中断位置 | 已知事实 | 恢复动作 |
|---|---|---|
| 记录调用意图前 | 没有正式接受动作 | 可以重新规划，但不能推断执行过 |
| 意图已记录、执行未开始 | 有逻辑调用，无执行确认 | 在确认执行器未启动后继续同一调用 |
| 文件已替换、结果未提交 | 外部效果可能已发生 | 比较前后哈希，识别已完成或部分完成 |
| 进程已启动、连接丢失 | PID/容器身份可能可核对 | 查 Job 身份与日志，不立刻重启 |
| 结果与事件已提交、UI 未收到 | 后端事实完整 | 重发已存结果，不再执行 |
| 外部发布超时 | 无法确认是否成功 | UNKNOWN，人工或远端核对，不盲目重发 |

对文件补丁，比较当前内容与预期前后哈希：等于后态时可认定相应文件步骤已落地；等于前态时可按计划继续；两者都不等则进入需人工检查。多文件任务可能部分完成，应逐项协调，不能把一个文件符合后态当成整个计划已完成。

对纯读取，重做通常可接受，但要重新标注事实版本。对模型请求，网络重试可能产生额外计费或不同答案，即使没有仓库副作用也应计入运行成本；不要宣称调用 ID 就能让所有模型供应商无重复计费。

## 状态漂移如何分类

工作区路径变了、Git 根不同、任务结构版本不兼容，属于强阻断；相关文件变化则只让依赖它的记忆、子任务结论与验证失效；无关文件变化不必把整次任务都作废。第一版可以偏保守，逐步通过依赖集缩小失效范围。

持久记忆可以作为导航保留，验证与写入依据必须重新核对。Skill 版本变更不影响旧 Run 对旧版本的可追溯性，但安全撤回可能要求阻断。恢复模型视图时，工具调用与结果必须成组完整；未解决的 UNKNOWN 作为显式待办，不能被压缩摘要省略。

## 租约与 fencing 的边界

数据库租约和执行代数可以阻止旧 worker 再写入新的数据库状态，却不能自动阻止它早已启动的 shell 继续写磁盘。一个“租约过期就抢占”的实现，如果没有进程终止确认，可能同时出现两个工作区写入者。

所以第一轮选择更简单的边界：本地单执行器持有操作系统级运行锁，进程由受控执行器管理；重启接管前确认旧写入进程已经结束或隔离。检测不清就暂停，需要用户核对。将来扩成远程 worker 再设计完整执行 fencing，而不是先给数据库字段取一个高级名字就认为问题解决。

## 保存频率与恢复粒度

每个已接受工具意图和正式结果都持久化；阶段切换、审批、上下文 epoch 切换与 Run 终态保存 checkpoint。无需在每个 token 后写完整会话文件，也不等到任务结束才一次性保存。

模型视图可以由 checkpoint 加后续事件重建，但应明确事件 schema 版本和迁移规则。仅重建 UI 的事件与能驱动执行状态的正式事件分开，避免把临时显示片段当成可恢复事实。

## 验收与范围

在调用意图、进程启动、文件替换、结果提交、事件发送和 checkpoint 切换之间逐点注入故障。检查最终文件、调用记录和恢复决策，验证不会盲目重放已发生副作用。服务关闭、客户端断开、机器关机和外部程序修改是不同类型，不用同一条“断线恢复成功”概括。

**本章目标不是任何故障都自动继续，而是能准确区分“可以继续、需要重验、结果未知、必须阻断”。** 一个诚实的 UNKNOWN 比一个错误的自动恢复更可靠，也更能体现后端工程深度。

# 13 可观测性与评测：证明深化有效，而不是只证明代码变多

## 模块功能：回答这次任务为什么慢、为什么贵、为什么失败

可观测性面向一次运行，帮助用户与开发者定位问题；评测面向一组受控任务，判断某个升级是否值得保留。二者都不应停留在打印完整 prompt 或统计工具次数。

用户可以问：刚才为什么压缩？缓存到底命中了多少？哪个子任务消耗最多？验证为何失效？某个 Skill 为什么被选中？系统应从正式记录中回答，而不是再让模型猜一次。

## 建议新增的亮点：Context Inspector

提供 `context explain` 或 `/context` 面板，展示本轮 P0/P1/摘要/近期消息/工具 schema 的估计 Token，真实输入与缓存读写用量，稳定边界版本，最近失效原因，被省略的大输出以及回查句柄。它属于上下文诊断模块，而不是另一个 Agent。

```text
Context view: epoch 4
Stable snapshot: unchanged
Compaction reason: input reserve threshold
Provider usage: cache read reported / cache write reported
Estimated vs actual input: deviation recorded
Omitted material: artifact references available
Current constraints: all required IDs present
```

这里故意不填虚构百分比。真实 UI 数据来自 PromptManifest 与 ModelResponse。供应商未报告缓存字段时显示 unknown，不把零、未支持和未采集混成一种情况。查看完整 prompt 需要用户显式选择并提醒源码/敏感信息风险，默认只展示分区摘要与哈希。

## 指标分层

| 层面 | 建议指标 | 防止误解 |
|---|---|---|
| 正确性 | 任务通过率、回归失败、误完成率 | 测试退出零不等于业务正确 |
| 上下文 | 实际输入 Tokens、压缩次数、约束遗漏 | 字符压缩不等于 Token 或费用下降 |
| 缓存 | 读取 Tokens 占比、写入费用、冷/热场景 | 本地前缀稳定不等于远端命中 |
| 工具 | 合法执行率、未知副作用、无进展循环 | 少调用不一定好，可能漏验证 |
| 恢复 | 正确恢复/正确阻断/误信过期状态 | 自动恢复比例不是唯一目标 |
| Skills | 误用率、拒用率、受控对照增益 | 选中过不代表真的有用 |
| 多 Agent | 总费用、完成时间、证据有效率 | 速度和总计算成本要一起看 |
| 体验 | 首次可见进度、断线补拉、取消收敛 | 不拿前端动画当执行进度 |

日志统一带 session/run/turn/call/job/subtask/epoch 的关联 ID，记录事件类型与耗时。模型费用包括摘要、子任务和重试，不能只把主 Agent 的一次调用统计成“总成本”。调试和评测记录默认本地保存，不未经用户同意把源码和 trace 发到第三方分析平台。

## 原有简历数字应怎样处理

原简历报告 12 组压力配置中的平均字符压缩率 19.71%，最大 34.06%，以及当前请求保留率等；这些是既有小样本口径，不应改写为“Token 成本降低 19.71%”或“缓存命中提高”。另一组均值 7,968.33 与 6,173.67 的比值得到约 22.52%，与逐样本压缩率再平均可能不同，不能未经原始记录复核就认定矛盾。[S01]

若每个样本原长度为 a_i、压缩后为 b_i，平均压缩率是 `mean(1-b_i/a_i)`，总体长度减少比例是 `1-sum(b_i)/sum(a_i)`，权重不同。升级评测同时输出两者、原始每例数据和样本说明。验证脚本只复核了聚合均值比例，没有重建原 12 组实验。[V01]

## 新评测怎样设计才有说服力

建议先建立三个层次。第一层是确定性单元/契约测试，覆盖身份、权限、预算、消息组、版本和状态迁移；第二层是故障注入，覆盖崩溃、超时、部分写入、断线与并发；第三层才是真实模型的端到端代码任务。

首批任务可规划为约 30 个可重复的小仓库任务，覆盖单文件修复、跨文件修改、测试失败定位、长日志、长会话、工具错误和约束变更。这个数量只是启动规模，若按统计功效要求证明小幅效果，往往需要更多任务。每题保留起始 commit、依赖环境、明确验收和隐藏回归检查；模型不能提前读取评分答案。

拆分任务集时按仓库或问题族隔离，尤其把 Skill 提炼任务与效果测试任务分开。不能让训练/提炼过的同一道题只改文件名就进入测试集。验证脚本和目标约束不应允许被 Agent 自由修改，或者至少由外部评分器核验它们未被篡改。

## 消融对照：一次只验证一个关键变化

建议对照组按以下顺序建立：原版快照；原生协议但不改变压缩；输出工件化与稳定前缀；语义压缩开启/关闭；Skills 开启/关闭；有界多 Agent 与单 Agent。实现依赖意味着不必强行做所有排列组合，但要说明比较时哪些组件一起改变了。

同一题使用相同模型版本、预算与环境，随机化方案执行顺序，并对关键配置重复若干次，观察模型随机性。供应商缓存无法精确清空时，应记录预热过程和 key 策略，冷/热场景分层报告；不把先运行的冷缓存方案和后来预热的方案直接比较。

成本以整个任务为单位，包括失败和重试；时间同时报告中位数、分布和样本数。小样本的尾部分位数不稳定，不能凭十次运行就宣传可靠的 p99。任务通过率可报告置信区间；同题不同方案适合配对比较，但同一题的多次重复不应被当成完全独立的新题目。

## 主动构造会推翻方案的负例

短任务可能因为摘要预热变贵；两个子 Agent 可能因为重复上下文与汇总更慢；严格审批可能打断过多；FTS5 可能错过语义相关线索；Skill 可能误用到不同分页机制；本地 SQLite 在大日志逐 token 写入时可能产生争用。这些不是要隐藏的坏数据，而是决定默认开关和适用范围的依据。

如果小任务多 Agent 持续更差，就保持自动委派关闭或加任务规模门槛；如果摘要没有改善长任务成功率，就只在硬窗口压力下使用；如果某 Skill 在负例中常误用，就缩窄前提或撤回。允许删除或关闭功能，才是真正的深化而不是技术堆叠。

## 何时能写进简历

先有源码落地和测试证据，再用真实口径描述：“建立缓存感知上下文视图与分层工件协议，结合原生工具调用、断线续传和有界只读委派改善长任务执行；在某数量、某类型任务上得到某结果”。数字必须带范围、基线与单位，不用“企业级”“极致提升”等无法验证的词。

当前交付是设计、源码核查和局部示例验证，不是上述效果已经获得的证明。第 14 章定义每阶段何时可以从“计划中”改为“已实现”。

# 14 落地顺序与范围控制：先补内核，再加亮点

## 模块之间的依赖为什么重要

这些章节不是要求一次性并行开发全部模块。原生响应合同影响并发安全，工件协议影响压缩和证据，持久调用账本影响恢复，任务版本影响审批和追加指令。如果先做漂亮的多 Agent 页面，再回头补底层身份和状态，返工会很大。

建议把源码整理为职责清楚的少量模块，保留已经存在的 WorkflowKernel、证据解析和 Skill 晋升规则。不是改目录名就算重构，而是每个边界有独立输入输出与测试。

```text
skillforge/
  runtime/       # run controller, workflow integration
  providers/     # model protocol and usage capabilities
  context/       # manifest, model view, compaction
  tools/         # typed registry, policy, patching
  execution/     # process jobs and optional isolation
  storage/       # SQLite state, events, artifact index
  memory/        # repository facts and freshness
  skills/        # candidate learning, versioning, retrieval
  subagents/     # bounded task scheduling and result merge
  api/           # optional local control and SSE
```

目录图只是建议职责，不要求一开始拆成十个 Python package。第一轮甚至可以先保留几个文件，通过接口和依赖注入逐步迁移；避免花大量时间移动代码却没有改善行为。

## 推荐交付分段

| 阶段 | 核心内容 | 可验收交付 | 不能提前宣称 |
|---|---|---|---|
| A 基线固定 | 核心源码快照、契约测试、原模型配置与评测输入 | 能重现原行为与已知弱点 | 升级已提高成功率 |
| B 执行与上下文 | 原生响应、工具组、P0/P1、工件化、Token 准入 | 调用可追踪，动态前缀不乱改，超窗可处理 | 零缓存损失、零幻觉 |
| C 可靠使用 | 调用账本、ProcessJob、SQLite、SSE、审批版本、恢复 | 断线可补拉，中断可协调，动作不盲重放 | 分布式 exactly-once |
| D 经验与协作 | 结构化 Skill 提炼、版本与按需加载、有界只读子任务 | 能解释技能适用性与子任务证据 | 自动持续学习必然变强 |
| E 评测与交互 | 消融、故障注入、Context Inspector、基本审阅页 | 有可复查数据与明确默认开关 | 未实际运行的性能数字 |

单人投入的粗略工程估计是约 40—60 个工作日完成 B—E 的受控首版，取决于现有测试质量、模型兼容后端和沙箱部署环境；这不是交付保证。只做可靠 CLI、一个模型后端、一个操作系统执行路径，会明显降低工作量；同时做完整 Web IDE、多供应商等价支持和并行写入则会扩大范围。

若时间只有三四周，优先交付 B 与 C 的缩减版：稳定前缀、统一工件、原生工具、持久 Job、补丁预条件和基础恢复；Skills 先保持原晋升流程，加正文按需加载；多 Agent 保持顺序只读，待响应对象和存储隔离到位再并行。这样的版本也比一个功能齐全但状态不可靠的演示更有价值。

## 哪些功能默认做，哪些延后

默认做的亮点是缓存感知上下文、可靠工具与 Job、证据驱动 Skill、版本化恢复，以及可解释上下文诊断。这些直接补现有薄弱点。最多两个只读子任务是可开启功能，而不是每个请求都执行的固定流程。

LSP 精确导航、独立 worktree 写入、任意历史分支恢复、第三方 Skill 安装、MCP 连接器和多机器执行都属于后续可选。每加入一项，都要回答用户价值、权限、状态与测试四个问题；答不清就不加入本轮。

明确不做：无限递归 Agent、自治投票组织、全局知识图谱、自动模型微调、企业级多租户控制台、自研容器隔离、跨云执行编排。也不把系统改成需要同时启动 Kafka、Redis、PostgreSQL 和向量库才能跑一次本地改码任务。

## 对外部框架的借鉴矩阵

| 外部来源 | 采用的原则 | 不照搬的部分 |
|---|---|---|
| Hermes | 程序性 Skill、渐进加载、会话内缓存稳定 | 自由写入所有技能、广泛消息平台和自动化生态 |
| pi | 保持内核小、压缩条目有边界、子 Agent 可隔离扩展 | 把扩展示例误写成默认内置能力；一次复制全部扩展 |
| OpenCode | 压缩 checkpoint 与持久历史分离、界面与服务分离 | V1/V2 默认参数混用、整套应用及插件平台 |
| Codex | 明确运行对象、流式事件、控制命令与审批边界 | 完整 App Server 协议及远程产品架构 |
| Claude Code 官方文档 | 子 Agent 独立上下文与权限、可选 worktree 思路 | 认为独立工作目录就等于安全沙箱 |

以上比较以本次可访问官方文档和开源路径为依据，不是完整功能竞赛或排行榜。pi 当前旧仓库入口重定向到新组织路径；OpenCode 的 V2 压缩说明与普通配置文档不是同一个版本页面。实施时固定依赖版本，再核对所采用行为，不从不同版本里各取一个默认值拼成虚构实现。[R01–R16]

## 对 Claude Code 泄漏镜像的核查结论

已查看一个公开的重建镜像 README 与架构索引。它自称来自意外暴露的源码，明确声明未经 Anthropic 授权，并列出被替换为空实现的内部功能，其中包括 Sandbox Runtime 与 Context Collapse。这里能够确认的是“该镜像如此自述”，并没有独立验证完整来源链或它与当前官方版本一致。[R23]

因此，这份方案没有复制镜像中的专有源码，也没有把那些空实现当成“Claude Code 真实压缩或沙箱算法”。可交叉核对的功能以 Claude Code 官方文档为准，可落地代码参考以正常公开的开源项目为主。这样仍回应了镜像参考需求，但不让不可验证的实现成为核心设计依据。[R16,R23]

## 如何从现有文件逐步迁移

`models.py` 先引入 ModelResponse 与 ProviderAdapter；`context_manager.py` 保留旧算法作为 benchmark baseline，新建 epoch 视图；`tools.py` 保留工具名称，逐个迁移严格合同与工件结果；`runtime.py` 逐步移出模型协议、Job 与存储，不同时改完所有行为；`skills.py` 保留 PromotionGate，用新提炼器替换模板生成；`memory.py` 沿用内容哈希；`workflow.py` 保留阶段与完成门；`run_store.py` 成为导出/兼容工件入口，运行事实迁到数据库。[S02–S11]

旧 Session JSON 只读导入，迁移生成新 session schema version，并保存原备份；不要让新旧程序同时写同一文件。每个功能开关都记录到 Run 配置，使评测和回滚可复现。

## 最终建议

把这一轮的叙事收束为三条：**缓存感知的长任务上下文；有副作用边界的可靠执行；有证据与版本的经验复用。** 多 Agent 与传统后端为这三条服务，不单独追求规模。做到这些，SkillForge 的深化就不是“功能比以前多了”，而是每个核心问题都有可解释的机制、边界与验证。

# 15 可选增强：LSP 语义导航与增量诊断

## 模块功能：减少“搜到了同名文本，却不是同一个符号”的误判

普通全文搜索适合快速发现线索，但同名函数、别名导入、继承与重载可能让纯文本结果难以判断。LSP 模块允许 Agent 获取符号定义、引用和诊断信息，帮助它更准确地定位代码与识别明显类型问题。它属于仓库工具能力，不是新的主 Agent，也不代替运行测试。

这是一项可选增强，建议在前面可靠执行与评测成立后再做。代码导航比新增聊天角色更贴近 Coding Agent 的业务，而且可以通过具体跳转结果验证价值。

## 技术基础与最小范围

Language Server Protocol 规定客户端与语言服务之间的消息、文档同步和语言功能。SkillForge 作为一个小型客户端，只请求定义、引用和诊断，不实现完整编辑器。参考协议的文档版本与生命周期约定，不能只发一个 JSON-RPC 查询就假设结果对应最新文件。[R27]

首版只选一种用户常用语言，例如 Python，接入已安装的语言服务；启动与退出由第 05 章的进程管理器接管。工具可为 `code_definition(path, line, column)`、`code_references(...)` 和 `code_diagnostics(paths)`，结果仍经过网关与工件预算管理。

不同语言服务的环境、索引时间和能力不一样，不能宣传一次接入支持所有语言。语言服务缺失或尚未索引完成时，明确返回 unavailable/indexing，并回退到现有搜索，而不是等待到整个 Run 超时。

## 新鲜度与位置编码

文件变化需要发送正确的文档同步事件或触发重索引，并把结果绑定到文档版本。LSP 位置编码与 Python 字符切片可能不同，特别是中文、emoji 和非 BMP 字符；适配器应按协商编码转换位置，而不是简单把字节偏移当列号。[R27]

修改后返回的旧诊断不能当作当前错误；导航位置也要核对内容哈希。模型准备按一个定义位置修改文件时，仍需读取原文和使用补丁前置条件。LSP 提供定位信息，不授予写入权限。

## 风险、退路与验收

语言服务可能执行插件、加载项目配置或占用较多内存，因此它不是完全没有副作用的字符串查询库。默认使用用户认可的服务与工作区，限制进程资源；不根据仓库文本自动安装陌生语言服务。

验收覆盖同名不同符号、重命名后的跳转、索引未就绪、中文位置、文件修改后的诊断过期、服务崩溃与回退。如果在目标任务集上没有比 ripgrep + 定向读文件带来明确收益，就保留为可选扩展，不让首版所有用户承担启动和依赖成本。

**本章边界：一种语言、三个只读语义能力、完整超时与回退。** 自动全仓库重构、跨语言调用图、代码知识图谱和自研编译器均不属于这一轮。

# 附录 B 验收矩阵：如何证明它不再只是演示

## 使用方式

下面是**待实施的验收规格，不是测试通过报告**。每个场景都应固定模型/适配器版本、工作区快照、配置和输入，保存 Run ID、事件、关键工件哈希与判断结果。优先通过确定性集成测试验证不变量，再用真实模型评测任务质量。仅靠模型说“我完成了”不能判定通过。

P0 表示可能造成错误副作用、状态误信或不可恢复故障，必须先处理；P1 表示核心体验与效果；P2 表示可选增强。编号是用例身份，不表示开发顺序。

## 上下文、协议与缓存

| 编号 / 优先级 | 构造场景 | 预期行为与需要的证据 |
|---|---|---|
| CT01 / P0 | 模型一轮发出两次工具调用，只收到一个结果时触发压缩 | 不切断未闭合调用组；两次 call_id 及对应结果仍能正确关联 |
| CT02 / P0 | 用户输入本身大于窗口可用额度 | 返回 INPUT_TOO_LARGE，不悄悄截掉限制，也不反复请求同一非法输入 |

| BE08 / P0 | 只跑了零个测试、跳过全部测试或只得到模型自述 | 完成门不能判为测试通过；显示覆盖缺口与实际命令结果 |
| BE09 / P0 | 测试通过之后代码又被改动 | 旧验证失效或明确降级，交付只能绑定当前可检查的代码版本 |
| BE10 / P1 | 用户点击取消后立即看到成功响应 | 响应区分“取消命令已接受”与“进程已停止”；不暗示已回滚代码 |
| BE11 / P0 | 跨站网页向 loopback Agent 服务发送命令 | Host/Origin 与认证检查阻止未授权控制；令牌不出现在 URL |
| BE12 / P1 | 不支持 schema 的旧 checkpoint 导入，或工件缺失 | 可解释地拒绝、迁移或部分恢复；不盲信旧状态继续写入 |

## 汇总与结果记录模板

共 44 个目标场景。建议先把 P0 场景做成能稳定重现的集成测试，不必为每一个场景付费调用模型。模型相关的 CT07、KS04 和最终任务质量评测另行建立在线测试集，避免单元测试被网络与模型随机性污染。

```text
case_id: EX07
implementation_version: <commit>
configuration_digest: <sha256>
fixture_id: <workspace snapshot>
fault_injection_point: after_spawn_before_result_commit
observed_state: <actual>
expected_invariant: no_blind_reexecution
artifact_refs: [<events>, <job log>, <workspace diff>]
result: NOT_RUN | PASS | FAIL | INCONCLUSIVE
notes: <limits and reproduction steps>
```

安全和正确性门采用“关键用例不通过则不启用对应功能”，不能用平均任务成功率抵消一次严重越权。性能与质量则用第 13 章的成对对照、冷/热缓存分层和消融来判断，不用“通过用例数量”冒充智能体能力提升。

## 一个完整的用户任务：修复分页漏数

以下是**假设案例**，不是从用户项目中取出的真实 bug，也不是已执行成果。用它把分散章节重新接成一条用户可以理解的流程。

用户提出：“客户列表按更新时间倒序分页，同一时间的记录有时漏掉。修复问题，保持接口响应格式，不修改鉴权逻辑，并补回归测试。”会话控制层建立 Run，记录任务版本 1，将两条不可变业务约束编成可检查的约束 ID。用户看到任务已创建、当前阶段为探索、可用预算和写入需要的审批方式。

运行时加载本次会话的稳定仓库导航与已批准 Skill 目录。它没有把 Git status 或剩余预算塞到最前面。工具网关提供只读搜索与文件读取。父 Agent 可以独自探索；如果确有两个独立问题，才并行派出两个只读子任务：一项调查排序和游标构造，一项查找已有分页测试与 API 合同。子任务不能跑任意 shell，也不能改文件。

两个调查返回的不是整段聊天，而是结论、文件范围、内容哈希、引用行号和不确定项。父 Agent 检查新鲜度后发现假设根因：只用更新时间作为排序和游标，没有唯一字段作为同时间记录的次序补充。这是待验证判断，不能直接当作已证实事实。

方案收敛后，父 Agent 准备补丁与测试计划。审批卡显示目标文件、预期差异摘要、当前文件哈希及任务版本。用户批准的是这一份动作，不是今后所有任意写入。若用户这时追加“还要兼容旧游标”，新要求生成任务版本 2；原方案和审批需要重新核对，不能把批准旧版本当成批准新范围。

补丁工具在写入前检查版本与唯一匹配条件，记录调用身份和 preimage，再通过临时文件替换写入。多文件修改使用日志明确记录进展，并不冒充跨文件原子事务。外部编辑器恰好修改同一文件时，系统报告冲突，优先保留用户的新内容，而不是无限重试覆盖。

验证阶段启动受管测试 Job。界面能实时显示运行中、日志摘要和耗时；完整日志落工件目录。模型只收到失败节点、有限片段和引用。它发现一个边界测试失败，按引用读取详细输出，修正后再验证。日志没有先完整塞进 prompt，再被下一轮抹掉。

任务较长，模型视图接近软阈值。压缩器先确认没有未闭合工具调用，固定来源事件区间，生成摘要：目标、接口约束、已改文件、失败路线、当前测试与剩余工作。校验不通过则不切换；通过后建立新 epoch，稳定规则保持，原始日志和历史仍可检索。是否节约了费用，最终看真实 usage，不靠摘要字数猜测。

此时用户关闭页面。Run 不因为订阅断开而消失；下次打开后从事件游标补拉。假设服务本身也重启：控制层首先核对旧测试进程和文件状态。无法确定是否仍在执行的动作进入 UNKNOWN，不再启动一份相同写入；确认后才能恢复。

最终，完成门检查当前代码版本、实际测试退出结果、测试收集数量、约束满足情况和未解决风险。交付页面展示修改差异、命令及验证结果；不能只展示模型生成的“已修复”。如果测试只覆盖局部，就明确局部覆盖，不包装成全系统正确性。

后置学习模块从本次通过验证的差异和证据中提取候选 Skill：“非唯一排序字段的游标分页需要稳定的唯一次序及一致游标条件”。候选包括适用前提、反例、验证要求和证据来源，而不是把当前文件路径原样粘成通用秘诀。它先在隔离候选区评测和审核；批准后形成不可变新版本。下次遇到别的 pytest 报错，不会仅因为同样使用 pytest 就加载这一技能。

这条链路的重点不是“多 Agent、数据库、Skills 全都启动了一遍”，而是每个模块有明确职责，可以关闭可选增强而不破坏主流程。

## 最小合同：先统一身份，再增加实现

下面是接口草案，不是已安装的 SkillForge API。字段用来说明模块边界，实际实现可以用 Pydantic/dataclass，并随 provider 协议调整。

```text
TaskContract
  run_id, task_revision
  objective, constraints[{id, text, kind}]
  acceptance_requirements[], authorized_scope
  model_budget, tool_budget, deadline

ModelResponse
  request_id, provider, model
  text_blocks[], tool_calls[{id, name, arguments}]
  usage_normalized, usage_raw
  finish_reason, adapter_version

ActionSpec
  call_id, run_id, task_revision
  tool_name, arguments, effect_class
  expected_file_hashes, spec_hash
  approval_id?, deadline

SubtaskPacket
  subtask_id, parent_run_id, parent_task_revision
  objective, evidence_scope, allowed_tools
  token_budget, deadline, expected_result_schema

VerificationRecord
  verification_id, run_id, task_revision
  job_id, command_spec_hash, exit_code
  collected_tests?, skipped_tests?, parser_status
  code_revision, artifact_refs[], observed_at
```

这些对象的安全边界不同。模型可以提出 ActionSpec 的候选参数，但不能自己决定审批有效；可以归纳 VerificationRecord 的解释，但不能伪造受控执行器写入的原始记录；可以写 Skill 候选正文，但不能把它直接设为 ACTIVE。

## 一段最小事务草案：状态与事件共同提交

以下 SQL 仅展示 runs/events 的一致性，不包含完整建表、迁移、权限或生产级错误处理；不能直接当成可运行产品代码。

```sql
BEGIN IMMEDIATE;

UPDATE runs
SET status = :new_status, version = version + 1
WHERE id = :run_id
  AND version = :expected_version
  AND status = :expected_status;

-- 应用层检查 changes() == 1；否则 ROLLBACK 并返回版本冲突。

INSERT INTO events(run_id, type, payload)
VALUES (:run_id, :event_type, :payload_json);

COMMIT;
-- 仅在提交成功后通知订阅端；通知丢失时仍可按游标补拉。
```

这段事务只覆盖数据库记录，**不覆盖 shell 的外部副作用或文件系统写入**。把它扩写成“整个 Agent exactly-once”就是错误推论。调用账本、文件预条件、工件状态协议和恢复协调分别处理这些数据库之外的问题。

## 术语定位：看到技术名时回到哪个模块

| 术语 | 这里的含义 | 所属章节 |
|---|---|---|
| Harness | 围绕模型组织任务、工具、状态与验证的执行系统 | 00、01 |
| 原生 Tool Calling | 供应商结构化的工具定义、调用身份与结果协议 | 01、04 |
| Prompt Cache | 供应商对可复用输入前缀的处理缓存，不是回答缓存 | 02 |
| epoch | 一版模型上下文视图的边界，不是新用户任务 | 02、03 |
| CompactionCheckpoint | 摘要、源事件区间和保留边界构成的压缩记录 | 03 |
| Artifact | 完整日志、diff、摘要等可校验和回读的文件内容 | 03、09、10 |
| 幂等 | 重复提交同一逻辑请求，不重复造成同一业务动作 | 04、10 |
| CAS | 基于预期版本提交；拒绝把旧状态更新套到新状态 | 04、10、11 |
| 背压 | 下游处理不过来时有界排队、限流或拒绝 | 05、10 |
| worktree | Git 的独立工作目录，不是安全沙箱 | 05、08 |
| 程序性 Skill | 可复用步骤、适用条件、验证要求及证据 | 07 |
| Single Writer | 同一工作区受控修改的唯一所有者；不能管住外部编辑器 | 04、08、12 |
| WAL | SQLite 的预写日志模式；不代表多写事务同时执行 | 10 |
| SSE | 单向服务器事件流，控制命令另走接口 | 10、11 |
| UNKNOWN | 动作是否生效暂时不确定；不能自动按失败重放 | 05、12 |
| 消融 | 一次去掉一项机制，判断效果来自哪里 | 13 |
| LSP | 语言工具的标准化导航与诊断协议 | 15 |

术语解释的外部依据分别见正文对应引用；合同、事务组合和任务案例是本次建议设计。对照阅读时，先找到用户问题，再找到模块职责，最后看技术，而不是反过来为了使用某个技术去创造功能。
