## 1. 模型接口：保留可用入口，深化工具协议

**功能是什么：** 让用户继续通过已有的 OpenAI 格式配置运行代码助手，并让模型提出的工具动作具有可追踪身份和严格参数，而不是靠整段回答里的 XML 标签表示动作。

**用户决定：** 项目升级前的 OpenAI 接口已经能用；沿用它，有缺口时按 OpenAI 格式补齐。不能把本轮描述为“从没有模型接入到新建 OpenAI 接入”。

现有接口可用与已经具备原生 tool calling 是两件事。既有源码核查表明请求已使用 OpenAI 风格端点，但消息主要是拼接文本，执行侧仍解析文本工具标签。B 阶段深化不可变 ModelResponse、原生 tool calls、消息组、结果回填和用量归属，保留已有 WorkflowKernel。

第一落点沿用当前实际配置的 OpenAI 格式后端；不擅自替换模型、不强迫迁到官方域名、不改动用户凭据。A 阶段由执行子 Agent 从现有可用配置确认具体端点协议和能力，仅记录去敏摘要。`/responses` 与 `/chat/completions` 的请求体不能混发；是否需要兼容路径以现有真实使用为依据，不承诺所有网关与官方 API 能力等价。

**A 报告确认的当前事实：** XML 是现有唯一工具执行协议，不是已经存在于原生协议旁边的可选模式。已有网关为 `codexapis.com` 的 `/v1/responses`，模型为 `gpt-5.5`；一次逻辑探测经内置重试后获得成功响应，不等于只发生一次 HTTP 尝试或一次计费。既有配置可用不表示原生 tool_calls 已验证。

**B 的目标：** 接入原生工具后，把仍有实际兼容需求的 XML 收成显式兼容，不静默切换。离线 fake 与旧版基线可用于对照，不能因此保留两套正式事实源或假成功执行路径。新增第二供应商原生协议不属于本轮必要交付。

**验收变化：** 既有可用配置应能继续使用；原生工具组及真实缓存能力分别验证。A 报告说明当前缺缓存字段被记为 `0`/`false`；缺字段显示 unknown 是 B 的目标，不是当前能力。当前 host 未发送 cache key，但响应仍可能报告 cached_tokens；不能把未发 key 等同于未命中。A 的单次响应样本不替代冷/热对照。

影响原章：01、02、14；阶段：A、B。

## 2. 产品入口：直接沿用 pico 的前台 CLI

**功能是什么：** 在目标仓库的终端里提交任务、连续对话、查看工具与验证结果，并在退出后通过本地记录恢复。

**用户决定：** 本问题不扩大设计，直接参考本地 pico 的做法。经定向只读核查，本地 pico 实际位于 `pico_coding-agent-main/coding-agent-main/`，使用前台 Python CLI；带 prompt 为 one-shot，不带 prompt 进入 REPL，使用 `--cwd` 与 `--resume <id|latest>`。它没有常驻服务或 Web 入口。

SkillForge 沿用这个交互拓扑和已有命令命名，保留自己的 `.skillforge` 状态目录，不改名为 `.pico`，也不要求复制 pico 的旧 JSON 存储实现。SQLite 与工件目录仍可在前台 CLI 内工作，asyncio 也不等于新增 daemon。

2026-09-13 A 报告已经核实：当前 SkillForge 本身是前台 CLI，one-shot/REPL/--cwd/--resume 路径已运行，无 FastAPI 或对外 SSE/Web 入口。此前 pico 核查不能单独证明 SkillForge 现状，此处现状依据是 A 报告。当前无服务可拆；若后续工作区确实出现已有可用服务，应记录并保留，不能为照搬 pico 自行拆除。

| 用户动作 | 本轮目标行为 |
|---|---|
| 带任务启动 | 执行单次任务并输出结果 |
| 不带任务启动 | 进入当前进程的 REPL |
| 暂停、取消、追加要求 | 在 CLI 的安全边界处理，区分受理与实际停止 |
| 正常退出或前台进程终止 | 不承诺任务继续；记录终态或下次可识别的未完成状态 |
| 再次启动并 resume | 核对工作区、调用、进程及证据后恢复，不能直接重放旧动作 |

强杀或终端关闭可能留下需要核对的子进程；不能据“前台结束”宣称整个进程树必然安全退出。这正是 C 阶段 ProcessJob 与恢复的验收对象。

**直接范围调整：** 原 10、11、14 章中 FastAPI、对外 SSE、浏览器重连、Web 审阅页和关闭客户端后后台持续执行延后。当前仍实施本地状态—事件事务、重复命令身份、时间线、取消、恢复和 CLI 差异审阅；不建一个没有当前消费者的 HTTP 控制面。上游模型响应可能采用 SSE，这是供应商协议，与对外提供 SSE 服务无关。

**平台：** 不新增“必须使用 WSL2”的产品入口要求，也不因 Python CLI 就宣称全平台进程管理等价。A 记录真实实施环境；C 对该环境的取消和路径行为验收。无法保证的原生 Windows 进程树能力应明确记为限制，不能冒称通过，也不自动扩展成跨平台改造项目。

**Skill 后置学习与 CLI：** 学习任务由当前 CLI 生命周期中的后置工作处理，不另起驻留服务。主结果先交付，随后明确显示学习状态；若退出、取消或进程中断，未完成 LearningRequested 保留为待办，在后续正常启动的既有授权和预算下继续。学习失败不改写主任务成功结果，不在 CLI 已退出后声称仍在学习。不得偷偷拉起后台收费进程。

核查定位：pico 的 `README.md:3–20`、`pico/cli.py:286–337`（one-shot/REPL）、`pico/cli.py:223–241`（resume 装配）、`pyproject.toml:12–13`（命令入口）。这些路径只作执行侧定位，阶段主控不亲自打开代码。

影响原章：00、05、10、11、12、14；阶段：A、C、D、E。

## 3. 工具授权：任务内持续执行，越界才重新确认

**功能是什么：** 用户授权一个明确改码任务后，Agent 能完成必要的修改—验证—修正循环，不需要每次小补丁都等用户点击。

**用户决定：** 普通改码与已批准验证在任务范围内自动继续；最终集中审阅差异。超范围、破坏性动作及对外发布等另外确认，逐补丁审批作为可选严格方式保留。

| 类别 | 默认行为 |
|---|---|
| 已授权仓库内读取、搜索、读工件 | 自动执行，仍检查范围 |
| 当前任务范围内的普通补丁 | 自动执行，仍检查文件前态哈希和记录差异 |
| 已声明并获准的验证操作 | 在批准的工作目录和动作范围内执行，不借此放行任意 shell |
| 超出任务范围、破坏性操作、安装/联网等未获准能力 | 请求对应范围的授权 |
| 推送、发布、发消息 | 本轮不自主执行；只有用户明确授权且能力已实现时才能另行处理 |
| 用户选择的严格逐补丁方式 | 批准精确 PatchPlan 后执行，版本或参数变化要重新核对 |

实现上区分两种事实：**授权范围**决定可做什么；**写入预条件**决定这份补丁是否仍可正确应用。文件哈希变化会使旧补丁失效，但不自动撤销原任务内普通写入授权。Agent 应重新读取、调整补丁并按原范围继续；存在无法自行解决的用户编辑冲突才请求协助。

精确审批仍绑定参数与版本，不能拿批准 A 的票据执行 B。任务范围授权也不能被 Skill、日志或子 Agent 输出扩大。用户追加要求要重新判定受影响计划；纯实现进展不应不断把同一授权作废。

范围授权与精确审批属于同一个工具策略中的两种授权依据，不另建相互冲突的权限系统。

**新增验收 ADD-AUTH：** 同范围多次修改和已获准验证无需重复询问；外部编辑使旧补丁停止但不错误撤销整个任务权限；越界动作仍被拦住；严格方式仍拒绝移用旧票据。

影响原章：04、09、11、12，附录 EX02/BE05 的适用方式；阶段：B、C。

## 4. Skill 沉淀：自动候选，人工发布，默认仓库内

**功能是什么：** 从有证据的完成任务提炼下次可用的诊断方法与限制条件；候选可以自动积累，但只有用户接受的版本才影响后续任务。

**用户决定：** 接受项目级自动候选，通过可学习性筛选后才在独立预算内提炼，不逐次询问是否生成；默认当前仓库，集中审核后生效。文档型候选不必每次重跑完整原任务。

流程仍是“可学习性筛选 → 证据包 → 候选提炼 → 来源/适用性/冲突检查 → 集中审核 → 不可变 ACTIVE 版本”。沿用原 PromotionGate，但其中不适合新合同的判据需要由执行侧修正，不能只保留名称却继续强制所有候选走 pytest 模板。

每条重要操作应有来源，未证实的推论必须标为待验证。候选默认 repository scope，跨仓库自动泛化与全局晋升不纳入首轮。保留反例、不适用条件、撤回及 Run 版本固定；来源可信不等于普遍正确。

候选准入和系统效果评测分开：单份候选执行适用的来源与内容检查，不机械重演整条改码链；D/E 仍用独立任务族正负例验证检索误用和机制效果。未经检查的候选不能借“减少成本”自动 ACTIVE。

学习预算与主任务执行分账并明确总费用，用户可关闭自动提炼。预算不足时记录待办或未生成原因，不偷用主任务剩余额度无限提炼。数值沿用已授权项目配置；尚未配置时由实施侧报告必要配置，不在本文编造价格或限额。

**新增验收 ADD-LEARN：** 任务不值得学习时不生成；主任务先交付，提炼失败不改变交付状态；候选不会自动启用；在当前 CLI 退出后不声称后台继续；待办恢复不重复生成同一版本。

影响原章：07、10、11、13；阶段：D、E。

## 5. 验证：按任务合同选择证据

**功能是什么：** 让“完成”对应这次任务真正需要的检查，既避免伪造测试成功，也避免纯文档工作被不相关测试卡住。

**用户决定：** 代码行为变更用相关测试，构建/类型/配置用对应检查，纯文档用内容与链接检查。人工验收必须来自用户真实结论。

目前证据链偏向 pytest；B 阶段将 VerificationRecord 与 TaskContract 接起来，首先支持当前任务实际需要的检查，不开发通用验证插件平台。

| 任务 | 可选择的依据 | 不能推断 |
|---|---|---|
| 修复行为或回归 | 目标测试、相关回归与当前差异版本 | 退出零就证明所有业务正确 |
| 类型或构建变更 | 真实类型/构建检查、命令及版本记录 | 未运行却写通过 |
| 配置/数据结构变更 | 对应格式、schema 或启动前合同检查 | 解析成功就证明全部运行行为正确 |
| 纯文档变更 | 内容要求、文件/链接存在性，必要时用户审阅 | 必须跑无关 pytest |
| 复杂视觉验收 | 用户实际确认、对应版本和范围 | 模型替用户写“人工通过” |

非 pytest 的可信命令退出状态可以记录，日志解析状态另列；无法解析细节不等于失败，也不能臆造测试计数。TaskContract 若要求精确收集数，未取得该事实仍为 INCONCLUSIVE。相关验证记录必须绑定最终版本。

**新增验收 ADD-VERIFY：** 文档任务可通过适用检查完成；类型/构建检查不因不是 pytest 被丢弃；明确要求 pytest 的任务仍不能用零收集或未解析日志冒充通过；模型自述不能生成正式验证记录。

影响原章：03、07、09、13，附录 BE08；阶段：B，后续阶段沿用。

## 6. 阶段依赖：最小存储放在 B 前置

**功能是什么：** 让工具身份、工件和压缩 checkpoint 从第一次接入时就有同一份可恢复记录，避免先造临时系统再迁移。

**用户决定：** A 固定基线后，B 的前置工作建立最小运行记录、调用身份、事件及工件存储；C 再补进程、控制、审批和恢复的完整行为。

顺序为 `A → B（存储基础 → 原生协议/工具/上下文）→ C → D → E`。仍是一阶段一主控，不增加新阶段或让两个主控共同拥有 B。

B 的最小存储含运行/会话身份、状态与事件共同提交、tool call 身份、工件索引及就绪状态，足以承接模型结果和 CompactionCheckpoint。是否独立建表由实现所需决定，不要求每个概念一个类或一张表。C 直接扩展同一事实源；原 JSON 可作兼容导入或导出，不能成为另一份可写主状态。

阶段的验收归属见开发指南。基础阶段不提前承诺 C 的完整恢复、D 的泛化效果和 E 的性能结果。

## 7. 维持与延后

维持原有核心：缓存感知稳定前缀、完整工具组、可回查大输出、Token 准入、可验证摘要、长进程治理、文件新鲜度、证据驱动 Skill、有界只读委派、SQLite 本地一致性、恢复和 Context Inspector。

产品多 Agent 仍最多两个并行只读子任务、深度一层，父级写入及验证；小任务不强制委派。实施团队的主控则不得亲自看代码、写代码或测试，两者不能混淆。

本轮延后：常驻服务/Web/SSE、并行写入、任意历史工作区还原、LSP、第三方 Skill 安装、MCP/插件市场与远程执行。容器隔离保留为原方案的可选路线，默认本地可信仓库执行不能声称通过容器隔离验收；若用户以后批准该路线，另定范围。

来源沿用原方案登记。外部行为在具体采用前由执行侧按目标版本核对，不依赖泄漏镜像中不可验证或空实现的机制。
