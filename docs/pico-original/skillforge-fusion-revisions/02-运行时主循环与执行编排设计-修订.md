# 02-运行时主循环与执行编排设计-修订

## 1. 修订结论

这一章需要认真修订。

Pico 原来的 `ask()` 主循环仍然是 SkillForge Pico Fusion 的核心底座：一条用户请求进入 runtime 后，依然会经历“创建 run、构建 prompt、请求模型、解析输出、执行工具、记录状态、写出报告”的闭环。

但 Fusion 在这条主循环上新增了一个重要控制面：`workflow / TaskPacket / evidence gate`。所以 02 章不能只做 `pico -> skillforge` 的改名，还要补清楚：

* 普通 one-shot / REPL 仍然走轻量主循环。
* workflow mode 会在主循环外加 phase 状态机。
* 每轮 prompt 可能多出 TaskPacket。
* 当前 phase 会限制 allowed tools。
* 工具结果会额外写入 EvidenceStore。
* handoff 前可能要过 completion evidence gate。
* 通过验证的 workflow 才可能产出 quarantine SkillCandidate。

一句话版本：

> SkillForge 保留 Pico 的感知、决策、行动、记录主循环；Fusion 新增的是 workflow 阶段约束和证据门禁，让“模型说完成了”变成“运行证据证明可以完成”。

## 2. 原章应保留的主线

原 Pico 02 章最值得保留的是这条执行闭环：

```text
user request
  -> ask()
  -> create TaskState + run dir
  -> build prompt + metadata
  -> model_client.complete()
  -> parse raw output
  -> tool / final / retry
  -> run_tool() 或 finish / retry
  -> update history / task_state / trace / memory
  -> write report.json
```

这条主线在 Fusion 中仍然成立，只是名字和落盘目录变了：

| Pico 原口径 | SkillForge Fusion 口径 |
| --- | --- |
| `Pico.ask()` | `SkillForge.ask()` |
| `pico/runtime.py` | `skillforge/runtime.py` |
| `.pico/runs/<run_id>/` | `.skillforge/runs/<run_id>/` |
| `Pico` 实例 | `SkillForge` 实例 |
| `tool_signature()` | `prompt_tool_signature()` / workflow-aware tool signature |

原章里对 `attempts`、`tool_steps`、`parse()`、`run_tool()`、`TaskState`、`RunStore` 的解释仍然有用，修订时不要推翻。

## 3. 普通路径：一次请求怎么跑

不启用 `--workflow` 时，SkillForge 的运行方式和 Pico 很接近。

### 3.1 启动后进入 `SkillForge.ask()`

CLI 在 `build_agent()` 中先装配好：

* `WorkspaceContext`
* `SessionStore`
* `ModelClient`
* approval policy
* max steps / max new tokens
* 可选 workflow 配置

如果用户发起 one-shot，请求会直接进入：

```text
SkillForge.ask(user_message)
```

如果是 REPL，每一轮用户输入也会进入同一个 `ask()` 主循环。

### 3.2 `ask()` 开头先立运行现场

`ask()` 一开始不是马上调模型，而是先把本轮 run 建起来：

1. 把用户请求写入 working memory 的 `task_summary`。
2. 把用户消息追加到 session history。
3. 重置本轮 workflow 状态（如果启用了 workflow）。
4. 创建新的 `TaskState`，生成 `run_id` 和 `task_id`。
5. 把 `resume_status` 写进 `TaskState`。
6. 在 `.skillforge/runs/<run_id>/` 下创建 run 目录。
7. 写出第一版 `task_state.json`。
8. 追加 `run_started` trace。

这样做的意义是：一条用户请求从刚开始就有物理边界。后续排查问题时，不需要从整段 session history 里猜“这一轮任务到底从哪里开始”。

### 3.3 主循环仍是四步

主循环仍然可以压成四个动作：

```text
感知 -> 决策 -> 行动 -> 记录
```

更具体一点：

```text
while tool_steps < max_steps and attempts < max_attempts:
  attempts += 1
  task_state.record_attempt()
  write task_state.json

  prompt, metadata = _build_prompt_and_metadata(user_message)
  emit trace: prompt_built

  raw = model_client.complete(prompt, ...)
  kind, payload = parse(raw)
  emit trace: model_parsed

  if kind == tool:
    run_tool(name, args)
    record tool result
    emit trace: tool_executed
    create checkpoint
    continue

  if kind == retry:
    record retry notice
    continue

  if kind == final:
    finish success
    write report.json
    return final
```

这里的两个计数仍然很关键：

| 字段 | 含义 | 诊断价值 |
| --- | --- | --- |
| `attempts` | 调模型的轮数 | 高 attempts 低 tool_steps，通常说明模型格式不稳定或一直 retry |
| `tool_steps` | 真正执行工具的次数 | 高 tool_steps 说明 agent 在真实做动作，需要关注副作用和预算 |

## 4. 每轮 prompt 怎么动态变化

02 章必须讲清楚：prompt 在 runtime 里不是固定文本，而是当前执行状态的投影。

每轮都会调用：

```text
_build_prompt_and_metadata(user_message)
```

这一步会做几件事：

1. 如果启用了 workflow，先编译当前 phase 的 TaskPacket。
2. 判断工具签名是否变化，必要时强制刷新 prefix。
3. 调用 `refresh_prefix()` 重新采样 workspace。
4. 重新评估 `resume_state`。
5. 调用 `ContextManager.build(user_message)` 拼装 prompt。
6. 生成 prompt metadata。

metadata 会记录很多运行时解释信息，例如：

* `prefix_chars`
* `workspace_chars`
* `memory_chars`
* `history_chars`
* `request_chars`
* `tool_count`
* `prefix_hash`
* `prompt_cache_key`
* `workspace_fingerprint`
* `tool_signature`
* `workspace_changed`
* `prefix_changed`
* `resume_status`
* `budget_reductions`

如果启用了 workflow，还会额外记录：

* `workflow_name`
* `workflow_phase`
* `workflow_status`
* `workflow_allowed_tools`
* `workflow_evidence_refs`
* `workflow_active_skill_ids`

所以 02 章可以这样讲：

> prompt 不是静态 prompt 模板，而是 runtime 把当前 workspace、memory、history、request、可用工具、workflow phase 和 evidence 摘要投影出来的一份执行状态快照。

## 5. parse：模型文本如何变成控制流

这一节原文基本保留。

模型返回的是文本，但 runtime 需要的是动作。`parse()` 会把 raw output 压成三类：

```text
tool
final
retry
```

### 5.1 tool 分支

模型如果返回工具调用，会进入 tool 分支。

支持两类格式：

```text
<tool>{"name":"read_file","args":{"path":"README.md"}}</tool>
```

以及：

```text
<tool name="write_file" path="demo.py"><content>...</content></tool>
```

解析成功后，主循环不会直接调用底层工具，而是统一进入：

```text
run_tool(name, args)
```

### 5.2 final 分支

模型如果返回：

```text
<final>...</final>
```

普通路径下就会准备结束本轮 run。

但在 workflow mode 下，final 不一定代表整个任务结束。它可能只是当前 phase 的阶段性输出。

### 5.3 retry 分支

如果模型输出格式损坏、空响应或不能解析成有效动作，runtime 会进入 retry 分支，把格式纠偏说明写回 history，然后进入下一轮。

这就是 `attempts` 高而 `tool_steps` 低的常见来源。

## 6. 工具调用如何接回主循环

`run_tool()` 是模型意图接触外部世界的总闸口。

原 Pico 已有这些检查：

* 工具是否注册。
* 参数是否合法。
* 路径是否逃出 workspace。
* 是否重复调用。
* 高风险工具是否需要 approval。
* read-only 模式是否允许。
* 执行前后是否产生 workspace diff。

Fusion 后要补充两点：

### 6.1 workflow phase 会限制工具

如果启用了 workflow，当前 phase 会决定 allowed tools。

例如：

* `repo_audit` 的只读阶段不能写 workspace。
* `verify` 阶段可以更关注 `log_run` / verification evidence。
* `handoff` 阶段通常不应该再自由修改代码。

所以工具边界从 Pico 的：

```text
tool registry + args validation + approval + path guard
```

变成 Fusion 的：

```text
tool registry + args validation + approval + path guard + workflow phase policy
```

### 6.2 工具结果会写 evidence

普通 trace 仍然会写：

```text
trace.jsonl
```

但 Fusion 还会额外把工具行为写入 EvidenceStore：

```text
.skillforge/runs/<run_id>/evidence/
  index.json
  records/
  log/
```

工具 evidence 会记录：

* tool name
* args 摘要
* status
* affected paths
* workspace_changed
* diff_summary
* related evidence ids
* 当前 workflow 和 phase

如果工具造成 workspace 变化，还可能生成 `diff` evidence。

如果在 `verify` phase 调用 `log_run`，且日志可解析为通过/失败，还可能生成 `verification` evidence。

这点很重要：Fusion 不只问“模型做了什么”，还问“这些动作能不能成为完成判定的证据”。

## 7. Workflow mode：新增的控制面

这是 02 章最需要补的内容。

Pico 原文说 runtime 没有复杂 phase machine。这个说法对 Pico 原项目成立，但对 Fusion 需要修订：

> 普通路径仍然是单循环；workflow mode 新增了 phase machine。

Fusion 内建三类 workflow：

| Workflow | Phases | 用途 |
| --- | --- | --- |
| `repo_audit` | `intake -> investigate -> audit -> handoff` | 只读仓库审阅 |
| `code_change` | `intake -> plan_compile -> implement -> verify -> audit -> skill_distill -> handoff` | 通用代码修改 |
| `test_fix` | `intake -> investigate -> implement -> verify -> audit -> skill_distill -> handoff` | 失败测试修复 |

### 7.1 WorkflowKernel 管 phase 和预算

`WorkflowKernel` 负责维护：

* 当前 workflow 名称。
* 当前 phase。
* phase history。
* rounds_used。
* tools_used。
* status。
* stop_reason。

每次请求模型后，会记录 round：

```text
workflow_kernel.record_round()
```

每次执行工具后，会记录 tool：

```text
workflow_kernel.record_tool()
```

如果超过 workflow 的 round budget 或 tool budget，workflow 可以进入 blocked / handoff 路径，避免无限循环。

### 7.2 TaskPacket 是当前 phase 的任务合同

每轮 prompt 前，workflow mode 会编译 TaskPacket。

TaskPacket 里包含：

* user intent
* workflow name
* current phase
* workflow state
* kernel state
* allowed tools
* evidence refs
* evidence briefs
* active skill ids
* active skill constraints
* prompt context

它不应该包含：

* raw log 全文
* secret
* quarantine / rejected / archived skill
* 未通过安全检查的 active skill

所以 TaskPacket 的作用不是“多塞一些上下文”，而是给模型一份当前阶段的任务合同：

> 当前你在哪个 phase，可以用哪些工具，可以引用哪些 evidence，有哪些 active skill 可以复用。

### 7.3 final 在 workflow 下可能只是 phase 输出

普通路径下，模型给 final 就结束。

workflow mode 下，如果当前 phase 还不是 `handoff`，模型给 final 后，runtime 会把它当成当前 phase 的阶段输出，然后尝试推进 workflow phase：

```text
intake -> investigate -> implement -> verify -> audit -> skill_distill -> handoff
```

也就是说：

```text
final != 整个任务完成
```

在 workflow mode 里，更准确是：

```text
final = 当前 phase 的交付文本
```

只有到了 handoff，并且证据门禁通过，才算整个 workflow run 完成。

## 8. Completion evidence gate：什么时候才算完成

Fusion 最大的语义变化之一，就是不能只相信模型的 final。

对于允许写 workspace 的 workflow，在 `handoff` phase 输出 final 时，runtime 会记录 handoff evidence，然后调用 completion gate。

gate 会检查 workflow 要求的完成证据，例如：

* diff evidence
* verification evidence
* audit evidence
* handoff evidence

如果缺证据，workflow 会被阻塞，`TaskState` 会记录类似 completion gate blocked 的 stop reason，并写出 report。

这改变了原 Pico 的完成语义：

| 原 Pico | Fusion workflow mode |
| --- | --- |
| 模型给 final，通常就能完成 | 模型给 final 只是必要条件，不一定充分 |
| report 主要解释运行过程 | evidence 还要支持完成判定 |
| evaluator 在侧边做验证 | completion gate 可以在 handoff 前阻止完成 |

这部分可以用一句面试话术解释：

> 原 Pico 的主循环保证 agent 有边界地跑完；Fusion 的 evidence gate 进一步保证它不能凭一句话宣布完成，必须拿出 diff、验证、审计和交接证据。

## 9. SkillCandidate 何时产生

如果 workflow 包含 `skill_distill` phase，并且最终 handoff 证据通过，runtime 可能从这次 verified run 中产出 SkillCandidate。

但要注意三个边界：

1. candidate 默认进入 quarantine。
2. candidate 不会自动进入后续 prompt。
3. 只有人工 promote 且 PromotionGate 通过后，才会成为 active SkillCard。

所以不要把它讲成“每次任务结束自动沉淀成长期技能”。准确说法是：

> Fusion 可以从 verified workflow 中提炼候选经验，但候选经验先隔离，只有通过人工 promote 和安全门禁后，才能作为 active skill 被 TaskPacket 编译进后续任务。

## 10. 停止条件的修订版

普通路径的停止条件仍然是：

1. 模型给出 final。
2. 达到 step limit。
3. 达到 retry limit。

Fusion 后需要补充 workflow 相关停止：

4. workflow round budget 超限。
5. workflow tool budget 超限。
6. completion evidence gate blocked。
7. audit fail blocked。
8. skill distill failed 时 fail-closed。

不是每个普通 one-shot 都会遇到这些条件。它们主要出现在 workflow mode。

## 11. 运行工件的修订版

原 Pico 每轮 run 至少关注三件套：

```text
task_state.json
trace.jsonl
report.json
```

Fusion 仍然保留这三件套，并新增 evidence 子树：

```text
.skillforge/runs/<run_id>/
  task_state.json
  trace.jsonl
  report.json
  evidence/
    index.json
    records/
    log/
```

可以这样解释每类工件：

| 工件 | 作用 |
| --- | --- |
| `task_state.json` | 看当前 run 状态、尝试次数、工具步数、停止原因 |
| `trace.jsonl` | 看事件时间线，回答“运行中发生了什么” |
| `report.json` | 看最终摘要、prompt metadata、stop reason、结果 |
| `evidence/index.json` | 看结构化证据索引 |
| `evidence/records/*` | 看 workflow/tool/diff/verification/audit/handoff/skill 等证据记录 |
| `evidence/log/*` | 保存 raw log，避免直接塞进 prompt |

这也是 Fusion 版 02 章应补的重点：trace 解释过程，evidence 支持判定。

## 12. 不应夸大的地方

修订 02 章时要特别注意这些边界：

* 不要说 workflow 替代了 `SkillForge.ask()`；它是加在主循环上的控制面。
* 不要说所有 one-shot / REPL 都强制经过完整 phase gate；当前主要通过 `--workflow` 启用。
* 不要说模型给 final 就一定完成；workflow handoff 还要看 completion gate。
* 不要说 raw log 进入 prompt；raw log 落盘，prompt 只用 brief / failure detail / evidence ref。
* 不要说 SkillCandidate 会自动复用；candidate 默认 quarantine，active 需要 manual promote。
* 不要说已经实现任意 DAG；v1 是固定 workflow templates。
* 不要说实现了 Web UI、标准 MCP server、RAG、多 worker 并发写码；这些是非目标。

## 13. 推荐改写结构

如果后续生成整合阅读版，02 章建议按这个顺序写：

1. 为什么 runtime 是系统心脏。
2. 从用户请求到一次 run。
3. `SkillForge.ask()` 开头如何创建现场。
4. 感知、决策、行动、记录主循环。
5. 每轮 prompt 和 metadata 为什么动态重建。
6. `parse()` 如何把模型文本压成 tool / final / retry。
7. `run_tool()` 如何把工具结果接回状态。
8. `TaskState`、`RunStore`、trace/report 的分工。
9. Fusion 新增 workflow mode：phase、TaskPacket、allowed tools、budget。
10. EvidenceStore 和 completion gate 如何改变“完成”的定义。

12. 停止条件和边界。

## 14. 推荐收口话术

可以把本章最后改成：

> SkillForge 的 runtime 主循环继承了 Pico 的核心设计：一条用户请求会被推进成一次独立 run，过程中每轮重新构建 prompt、请求模型、解析输出、执行工具、记录状态，并把 task_state、trace 和 report 落盘。Fusion 的新增点不是推翻这个循环，而是在需要强约束的 workflow mode 下，为主循环加上 phase、TaskPacket、allowed tools、evidence gate、audit 和 skill distill。这样 runtime 不只知道“模型最后说了什么”，还知道“它在哪个阶段做了什么、用了什么工具、留下了什么证据、是否真的满足完成条件”。
