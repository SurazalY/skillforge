# 07-会话状态、运行工件与恢复机制设计-修订

## 1. 修订结论

这一章需要认真修订。

原 Pico 07 章的核心设计仍然成立：session 和 run artifact 必须分开。session 回答“下一次怎么继续做”，run artifact 回答“刚才这轮到底发生了什么”。`task_state.json`、`trace.jsonl`、`report.json` 三件套仍然是 SkillForge Pico Fusion 的运行复盘底座。

但 Fusion 在这一章上新增了很重要的证据面和恢复面：

* `.pico/` 迁移为 `.skillforge/`。
* session 里新增 checkpoints、runtime identity、resume_state。
* `TaskState` 新增 `checkpoint_id` 和 `resume_status`。
* run 目录下新增 `evidence/` 子树。
* workflow 会生成 workflow/tool/log/diff/verification/audit/skill/handoff 等 EvidenceRecord。
* completion gate、audit 和 handoff 依赖 evidence，而不是只看模型 final。
* verified skills 的 candidate/active/archive 落在 `.skillforge/skills/`，和 run evidence 有引用关系，但不是 run 三件套本身。

一句话版本：

> Pico 07 章讲的是“session 和 run 三件套解耦”；Fusion 版 07 章还要讲“checkpoint/resume/evidence/skills 如何把恢复、审计和经验沉淀接到同一套 `.skillforge/` 持久化布局里”。

## 2. 原章应保留的主线

原章这条分层仍然要保留：

```text
session
  -> 为下一次继续工作服务
  -> history / memory / checkpoint / runtime identity

run artifact
  -> 为本次运行复盘、审计、评测服务
  -> task_state.json / trace.jsonl / report.json / evidence
```

不要把 07 章改成“Fusion 新写了一套状态系统”。更准确的是：

> Fusion 保留 Pico 的 session/run 解耦，并在 run artifact 下增加结构化 evidence，在 session 下增加 checkpoint/resume 判断。

原来三件套的职责也仍然成立：

| 工件 | 回答的问题 | 是否保留 |
| --- | --- | --- |
| `task_state.json` | 这轮当前跑到哪了 | 保留 |
| `trace.jsonl` | 过程里发生过什么 | 保留 |
| `report.json` | 最终摘要和聚合指标是什么 | 保留 |

Fusion 不是替换三件套，而是在三件套旁边加证据索引。

## 3. 新目录布局

原 Pico 目录大致是：

```text
.pico/
  sessions/
  runs/<run_id>/
    task_state.json
    trace.jsonl
    report.json
  memory/
```

Fusion 版改为：

```text
.skillforge/
  sessions/
    <session_id>.json
  runs/<run_id>/
    task_state.json
    trace.jsonl
    report.json
    evidence/
      index.json
      records/
        ev-*.json
      log/
        log-*.txt
  memory/
    MEMORY.md
    topics/*.md
  skills/
    candidates/
    active/
    archive/
```

这里最重要的变化不是换目录名，而是运行证据和技能生命周期都被纳入 `.skillforge/`。

可以这样讲：

* `sessions/` 负责可恢复会话。
* `runs/` 负责单轮运行复盘。
* `runs/<run_id>/evidence/` 负责结构化完成证据。
* `memory/` 负责长期主题记忆。
* `skills/` 负责 verified skills 的候选、激活和归档。

## 4. Session 现在保存什么

Session 仍然落在：

```text
.skillforge/sessions/<session_id>.json
```

核心字段仍包括：

| 字段 | 作用 |
| --- | --- |
| `id` | session id |
| `created_at` | 创建时间 |
| `workspace_root` | 工作区根目录 |
| `history` | 会话历史 |
| `memory` | working memory |

Fusion 还会确保 session 中存在：

| 字段 | 作用 |
| --- | --- |
| `checkpoints` | checkpoint 索引和内容 |
| `runtime_identity` | 上次运行的身份指纹 |
| `resume_state` | 本次恢复判断结果 |
| `workflow` | 可选 workflow 名称 |

所以现在 session 不只是 history + memory。它还保存用于恢复判断的 checkpoint 和 runtime identity。

但要注意：session 仍然不是完整运行证据库。

session 里不应该保存 raw log、完整 evidence record、完整 trace，也不保存 SkillCandidate 的正式文件。那些属于 run evidence 或 SkillStore。

## 5. Resume 恢复的仍是会话状态

CLI 恢复入口仍然是：

```text
--resume <session_id>
--resume latest
```

实现上仍然是：

```text
SessionStore.load(session_id)
SkillForge.from_session(...)
```

恢复时会重新构造一个新的 SkillForge 实例，并重新注入：

* 当前 model client
* 当前 WorkspaceContext
* 当前 approval policy
* 当前 max steps / max tokens
* 当前 workflow 配置

然后把旧 session 的 history、memory、checkpoints 等读回来。

所以原章这句话仍然正确：

> resume 恢复的是会话数据状态，不是旧进程本身。

Fusion 要补充的是：恢复后会立即评估 checkpoint 与当前运行现场是否一致。

## 6. Runtime Identity 与 Resume State

Fusion 现在会记录 runtime identity，用来判断恢复时环境有没有漂移。

`current_runtime_identity()` 大致包含：

* `session_id`
* `cwd`
* `model`
* `model_client`
* `approval_policy`
* `read_only`
* `max_steps`
* `max_new_tokens`
* `feature_flags`
* `shell_env_allowlist`
* `workspace_fingerprint`
* `tool_signature`

恢复时 `evaluate_resume_state()` 会比较：

* checkpoint schema 是否匹配。
* key files 的 freshness 是否匹配。
* runtime identity 里的关键字段是否变化。
* memory 中 stale file summaries 是否被失效。

最终得到的状态包括：

| resume status | 含义 |
| --- | --- |
| `no-checkpoint` | 没有 checkpoint 可判断 |
| `full-valid` | checkpoint 与当前现场匹配 |
| `partial-stale` | key files 或文件摘要 freshness 过期 |
| `workspace-mismatch` | runtime identity / workspace / tool surface 不一致 |
| `schema-mismatch` | checkpoint schema 不兼容 |

这比原 Pico 的简单 session resume 更强。它不只是恢复，还会告诉模型“恢复后的现场是否可信”。

## 7. Checkpoint 保存什么

Fusion 的 checkpoint 存在 session 里：

```text
session["checkpoints"]
  current_id
  items
```

每个 checkpoint 大致包含：

| 字段 | 作用 |
| --- | --- |
| `checkpoint_id` | checkpoint id |
| `parent_checkpoint_id` | 父 checkpoint |
| `schema_version` | checkpoint schema |
| `created_at` | 创建时间 |
| `current_goal` | 当前目标 |
| `completed` | 已完成内容 |
| `excluded` | 已排除内容 |
| `current_blocker` | 当前阻塞原因 |
| `next_step` | 下一步建议 |
| `key_files` | 关键文件及 freshness |
| `freshness` | 路径到 freshness 的映射 |
| `summary` | 触发原因摘要 |
| `runtime_identity` | 创建时运行身份 |

checkpoint 会在多种场景创建：

* 工具执行后
* run finished
* step limit / retry limit 等停止条件
* freshness mismatch
* workspace mismatch
* context reduction
* completion gate blocked
* audit failed
* skill distill failed

这说明 Fusion 的 checkpoint 不只是“中断恢复点”，也是“重要状态变化的锚点”。

## 8. TaskState 的修订点

原 Pico 的 `TaskState` 记录：

* `run_id`
* `task_id`
* `user_request`
* `status`
* `tool_steps`
* `attempts`
* `last_tool`
* `stop_reason`
* `final_answer`

Fusion 新增或强调：

* `checkpoint_id`
* `resume_status`
* 新的 stop reason

新增 stop reason 包括：

| stop reason | 含义 |
| --- | --- |
| `completion_gate_blocked` | 完成证据不足 |
| `audit_failed` | 审计失败 |
| `skill_distill_failed` | skill 提炼失败 |
| `resume_load_error` | 恢复加载错误 |

所以 `task_state.json` 现在不只看“工具走了几步”，也能看 workflow gate / audit / resume 判断对本轮结果的影响。

## 9. Trace 现在记录什么

`trace.jsonl` 仍然是追加写事件流。

原有事件仍然包括：

* `run_started`
* `prompt_built`
* `model_requested`
* `model_parsed`
* `tool_executed`
* `checkpoint_created`
* `run_finished`

Fusion 会增加 workflow 相关事件，例如：

* `workflow_task_packet_compiled`
* `workflow_phase_transition`
* `skill_candidate_distilled`
* audit / gate 相关失败事件

trace 仍然回答“过程发生了什么”，但它不是 completion gate 的唯一依据。

completion gate 主要看 EvidenceStore 中的结构化 evidence。trace 更适合调试过程和复盘执行路径。

## 10. Report 现在记录什么

`report.json` 仍然是最终摘要层。

Fusion 的 `build_report()` 包含：

* `run_id`
* `task_id`
* `status`
* `stop_reason`
* `final_answer`
* `tool_steps`
* `attempts`
* `checkpoint_id`
* `resume_status`
* `task_state`
* `prompt_metadata`
* `durable_promotions`
* `durable_rejections`
* `durable_superseded`
* `redacted_env`

也就是说 report 现在能回答更多问题：

* 本轮恢复状态是什么？
* 最终挂在哪个 checkpoint？
* prompt 是否发生过 budget reduction？
* 是否有 durable memory promotion？
* secret env 是否被识别并脱敏？
* workflow metadata 是否进入 prompt metadata？

但 report 仍然不是完整证据库。完整 evidence 要去 `runs/<run_id>/evidence/` 看。

## 11. EvidenceStore 是本章最大新增点

Fusion 版 07 章最需要补的是 EvidenceStore。

路径是：

```text
.skillforge/runs/<run_id>/evidence/
  index.json
  records/
    ev-*.json
  log/
    log-*.txt
```

EvidenceRecord 支持的类型包括：

```text
workflow
tool
log
diff
verification
audit
skill
handoff
```

它解决的是原 Pico 三件套没有完全解决的问题：

> 模型说完成了，或者 trace 里出现了某个动作，并不等于系统具备可验证的完成证据。

Fusion 把关键结果结构化成 evidence：

* 工具执行结果变成 `tool` evidence。
* workspace 修改变成 `diff` evidence。
* `log_run` 产出 `log` evidence。
* verify phase 的可解析测试结果变成 `verification` evidence。
* audit phase 产出 `audit` evidence。
* handoff phase 产出 `handoff` evidence。
* skill distill 产出 `skill` evidence。

completion gate 只相信这些结构化 evidence，而不是只相信 final answer 或 trace 文本。

## 12. Raw Log 的落盘语义

`log_run` 会把 raw log 写到：

```text
.skillforge/runs/<run_id>/evidence/log/log-*.txt
```

对应的 `log` evidence record 会保存：

* command
* cwd
* returncode
* status
* parsed_summary
* raw_log_path
* failure_count
* failures

注意边界：

* raw log 不直接进 prompt。
* raw log 不直接进 report。
* prompt 只接收 brief、failure detail 或 evidence ref。
* unparsed log 可以复盘，但不能当 verification pass。

这部分应该放入 07 章，因为它是运行工件布局的一部分。

## 13. Handoff 与 Completion Gate

Fusion 的 workflow 在 handoff 前会检查 completion evidence。

例如 code_change / test_fix 这类 workflow，通常需要：

* diff evidence
* verification evidence
* audit evidence
* handoff evidence

如果证据缺失，会触发：

```text
stop_reason = completion_gate_blocked
```

并写入 workflow evidence、checkpoint、trace 和 report。

handoff 本身也会记录成 `handoff` evidence。`HandoffArtifact` 包含：

* completed
* open_items
* risks
* next_phase
* evidence_refs

这里要注意，不要把 handoff 写成“总会生成独立 handoff.json”。当前 runtime 的核心路径是把 handoff 作为 EvidenceRecord 记录；demo 或其它工具链可能会额外生成 handoff artifact，但 07 章主口径应以 evidence 为准。

## 14. SkillStore 和 Run Artifact 的关系

Fusion 新增 `.skillforge/skills/`：

```text
.skillforge/skills/
  candidates/
  active/
  archive/
```

workflow 通过验证后，SkillDistiller 可能根据 run evidence 生成 SkillCandidate，并写入：

```text
.skillforge/skills/candidates/<candidate_id>.json
```

同时 run evidence 中会记录一条 `skill` evidence，引用 candidate 信息和 freshness path。

这里要分清：

* SkillCandidate 文件属于 SkillStore。
* `skill` EvidenceRecord 属于本次 run。
* candidate 默认 quarantine，不直接进入 prompt。
* 只有人工 promote 后的 active skill 才会被后续 TaskPacket 编译进 prompt。

所以 07 章可以这样说：

> run evidence 提供“这个 candidate 从哪次验证运行来”的证据链；SkillStore 管理 candidate 到 active skill 的生命周期。

## 15. Redaction 与敏感信息

原章提到 secret 脱敏需要回看源码。Fusion 中这个点应该明确保留。

运行时会对 trace / report / evidence payload 做 redaction：

* secret env names 会被识别。
* redacted env summary 会写入 report。
* raw log 和 active skill / candidate 也有安全边界，避免 raw log、secret、protected path 等直接进入 prompt 或 active skill。

注意不要过度宣称：

* 脱敏不是完整 DLP 系统。
* raw log 仍然落盘到本地 evidence/log，需要本地文件权限保护。
* prompt 中不应直接包含 raw log。

## 16. 和前几章的关系

02 章讲运行主循环：

```text
ask -> prompt -> model -> parse -> tool/final -> update state
```

07 章讲这些状态怎么落盘。

03 章讲工具边界：

```text
run_tool -> metadata -> evidence
```

07 章讲这些 evidence 放在哪里。

05 章讲 memory 和 durable memory：

```text
session memory / .skillforge/memory
```

07 章讲 session 如何保存 memory，以及 durable promotions 如何进入 report。

06 章讲 context reduction：

```text
budget_reductions -> context_reduction checkpoint
```

07 章讲 checkpoint 如何保存并参与 resume 判断。

所以 07 章是状态和证据的汇合点：

> 前面几章产生的工具结果、记忆、prompt metadata、checkpoint、workflow evidence，最终都要在 `.skillforge/` 中找到自己的位置。

## 17. 修订原文时应替换的重点

原文如果写：

```text
run artifact 主要是 task_state.json、trace.jsonl 和 report.json。
```

修订为：

```text
这三件套仍是 run artifact 的核心；Fusion 在 run 目录下新增 evidence 子树，用于保存 workflow/tool/log/diff/verification/audit/skill/handoff 等结构化证据。三件套回答运行状态和过程，evidence 回答完成、验证和审计是否有依据。
```

原文如果写：

```text
resume 只是恢复 session 的 history 和 memory。
```

修订为：

```text
resume 仍然恢复 session 数据状态，但 Fusion 会额外评估 checkpoint、key file freshness 和 runtime identity，生成 resume_status。恢复后模型会知道 checkpoint 是 full-valid、partial-stale、workspace-mismatch、schema-mismatch 还是 no-checkpoint。
```

原文如果写：

```text
run artifact 还没有 schema version。
```

修订为：

```text
原始 task_state/report 仍然较轻，但 Fusion 的 checkpoint、EvidenceRecord、EvidenceIndex、TaskPacket 等新增结构已经带 schema_version / artifact_type 等校验字段。修订时应区分“核心三件套本身”和“新增证据/任务包结构”的版本化程度。
```

原文如果写：

```text
trace 和 report 负责审计。
```

修订为：

```text
trace/report 仍然负责过程复盘和聚合；Fusion 的完成审计主要依赖 EvidenceStore 中的结构化 evidence。trace 说明发生过什么，evidence 说明完成条件是否被证据满足。
```

## 18. 不要过度宣称的地方

写 07 章时要避免这些说法：

* 不要说 Fusion 推翻了 Pico 的三件套。三件套仍是核心。
* 不要说 resume 恢复旧进程。它恢复的是 session 数据状态，并重新构造 runtime。
* 不要说所有 run artifact 都完整 schema-versioned。新增 evidence/checkpoint/taskpacket 有 schema，核心三件套仍较轻。
* 不要说 raw log 不落盘。raw log 会落盘，但不进入 prompt。
* 不要说 SkillCandidate 自动变成 active skill。candidate 默认 quarantine，需要人工 promote。
* 不要说 SkillStore 属于 run artifact。SkillStore 是跨 run 的技能生命周期存储；run evidence 只记录本次 run 与 skill 的关系。
* 不要说 handoff 一定是独立 JSON 文件。核心 runtime 口径是 handoff evidence。
* 不要说 EvidenceStore 替代 trace。它们用途不同。

## 19. 建议放入修订版的讲解段

可以把 07 章开头改成下面这种口径：

> SkillForge 继承了 Pico 的状态分层：session 保存下一轮还要继续使用的会话状态，run artifact 保存本轮运行中发生过的事实。区别在于，Fusion 把 run artifact 从三件套扩展成了三件套加 evidence 子树，让验证、审计、交接和 skill distill 都能引用结构化证据。

恢复部分可以写：

> resume 不是把旧进程恢复回来，而是读取旧 session，重新构造一个新的 SkillForge runtime。Fusion 会进一步检查 checkpoint schema、key file freshness 和 runtime identity。如果文件或工具表面已经变化，resume_status 会标记为 partial-stale 或 workspace-mismatch，提醒模型不要盲目相信旧状态。

证据部分可以写：

> EvidenceStore 是 Fusion 对 Pico run artifact 的最大增量。工具、日志、diff、verification、audit、handoff 和 skill 都会以 EvidenceRecord 形式落在 `.skillforge/runs/<run_id>/evidence/`。completion gate 不再相信模型自述完成，而是检查这些 evidence 是否满足 workflow 的完成要求。

结尾可以强调：

> Fusion 版 07 章的重点不是“存了更多 JSON”，而是把恢复状态、运行过程、验证证据和经验沉淀分到不同生命周期里：session 负责继续工作，run 三件套负责复盘，evidence 负责完成证明，SkillStore 负责跨 run 的经验复用。

  |     - tool_steps
  |     - checkpoint_id
  |     - resume_status
  |

  |     - tool_executed
