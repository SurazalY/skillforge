# 04-提示词形态与缓存复用设计-修订

## 1. 修订结论

这一章需要修订。

原 Pico 04 章的主线仍然成立：prompt 不能只当作一整段字符串随便拼，而要区分“相对稳定、值得复用的前缀”和“每轮都会变化的动态内容”。`PromptPrefix`、`prefix_hash`、`workspace_fingerprint`、`tool_signature`、`prompt_cache_key` 这些设计，在 SkillForge Pico Fusion 中仍然保留。

但是 Fusion 让 prompt 形态变复杂了。修订时不能只做 `pico -> skillforge` 的改名，还要补清楚四件事：

* `ContextManager` 已经独立到 `skillforge/context_manager.py`，负责动态 section、预算压缩和 metadata。
* workflow 模式会把 TaskPacket、phase、allowed tools、evidence briefs、active skills 编进 prompt。
* 当前 phase 会改变 `prompt_tool_names()`，从而改变工具说明、工具示例和 `tool_signature`。
* `PromptPrefix.hash` 和 provider 真实缓存命中不是一回事，最终还要看后端返回的 `cached_tokens` / `cache_hit`。

一句话版本：

> Pico 04 章讲的是“稳定前缀怎么复用”；Fusion 版 04 章还要讲“workflow 动态任务包怎么进入 prompt，以及它会怎样影响 prefix、工具签名和真实缓存命中”。

## 2. 原章应保留的主线

原章这条逻辑仍然成立：

```text
PromptPrefix
  - text
  - hash
  - workspace_fingerprint
  - tool_signature
  - built_at

每轮请求前：
  refresh_prefix()
    -> 重新采样 WorkspaceContext
    -> 比较 workspace_fingerprint
    -> 必要时重建 PromptPrefix

真正调用模型前：
  prompt_cache_key = prefix_hash
  prompt_cache_retention = "in_memory"
  model_client.complete(...)

模型返回后：
  抽取 usage / cached_tokens / cache_hit
  写入 prompt_metadata / trace / report
```

这部分不要推翻。Fusion 的变化是在这条链路上增加了 workflow-aware 的 prompt 形态，而不是换掉整个缓存模型。

对应的命名迁移是：

| Pico 原口径 | SkillForge Fusion 口径 |
| --- | --- |
| `pico/runtime.py` | `skillforge/runtime.py` |
| `pico/models.py` | `skillforge/models.py` |
| `ContextManager` 在 runtime 语境中讲解 | `skillforge/context_manager.py` 独立模块 |
| `Pico.ask()` | `SkillForge.ask()` |
| `Pico` | `SkillForge` |

## 3. 先分清两个 prefix

04 章最容易讲混的是“prefix”这个词。

Fusion 当前代码里，至少有两个相关但不同的概念。

第一个是 `PromptPrefix`。

这是 runtime 里真正有 hash 的稳定前缀对象：

```text
PromptPrefix(
  text=稳定前缀文本,
  hash=sha256(text),
  workspace_fingerprint=...,
  tool_signature=...,
  built_at=...
)
```

它由 `SkillForge.build_prefix()` 生成，里面主要包含：

* agent rules
* 当前可暴露工具清单
* 工具调用示例
* `WorkspaceContext.text()`

第二个是 `ContextManager` 里的 `prefix` section。

`ContextManager.build()` 最终会按 section 拼整段 prompt：

```text
prefix
memory
relevant_memory
history
current_request
```

但这里的 `prefix` section 不一定完全等于 `PromptPrefix.text`。Fusion 会把 checkpoint text 和 workflow task packet 作为 prefix extras 拼到这个 section 前面：

```text
checkpoint text
Workflow task packet:
  ...
PromptPrefix.text
```

所以修订文档必须讲清楚：

* `PromptPrefix.hash` 只对稳定前缀对象签名。
* `ContextManager` 的 `prefix` section 是最终 prompt 的第一段，可能包含动态 extras。
* `prompt_cache_key` 来自 `PromptPrefix.hash`，不是整段 prompt 的 hash。
* 真实 provider 能缓存多少 token，要看最终 prompt 的实际前缀是否稳定，以及后端返回的 `cached_tokens`。

这个区别非常关键。否则读者会误以为只要 `prompt_cache_key` 没变，真实 token cache 就一定高命中。

## 4. PromptPrefix 现在装了什么

Fusion 的 `build_prefix()` 仍然把稳定规则和工作区基线收成一块。

它大致包含：

```text
You are skillforge...

Rules:
- Use tools instead of guessing about the workspace.
- Return exactly one <tool>...</tool> or one <final>...</final>.
- Tool calls must look like ...
- Never invent tool results.
- Keep answers concise and concrete.
- Do not repeat the same tool call...
- Required tool arguments must not be empty...

Tools:
- read_file(...)
- search(...)
- patch_file(...)
...

Valid response examples:
<tool>...</tool>
<final>Done.</final>

WorkspaceContext.text()
```

与原 Pico 相比，这里的关键变化是工具清单不一定等于全部注册工具。

普通模式下，`prompt_tool_names()` 返回当前 agent 注册的全部工具。
workflow 模式下，`prompt_tool_names()` 会根据当前 phase 的 `allowed_tools` 收缩工具列表。

所以同一个 agent 在不同 workflow phase 里，`PromptPrefix.text` 可能不同：

* intake 阶段可能只列读取和搜索工具。
* implement 阶段可能列写文件、patch、run_shell。
* verify 阶段可能列 `log_run`、`log_brief`、`log_failure_detail`。
* audit 阶段又会收缩成只读检查工具。

这会直接影响 `tool_signature` 和 `prefix_hash`。

## 5. 前缀什么时候会重建

原 Pico 的前缀重建主要看 workspace fingerprint 和工具表面。

Fusion 仍然如此，但工具表面现在是 workflow-aware 的。

每轮 `_build_prompt_and_metadata(user_message)` 会先做：

```text
if workflow enabled:
  task_packet = _compile_workflow_task_packet(user_message)
  force_refresh = previous_tool_signature != prompt_tool_signature()

refresh_prefix(force=force_refresh)
```

这说明在 workflow 模式下，前缀重建有两类常见原因。

第一类是 workspace 变化。

例如：

* 分支变化
* git status 变化
* 最近 commit 变化
* README / AGENTS / pyproject / package 等工作区文档变化

这些会改变 `WorkspaceContext.fingerprint()`，因此需要重建 prefix。

第二类是可暴露工具变化。

例如 workflow 从 `implement` 进入 `verify`，当前 phase 允许的工具集合变了，`prompt_tool_signature()` 也会变。这时即使 workspace 没变，也会强制刷新 prefix。

所以修订后的表达应该是：

> Fusion 中 prefix 失效不只来自仓库现场变化，也来自当前 workflow phase 导致的可见工具表面变化。

## 6. TaskPacket 怎么进入 prompt

Fusion 新增的 TaskPacket 不是 `PromptPrefix` 的一部分，但会进入最终 prompt。

在 workflow 模式中，每轮构建 prompt 前会编译 TaskPacket：

```text
TaskPacketCompiler.compile(...)
  -> workflow state
  -> kernel state
  -> phase
  -> allowed_tools
  -> evidence_refs
  -> evidence_briefs
  -> active_skill_constraints
  -> prompt_context
```

然后 `ContextManager.build()` 会调用：

```text
agent.render_workflow_prompt_context()
```

把 TaskPacket 渲染成：

```text
Workflow task packet:
User intent: ...
Workflow: code_change
Phase: verify
Workflow status: running
Phase history: intake, plan_compile, implement
Budgets used: rounds 3/12, tools 8/40
Allowed tools:
- log_run
- log_brief
- log_failure_detail
Evidence briefs:
- ev-... (diff): patch_file changed ...
- ev-... (log): 1 failed in 0.23s
Active skills:
- skill-...
  step: ...
  verify: ...
```

这段内容是动态的。phase 会变，budget 会变，evidence 会变，active skill 也可能根据任务和路径匹配结果变化。

因此它不应该被理解成稳定 prefix。更准确的说法是：

> TaskPacket 是 workflow runtime 给模型的当前阶段任务合同；它位于最终 prompt 的前部，但语义上属于每轮动态上下文。

## 7. active skills 如何影响 prompt

Fusion 新增 verified skills 以后，prompt 可能会多出 active skill 约束。

流程是：

```text
SkillStore
  -> SkillMatcher.match(user_intent, workflow, paths)
  -> SkillCompiler.compile_for_task(...)
  -> TaskPacket.active_skill_constraints
  -> TaskPacket.prompt_context
  -> final prompt
```

这里要强调三条边界。

第一，只有 active skill 会进入 TaskPacket。candidate / quarantine skill 不会直接进入 prompt。

第二，active skill 进入 prompt 前要过安全检查。如果 skill 内容里包含 raw log、protected path 等危险 prompt 内容，会被拒绝。

第三，TaskPacket 只注入 skill 的约束性摘要，例如步骤和验证要求，不把完整 trace、raw log、source dump 直接塞进去。

这部分是原 Pico 04 章没有的，需要在 Fusion 修订中补上。否则读者会不知道“经验沉淀”到底是怎么影响下一次 prompt 的。

## 8. Evidence briefs 如何影响 prompt

Fusion 把工具、日志、diff、verification、audit、handoff 等结果写进 EvidenceStore。TaskPacket 编译时会读取当前 run 的 evidence records，并渲染成 evidence briefs。

这和 raw log 进入 prompt 完全不同。

正确流程是：

```text
raw log
  -> 落盘到 EvidenceStore
  -> evidence record
  -> brief / parsed summary / failure detail
  -> TaskPacket evidence_briefs
  -> prompt_context
```

错误理解是：

```text
raw log
  -> 直接塞进 prompt
```

Fusion 选择前一种方式，是为了保留复盘能力，同时控制 prompt 预算和安全风险。

04 章修订时要明确：

* raw log 不直接进入 prompt。
* prompt 里放的是 evidence brief。
* 需要失败细节时，通过 `log_failure_detail` 按 evidence id 获取。
* 不可解析 log 不应被当作验证通过。

## 9. ContextManager 的预算策略

原 Pico 04 章讲 stable prefix 和 cache，06 章会讲上下文瘦身。Fusion 版 04 至少要提前点一下预算，因为缓存和 section 形态已经绑定在一起。

当前 `ContextManager` 的默认 section 顺序是：

```text
prefix
memory
relevant_memory
history
current_request
```

默认总预算是：

```text
DEFAULT_TOTAL_BUDGET = 12000
```

默认 section budget 是：

| section | 默认预算 |
| --- | ---: |
| `prefix` | 3600 |
| `memory` | 1600 |
| `relevant_memory` | 1200 |
| `history` | 5200 |
| `current_request` | 不裁剪 |

如果超预算，压缩顺序是：

```text
relevant_memory -> history -> memory -> prefix
```

也就是说，系统会优先牺牲相关记忆和历史，最后才动 prefix。当前用户请求永远不裁剪。

这点和 cache 有关系：如果 prefix section 被压缩，最终 prompt 的开头稳定性会变差，真实 provider cache 也可能受影响。

## 10. 缓存链路现在怎么走

Fusion 的模型适配层仍然保留原 Pico 的 prompt cache 传递方式。

在 runtime 中：

```text
prompt_cache_key = prompt_metadata["prompt_cache_key"]
prompt_cache_retention = "in_memory"
model_client.complete(prompt, ..., prompt_cache_key, prompt_cache_retention)
```

在 OpenAI-compatible client 中：

```text
if supports_prompt_cache and prompt_cache_key:
  payload["prompt_cache_key"] = prompt_cache_key

if supports_prompt_cache and prompt_cache_retention:
  payload["prompt_cache_retention"] = prompt_cache_retention
```

当前只在明确支持这套语义的 OpenAI-compatible 后端上打开：

```text
supports_prompt_cache = base_url contains "openai.com" or "right.codes"
```

Ollama 不启用这条缓存语义。

模型返回后，client 会从 usage 里抽：

* `input_tokens`
* `output_tokens`
* `total_tokens`
* `cached_tokens`
* `cache_hit`

这些 metadata 会回流到 runtime，最后进入 trace 和 report。

## 11. prefix_hash 和真实 cache 命中不是一回事

这点是 04 章修订里最应该讲清楚的。

`prefix_hash` 是本地 runtime 对 `PromptPrefix.text` 算出来的稳定签名。它能回答：

```text
这份稳定前缀对象和上一轮是不是同一份？
```

但 provider 的真实缓存命中要看后端怎么识别请求文本、缓存 key 和 token 前缀。它最终由返回的 `cached_tokens` 证明。

因此要区分三个层次：

| 层次 | 含义 |
| --- | --- |
| `prefix_hash` 没变 | 本地稳定前缀对象没变 |
| `prompt_cache_key` 一样 | runtime 向 provider 传了同一个缓存 key |
| `cached_tokens > 0` | provider 实际报告有 token 被缓存复用 |

在普通路径里，prefix 一般更稳定，cache 命中更容易解释。

在 workflow 路径里，以下因素都会让最终 prompt 更动态：

* TaskPacket 每轮变化。
* phase 改变会让 allowed tools 改变。
* allowed tools 改变会让 `prompt_tool_signature()` 改变。
* evidence briefs 会随工具执行不断增加。
* active skills 可能随任务、路径和 skill store 状态变化。
* checkpoint text 可能随恢复状态变化。

所以不能只看 `prefix_hash` 判断缓存效果，必须结合 `cached_tokens` 观测真实命中。

## 14. 不要过度宣称的地方

写 04 章时要避免这些说法：

* 不要说 provider cache 一定按 `prefix_hash` 高命中。`prefix_hash` 是本地 key，真实命中要看 `cached_tokens`。
* 不要说 workflow 的 TaskPacket 是稳定 prefix。它在最终 prompt 前部，但语义上是动态任务合同。
* 不要说 raw log 进入 prompt。prompt 只接收 brief / detail / evidence id 这类受控内容。
* 不要说所有 provider 都支持 prompt cache。Ollama 当前不启用，OpenAI-compatible 也只对特定 base URL 打开。
* 不要说 prefix 已经拆成多个可独立缓存子块。当前仍是一个 `PromptPrefix.text` 对象。
* 不要说 `prompt_cache_retention` 已经是策略化配置。当前模型调用里仍使用 `"in_memory"`。

## 15. 建议放入修订版的讲解段

可以把 04 章开头改成下面这种口径：

> SkillForge 仍然沿用 Pico 的稳定前缀设计：系统规则、工具说明、调用示例和工作区基线会被收成 `PromptPrefix`，并带有 `hash`、`workspace_fingerprint` 和 `tool_signature`。每轮请求前，runtime 会检查工作区指纹和工具签名；如果它们没变，就复用前缀；如果仓库现场或当前可见工具表面变化，就重建前缀。

中段可以补：

> Fusion 新增的 workflow 不会简单塞进系统提示词。它会在每轮模型调用前编译 TaskPacket，把当前 phase、allowed tools、budget、evidence briefs 和 active skill constraints 渲染成动态 prompt context。这个任务包会出现在最终 prompt 的前部，但它不是稳定 `PromptPrefix` 的一部分，因此会影响真实缓存命中的观测。

缓存部分可以写：

> `prompt_cache_key` 仍然来自 `PromptPrefix.hash`，但它只是本地 runtime 对稳定前缀的签名。最终 prompt 中还可能含有 checkpoint、TaskPacket 和 evidence brief 等动态内容，所以真实缓存是否命中，要以后端返回的 `cached_tokens` 和 `cache_hit` 为准。也就是说，prefix 复用率和 provider cache 命中率相关，但不能画等号。

结尾可以强调：

> Fusion 版 04 章的重点，不是说 prompt 变得更长了，而是说 prompt 变得更有结构了：稳定规则和工作区基线继续复用，动态任务合同按轮编译，日志和验证只以 evidence brief 的形式进入上下文，最终缓存效果通过 provider usage 元数据被审计。
