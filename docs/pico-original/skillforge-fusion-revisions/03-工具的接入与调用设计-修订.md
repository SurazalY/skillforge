# 03-工具的接入与调用设计-修订

## 1. 修订结论

这一章需要修订，而且修订幅度比 01 章明显更大。

原 Pico 03 章的核心判断仍然成立：模型不能直接碰外部世界，所有工具动作都必须经过统一的 `run_tool()` 网关。这个网关负责检查工具是否存在、参数是否合法、路径是否越界、是否重复调用、是否需要审批、执行前后工作区有没有变化。

SkillForge Pico Fusion 没有推翻这条安全主线。它是在原来的工具网关上又加了三层控制：

* workflow / TaskPacket 会限制当前阶段能看到和调用哪些工具。
* `log_run` / `log_brief` / `log_failure_detail` 把测试日志变成 evidence，而不是把 raw log 全塞进 prompt。
* 工具执行结果会在 active run 中进入 EvidenceStore；workflow 路径下，completion gate、audit、handoff 还会继续依赖这些结构化证据。

一句话版本：

> 原 Pico 03 章讲的是“工具调用必须过安全网关”；Fusion 版 03 章还要补上“工具调用必须符合当前阶段合同，并把关键结果沉淀为可验证证据”。

## 2. 原章应保留的主线

原章里最重要的内容仍然要保留：

```text
model output
  -> parse <tool>
  -> run_tool(name, args)
  -> tool registry lookup
  -> validate_tool()
  -> repeated-call guard
  -> approval / read_only guard
  -> workspace snapshot before execution
  -> execute actual tool
  -> workspace snapshot after execution
  -> status / affected_paths / diff_summary
  -> tool result returned to model
```

这些机制在 Fusion 中仍然存在，只是名字和落盘目录变了：

| Pico 原口径 | SkillForge Fusion 口径 |
| --- | --- |
| `pico/tools.py` | `skillforge/tools.py` |
| `Pico.run_tool()` | `SkillForge.run_tool()` |
| `.pico/runs/<run_id>/` | `.skillforge/runs/<run_id>/` |
| `Pico` 子 agent | `SkillForge` 子 agent |
| trace / report | trace / report / evidence |

03 章不要改成“Fusion 重新实现了一套工具系统”。更准确的写法是：

> Fusion 沿用了 Pico 的工具网关，把它扩展成 workflow-aware、evidence-aware 的执行边界。

## 3. 工具调用发生在 ask() 的哪个位置

工具调用不是启动时发生的，也不是构建 workspace context 时发生的。它发生在 `SkillForge.ask()` 主循环内部。

一次普通工具调用的顺序是：

```text
用户输入
  -> SkillForge.ask()
  -> 构建本轮 prompt
  -> 模型返回文本
  -> parse() 解析出 <tool>
  -> run_tool(name, args)
  -> 把工具结果作为 tool message 记入 history
  -> 下一轮重新构建 prompt
```

所以 01 章和 03 章讲的是两个不同时间点：

* 01 章的 workspace context 是 agent 启动和 prompt 构建时用来理解仓库现场的输入。
* 03 章的 tool boundary 是模型已经做出行动选择之后，系统真正执行行动之前的闸门。

在 Fusion 里，这个闸门还会读当前 workflow phase 和 TaskPacket。也就是说，工具是否能执行，不只看“工具本身是否合法”，还看“当前阶段是否允许它”。

## 4. 工具注册表的变化

原 Pico 的基础工具主要是这些：

| 工具 | 风险 | 作用 |
| --- | --- | --- |
| `list_files` | 低 | 列出工作区文件 |
| `read_file` | 低 | 按行读取文件 |
| `search` | 低 | 搜索文本 |
| `run_shell` | 高 | 在 repo root 执行 shell 命令 |
| `write_file` | 高 | 写入文本文件 |
| `patch_file` | 高 | 用精确 old_text 替换一次 |
| `delegate` | 低但受限 | 启动只读子 agent 调查 |

Fusion 保留这些工具，并新增三类日志证据工具：

| 工具 | 风险 | 作用 | prompt 边界 |
| --- | --- | --- | --- |
| `log_run` | 高 | 执行命令，把 raw log 落成 evidence，并返回 evidence id 和摘要 | raw log 不直接进入 prompt |
| `log_brief` | 低 | 按预算读取某条 log evidence 的摘要 | 只返回短摘要 |
| `log_failure_detail` | 低 | 读取某个 pytest failure 的断言、位置和栈 | 只返回结构化失败细节 |

这里最容易误解的是 `log_run`。

`log_run` 看起来像 `run_shell` 的变体，但它的设计目标不同：

* `run_shell` 是通用命令执行工具，返回裁剪后的 stdout / stderr / exit_code。
* `log_run` 是验证证据工具，它会把完整 raw log 写到 `.skillforge/runs/<run_id>/evidence/log/`，再创建一条 log evidence record。

因此 `log_run` 的重点不是“把命令输出给模型看”，而是“把验证过程变成可复盘证据”。模型下一步如果需要理解结果，应该通过 `log_brief` 或 `log_failure_detail` 取摘要和失败细节。

## 5. Fusion 新增的第一层边界：阶段允许工具

原 Pico 的工具边界主要是静态注册表：

```text
只要工具在 registry 里，并且参数、审批、路径都通过，就可以执行。
```

Fusion 在 workflow 模式下多了一层动态边界：

```text
工具必须在 registry 里
  并且必须属于当前 workflow phase 的 allowed_tools
```

这层边界会影响两个地方。

第一，影响 prompt 里暴露给模型的工具列表。

普通模式下，prefix 会列出当前 agent 注册的全部工具。workflow 模式下，`prompt_tool_names()` 会根据 `current_allowed_tool_names()` 收缩工具列表。模型在 intake / investigate / audit 等不同阶段看到的工具是不一样的。

第二，影响真正执行。

即使模型想办法输出了一个当前阶段不允许的工具，`run_tool()` 也会再次检查。如果不允许，会直接返回类似这样的错误：

```text
error: tool log_run is not allowed in workflow repo_audit phase investigate
```

这点很关键：工具限制不是只靠提示词自觉，而是在执行层 fail-closed。

## 6. 常见 workflow 阶段里的工具变化

以 `code_change` 类型 workflow 为例，可以这样理解工具开放节奏：

| 阶段 | 主要目标 | 典型允许工具 |
| --- | --- | --- |
| `intake` | 读需求、看文件、理解现场 | `list_files`、`read_file`、`search` |
| `plan_compile` | 形成计划，必要时只读调查 | `list_files`、`read_file`、`search`、`delegate` |
| `implement` | 真正修改代码 | `read_file`、`search`、`write_file`、`patch_file`、`run_shell` 等 |
| `verify` | 运行验证并收集证据 | `run_shell`、`log_run`、`log_brief`、`log_failure_detail` |
| `audit` | 审计证据和改动 | `list_files`、`read_file`、`search`、`log_brief`、`log_failure_detail` |
| `skill_distill` | 从通过验证的流程中沉淀候选 skill | 与 workflow 设定相关 |
| `handoff` | 汇总交接 | 主要依赖已有 evidence |

这个表不是说所有 workflow 都一样。`repo_audit` 这种只读 workflow 本身就不应该暴露 `write_file`、`patch_file`、`run_shell`、`log_run` 这类会改变现场或执行命令的工具。

真正的规则来自 workflow IR 和当前 phase 的 `allowed_tools`。文档里可以用上表帮助理解，但不要把它写成唯一硬编码流程。

## 7. run_tool() 的完整护栏链

Fusion 版 `run_tool()` 可以分成八步理解。

### 7.1 检查工具是否存在

如果工具名不在当前 agent 的 `self.tools` 中，直接拒绝：

```text
error: unknown tool '<name>'
```

同时记录 metadata：

* `tool_status = rejected`
* `tool_error_code = unknown_tool`
* `risk_level = high`
* `workspace_changed = false`

这一步防止模型编造工具名，比如输出一个系统根本没有注册过的 `delete_project`。

### 7.2 检查 workflow phase 是否允许

如果当前启用了 workflow，`run_tool()` 会编译或读取当前 TaskPacket，然后检查工具是否在 `allowed_tools` 内。

拒绝时会记录：

* `tool_status = rejected`
* `tool_error_code = workflow_tool_not_allowed`
* `security_event_type = workflow_tool_not_allowed`
* `workspace_changed = false`

这一步是 Fusion 相对 Pico 的核心新增边界。

### 7.3 参数校验

接着进入 `validate_tool()`。

不同工具有不同校验：

* `list_files` 要求 path 是目录。
* `read_file` 要求 path 是文件，且 line range 合法。
* `search` 要求 pattern 非空。
* `run_shell` 要求 command 非空，timeout 在允许范围内。
* `write_file` 要求 path 和 content 合法。
* `patch_file` 要求 `old_text` 非空，且目标文件里刚好出现一次。
* `log_brief` / `log_failure_detail` 要求 evidence id、max chars、failure index 等参数合法。
* `delegate` 要求 task 非空，且不能超过 delegate 深度限制。

其中路径相关工具都会经过 `agent.path()`，它会把相对路径解析到工作区内，并拒绝逃逸出 workspace 的路径。

### 7.4 重复调用保护

如果最近两次 tool message 的工具名和参数都与当前调用完全一致，系统会拒绝第三次重复调用：

```text
error: repeated identical tool call for <name>; choose a different tool or return a final answer
```

这不是为了限制模型正常探索，而是防止一种常见坏循环：模型拿不到新信息，却反复调用同一个工具，消耗步骤和 token。

### 7.5 审批与只读保护

高风险工具会经过 `approve()`。

在普通可写模式里，approval policy 可以是 ask / auto / never 等策略。
在 read-only 子 agent 或 audit 子 agent 里，高风险工具会被挡住。

所以风险判断分两层：

* 工具定义里的 `risky` 决定它是否需要审批。
* 当前 agent 的 `read_only`、workflow phase、delegate whitelist 决定它是否有机会通过审批。

### 7.6 执行前快照

对高风险工具，系统会在执行前捕获 workspace snapshot。

这样做不是为了阻止变化，而是为了知道变化发生在哪里。执行后系统会再捕获一次 snapshot，然后比较：

* 哪些路径被影响。
* 工作区是否真的发生变化。
* diff summary 是什么。

### 7.7 真正执行工具

只有前面的检查都通过，才会进入实际工具函数。

例如：

* `tool_read_file()` 读取文件并裁剪输出。
* `tool_patch_file()` 做一次精确替换。
* `tool_run_shell()` 用受限环境执行命令。
* `tool_log_run()` 执行命令，把 raw log 写入 EvidenceStore。
* `tool_delegate()` 启动只读子 agent。

这一步是模型意图真正接触外部世界的地方，所以它必须位于所有边界之后。

### 7.8 执行后分析与返回

执行成功后，系统会生成工具 metadata：

* `tool_status`
* `tool_error_code`
* `risk_level`
* `read_only`
* `affected_paths`
* `workspace_changed`
* `workspace_fingerprint`
* `diff_summary`

如果工具执行失败，但工作区已经发生变化，状态会标成 `partial_success`。这比简单说 error 更准确，因为它提醒后续流程：虽然工具失败了，但现场已经变了，需要审计。

最后工具结果会被裁剪后返回给模型，并作为 tool message 写入 history。下一轮 prompt 会带上这条结果。

## 8. EvidenceStore 如何接入工具层

Fusion 版 03 章要补清楚：在一次 active run 里，工具结果不只是“返回一段字符串”，还会变成证据。

每次工具执行后，runtime 会根据 `_last_tool_result_metadata` 生成 tool evidence：

```text
tool evidence
  - tool_name
  - status
  - error code
  - risk level
  - read_only
  - args
  - affected_paths
  - workspace_changed
  - diff_summary
  - run_id / task_id
  - workflow / phase
  - related_evidence_ids
```

如果工具导致工作区变化，还会生成 diff evidence。

如果当前处于 workflow 的 `verify` phase，并且调用的是 `log_run`，系统会尝试把 log evidence 转成 verification evidence。只有可解析的验证结果才适合进入 completion gate。

这就是 Fusion 和原 Pico 最大的语义差异之一：

```text
Pico:
  工具结果主要服务于下一轮模型决策和 trace/report 复盘。

Fusion:
  工具结果同时服务于下一轮模型决策、trace/report 复盘和 EvidenceStore；在 workflow 路径中，它还会继续服务于 completion gate、audit 和 handoff。
```

## 9. log_run 为什么不把 raw log 放进 prompt

测试日志通常很长，而且包含大量对当前决策没有帮助的噪音：

* 完整 traceback
* 临时路径
* 环境输出
* pytest 插件信息
* 重复失败块
* 与当前修复无关的上下文

如果把 raw log 直接塞进 prompt，会有几个问题：

* prompt 预算很快被吃掉。
* 重要规则和当前请求会被挤到后面。
* 模型可能抓住无关路径或环境细节误判。
* raw log 可能包含不该进入 prompt 的敏感信息。

Fusion 的处理方式是：

```text
log_run:
  raw log -> 落盘
  parsed summary -> evidence payload
  evidence_id + status + summary -> 返回给模型

log_brief:
  evidence_id -> 短摘要

log_failure_detail:
  evidence_id + failure_id / failure_index -> 单个失败细节
```

这样既保留了完整复盘能力，又避免 prompt 被日志污染。

这里要特别注意一个边界：不可解析的 log 不能被当成通过验证。

比如一个非 pytest 命令，或者 pytest 输出缺少可解析 summary，`log_run` 会生成 `status = unparsed` 的 raw log evidence。它可以用于复盘，但不能直接作为“测试通过”的 completion evidence。

## 10. delegate 的修订点

原 Pico 里 `delegate` 已经是一个受限工具：

* 子 agent 是 read-only。
* approval policy 是 `never`。
* max steps 更小。
* depth 超过上限后不再暴露 delegate。
* 子 agent 只返回调查结论，不替父 agent 执行修改。

Fusion 保留这些限制，并新增 workflow 继承逻辑。

当父 agent 处在 workflow 中时，delegate 子 agent 会继承或编译当前 TaskPacket：

```text
parent workflow phase
  -> delegated TaskPacket
  -> child SkillForge
  -> read_only = true
  -> approval_policy = never
  -> workflow phase locked
```

如果当前 phase 是 `audit`，还会套上 audit 子 agent 的工具白名单。审计子 agent 只能使用：

```text
list_files
read_file
search
log_brief
log_failure_detail
```

它不能调用：

```text
write_file
patch_file
run_shell
log_run
promote
delegate
```

这里的设计目标是：审计者只能检查现场和证据，不能修改现场，也不能自己制造新的验证日志来改变被审计对象。

## 11. prefix 和工具边界会怎么动态变化

03 章也应该补一点 prompt 动态变化，因为工具边界会直接影响 prefix。

在普通模式下，`build_prefix()` 会把当前 agent 注册的工具都列进去。

在 workflow 模式下，`build_prefix()` 只会列出当前 phase 允许的工具。比如 investigate 阶段可能只看到读取和搜索工具；implement 阶段才看到写入工具；verify 阶段才看到 `log_run`。

所以工具边界变化会带来两个结果：

1. 模型看到的工具说明会变。
2. tool signature 会变，可能触发 prefix 刷新。

这不是 bug，而是安全边界的一部分：当系统进入不同阶段时，模型不应该继续看到上一阶段才允许的工具。

不过文档里不要把这件事写成“所有 prompt 都完全重建且缓存全部失效”。更准确的说法是：

* 本地 prefix hash 会因为工具列表变化而变化。
* provider 侧 prompt cache 是否还能命中，取决于前缀里有多少 token 仍保持完全相同。
* Fusion 当前更关心边界正确性，而不是把所有动态内容都优化到最有利于缓存的位置。

## 12. 和 02 章的关系

02 章讲的是 `ask()` 主循环如何转起来：

```text
构建 prompt -> 请求模型 -> 解析输出 -> 执行工具 / final / retry -> 更新状态
```

03 章只展开其中的“执行工具”这一段：

```text
parse 出 tool
  -> run_tool()
  -> 检查工具边界
  -> 执行
  -> 记录结果和证据
  -> 返回给下一轮模型
```

所以二者不是重复关系。可以这样分工：

* 02 章负责解释“大循环怎么走”。
* 03 章负责解释“模型一旦想做动作，系统怎么把动作关进边界里”。

## 14. 不要过度宣称的地方

写 03 章时要避免这些说法：

* 不要说 Fusion 已经实现标准 MCP server。当前 `log_run` 等工具更准确地说是 MCP-like 的本地工具能力。
* 不要说 raw log 会进入 prompt。实际设计是 raw log 落盘，prompt 只拿摘要或失败细节。
* 不要说不可解析日志也能作为验证通过。unparsed log 只能复盘，不能直接当 pass。
* 不要说 audit subagent 可以执行验证或修复。audit 子 agent 是只读检查者。
* 不要说 workflow phase gate 覆盖所有普通非 workflow 路径。普通路径仍保留 Pico 式工具网关；phase 工具限制主要发生在启用 workflow 的路径里。
* 不要说系统拥有完整 OS 级沙箱。当前边界主要来自路径守卫、审批策略、只读 delegate、phase 白名单、环境变量 allowlist、输出裁剪和 evidence 审计。

## 15. 建议放入修订版的讲解段

可以把 03 章开头改成下面这种口径：

> 工具层是 agent 从“会说话”进入“会行动”的边界。模型可以在输出里提出工具调用，但它不能直接执行工具。所有工具请求都会进入 `SkillForge.run_tool()`，由 runtime 统一检查工具是否注册、参数是否合法、当前 workflow phase 是否允许、是否重复调用、是否需要审批、路径是否仍在 workspace 内。只有这些检查全部通过，底层工具函数才会真正运行。

中段可以补上：

> 在 Fusion 中，工具边界不再只是静态白名单。workflow 会为每个 phase 编译 TaskPacket，TaskPacket 中的 `allowed_tools` 会同时影响 prompt 中暴露的工具列表和 `run_tool()` 的执行检查。因此模型在不同阶段看到的行动空间不同：理解阶段偏读取，实施阶段才允许写入，验证阶段才暴露日志证据工具，审计阶段重新收缩为只读检查工具。

日志部分可以写：

> `log_run` 的目的不是把完整命令输出塞回模型，而是把验证过程落成证据。它会执行命令、保存 raw log、解析 pytest summary 和失败细节，并返回 evidence id。后续模型若需要概要，使用 `log_brief`；若需要定位单个失败，使用 `log_failure_detail`。这种设计让系统既保留完整审计材料，又避免 raw log 污染 prompt。

结尾可以强调：

> 所以 Fusion 版工具层的核心不是“工具更多了”，而是“动作更可控了”。工具调用不仅要通过传统安全检查，还要符合当前阶段合同；工具结果不仅反馈给模型，还会进入 evidence 链，成为验证、审计和交接的依据。
