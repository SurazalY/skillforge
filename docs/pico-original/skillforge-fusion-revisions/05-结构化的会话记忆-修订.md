# 05-结构化的会话记忆-修订

## 1. 修订结论

这一章需要修订，但不是推翻重写。

原 Pico 05 章讲的轻量工作记忆仍然是 SkillForge Pico Fusion 的底座：`task_summary`、`recent_files`、`file_summaries`、`episodic_notes` 仍然存在，freshness 校验也仍然用于防止过期文件摘要继续进入 prompt。

Fusion 在这层上主要新增了四件事：

* `.skillforge/memory/` 下的 `DurableMemoryStore`，用于保存长期主题记忆。
* 工具失败、部分成功、被拒绝时，会生成 `process` 类型的过程笔记。
* workflow 的 TaskPacket 会利用 `recent_files` 作为路径信号，参与 active skill 匹配。
* 记忆层需要和 EvidenceStore、SkillStore 区分边界，不能把三者混成一个“大记忆系统”。

一句话版本：

> Pico 05 章讲的是轻量 working memory 如何减少重复读取；Fusion 版 05 章还要补上 durable memory、过程笔记、workflow/skills 对记忆的读取，以及它和 evidence/skills 的边界。

## 2. 原章应保留的主线

原 Pico 的四层工作记忆仍然成立：

| 层 | 作用 | 是否保留 |
| --- | --- | --- |
| `working.task_summary` | 当前任务短摘要 | 保留 |
| `working.recent_files` | 最近接触文件 | 保留 |
| `file_summaries` | 文件短摘要和 freshness | 保留 |
| `episodic_notes` | 跨轮短笔记和相关召回 | 保留 |

原来的工具回写链路也保留：

```text
read_file
  -> remember_file(path)
  -> summarize_read_result(result)
  -> set_file_summary(path, summary)
  -> append_note(summary, tags=(path,), source=path)

write_file / patch_file
  -> remember_file(path)
  -> invalidate_file_summary(path)
```

这条链路仍然是 05 章最重要的骨架。修订时不要写成“Fusion 换成了新的记忆系统”。更准确的说法是：

> Fusion 保留 Pico 的轻量 working memory，并在其旁边增加 durable memory、workflow skill 匹配和 evidence/skill 边界。

## 3. 命名和路径迁移

本章最基础的修订是命名迁移：

| Pico 原口径 | SkillForge Fusion 口径 |
| --- | --- |
| `pico/memory.py` | `skillforge/memory.py` |
| `Pico.memory` | `SkillForge.memory` |
| `.pico/memory/` | `.skillforge/memory/` |
| `.pico/sessions/` | `.skillforge/sessions/` |
| `Pico.ask()` | `SkillForge.ask()` |

但注意：`.skillforge/memory/` 不是普通 session memory 的唯一位置。

Fusion 里有两类不同记忆：

```text
session memory
  -> 保存在 session JSON 里
  -> task_summary / recent_files / file_summaries / episodic_notes

durable memory
  -> 保存在 .skillforge/memory/
  -> MEMORY.md / topics/*.md
```

这两类都会影响下一轮 prompt，但生命周期不同。

## 4. 记忆数据结构现在长什么样

`default_memory_state()` 仍然很小：

```text
{
  "working": {
    "task_summary": "",
    "recent_files": [],
  },
  "episodic_notes": [],
  "file_summaries": {},
  "task": "",
  "files": [],
  "notes": [],
  "next_note_index": 0,
}
```

其中 `task`、`files`、`notes` 更像兼容字段，会同步到当前结构：

* `task` 对应 `working.task_summary`
* `files` 对应 `working.recent_files`
* `notes` 对应 `episodic_notes` 的文本列表

Fusion 额外会在规范化时补一个派生字段：

```text
durable_topics
```

它来自 `.skillforge/memory/MEMORY.md` 中的主题索引，用来告诉 prompt 当前有哪些长期主题可被召回。

因此 05 章修订时可以这样讲：

> working memory 仍然是 session 内的小状态；durable memory 不是直接塞进 session，而是通过 `.skillforge/memory/` 维护主题索引，并在渲染和召回时被读入。

## 5. Working Memory 四层职责

### 5.1 `task_summary`

每次 `SkillForge.ask(user_message)` 开始时，runtime 仍然会调用：

```text
self.memory.set_task_summary(user_message)
```

它会把用户请求裁剪到 300 字符以内，作为本轮任务锚点。

这层不是完整任务计划，也不是 workflow state。它只是让模型在 history 被裁剪后，仍然知道“这一轮大概在做什么”。

workflow 的 phase、budget、completion requirements 不存在这里，而是在 WorkflowKernel / TaskPacket 里。

### 5.2 `recent_files`

`recent_files` 仍然记录最近接触过的文件，去重并保留最近 8 个：

```text
WORKING_FILE_LIMIT = 8
```

这层原来主要给下一轮 prompt 看，减少模型反复猜文件。

Fusion 中它还有一个新用途：作为 active skill 匹配的路径信号。

workflow 编译 TaskPacket 时会读取：

```text
self.memory.to_dict()["working"]["recent_files"]
```

并把它传给 SkillMatcher。SkillMatcher 会用 active skill 的 `file_patterns` 和这些路径做匹配，从而决定是否把某个 active skill 的约束编入 TaskPacket。

所以 `recent_files` 现在不仅是“记住刚碰过哪些文件”，也会影响“哪些经验规则可能与当前任务相关”。

### 5.3 `file_summaries`

`file_summaries` 仍然是工作记忆里最实用的一层。

`read_file` 的完整结果不会原样进入 memory，而是先压缩：

```text
summary = summarize_read_result(result)
set_file_summary(path, summary)
```

每条摘要会带：

```text
summary
created_at
freshness
```

这里的 `freshness` 是文件内容的 SHA-256。每次渲染 memory 时，会重新计算当前文件 freshness。只有摘要 freshness 和当前文件 freshness 相等，才会展示给模型。

如果文件被 `write_file` 或 `patch_file` 改过，runtime 会主动调用：

```text
invalidate_file_summary(path)
```

这点和原章完全一致，应该继续保留。

### 5.4 `episodic_notes`

`episodic_notes` 仍然保存短笔记，数量上限是：

```text
EPISODIC_NOTE_LIMIT = 12
```

每条 note 包含：

```text
text
tags
source
created_at
note_index
kind
```

原 Pico 主要用 `kind = episodic`。Fusion 里还会出现 `kind = process`，用于记录工具失败、部分成功或被拒绝这类过程性提醒。

召回仍然是轻量规则，不是向量检索：

```text
tag overlap
keyword overlap
recency
note_index
```

这套规则继续服务于 `relevant_memory` section，默认召回 top 3。

## 6. DurableMemoryStore 新增了什么

Fusion 新增 `DurableMemoryStore`，路径是：

```text
.skillforge/memory/
  MEMORY.md
  topics/
    project-conventions.md
    key-decisions.md
    dependency-facts.md
    user-preferences.md
```

它的目标不是把所有 session 记忆永久化，而是保存少数长期稳定事实。

默认 topic 有四类：

| topic | 作用 |
| --- | --- |
| `project-conventions` | 项目约定 |
| `key-decisions` | 关键决策 |
| `dependency-facts` | 依赖和环境事实 |
| `user-preferences` | 用户偏好 |

长期记忆不会自动把所有 final answer 都塞进去。只有当用户请求里出现明确的持久化意图，例如：

```text
remember / save / persist / note
记住 / 保存 / 记录 / 沉淀 / 长期记忆 / 持久记忆
```

并且 final answer 中出现符合格式的行，才会抽取：

```text
Project convention: ...
Decision: ...
Dependency: ...
Preference: ...

项目约定：...
决策：...
依赖：...
偏好：...
```

然后写入对应 topic。

这说明 durable memory 是受控沉淀，不是自动总结。

## 7. Durable memory 的安全边界

长期记忆比 working memory 更危险，因为它会跨 session 持续影响未来 prompt。

Fusion 因此在持久化前做了拒绝规则：

* 空文本不写入。
* 包含 redacted 值不写入。
* 看起来像 secret、token、password、API key 的内容不写入。
* 像 checkpoint / current phase / key files / freshness 这种瞬时任务状态不写入。
* stdout / stderr / traceback / exit_code 等噪音输出不写入。
* 超长文本不写入。

这层边界很重要。05 章不能把 durable memory 写成“更强的自动记忆”。准确说法是：

> durable memory 只保存用户明确要求长期保留、且通过安全过滤的稳定事实。

## 8. Process Note：工具失败也会进记忆

Fusion 里 `record_process_note_for_tool()` 会把一些工具异常结果写成过程笔记。

触发条件包括：

* `partial_success`
* `error`
* `rejected`

生成的 note 类似：

```text
patch_file partial_success on src/app.py; inspect diff before retry
run_shell error on workspace; check the failure before retry
log_run rejected; choose a different action before retry
```

这些 note 的 `kind` 是：

```text
process
```

它们的作用不是保存长期知识，而是避免下一轮继续盲目重复同一个失败动作。

这和 03 章的工具边界是连着的：

```text
run_tool()
  -> rejected / error / partial_success
  -> record_process_note_for_tool()
  -> episodic_notes(kind=process)
  -> relevant_memory 可能召回
```

所以 05 章修订时要补一句：

> Fusion 的记忆不仅记录读过什么，也会记录“刚才哪类动作失败了，下一步应该换策略”。

## 9. 记忆如何进入 prompt

这部分和 04 章衔接。

`ContextManager.build(user_message)` 会把记忆分成两段：

```text
memory
relevant_memory
```

`memory` 来自：

```text
self.memory.render_memory_text()
```

渲染出来的是一个小仪表盘：

```text
Memory:
- task: ...
- recent_files: ...
- file_summaries:
  - path: summary
- episodic_notes: 3
- durable_topics: project-conventions, key-decisions
```

这里不会展开所有 episodic note，也不会展开 durable topic 全文。

`relevant_memory` 来自：

```text
self.memory.retrieval_candidates(user_message, limit=3)
```

它会同时从两处召回：

* session 内的 `episodic_notes`
* `.skillforge/memory/topics/*.md` 里的 durable notes

metadata 里还会记录：

* selected_count
* selected_notes
* selected_sources
* selected_kinds
* selected_durable_count

所以 Fusion 版记忆有两种进入 prompt 的方式：

| section | 内容 | 特点 |
| --- | --- | --- |
| `memory` | 任务、最近文件、仍新鲜的文件摘要、笔记数量、durable topic 列表 | 稳定仪表盘 |
| `relevant_memory` | 当前请求召回的 episodic/durable notes | 按需展开 |

## 10. 记忆和 workflow / TaskPacket 的关系

Fusion 的 workflow 不直接替代 memory。

二者分工是：

| 模块 | 负责什么 |
| --- | --- |
| memory | 当前任务摘要、最近文件、文件摘要、短笔记、长期主题 |
| WorkflowKernel | 当前 phase、round/tool budget、状态推进 |
| TaskPacket | 当前阶段任务合同、allowed tools、evidence briefs、active skill constraints |

它们之间有几条连接：

1. `task_summary` 可作为当前任务描述的 fallback。
2. `recent_files` 会进入 `_workflow_paths()`，作为 SkillMatcher 的路径信号。
3. durable / episodic notes 可通过 `relevant_memory` 给模型补充上下文。
4. TaskPacket 会进入 prompt 前部，但它不是 memory 的一部分。

所以不能说“Fusion 把 workflow 状态存进 memory”。更准确的是：

> memory 给 workflow 提供任务和路径上下文；workflow 自己的 phase、budget 和 evidence 状态仍由 WorkflowKernel / TaskPacket 管理。

## 11. 记忆和 EvidenceStore 的边界

Fusion 新增 EvidenceStore 后，05 章容易和 03/07 章混。

要明确：

| 内容 | 应放在哪里 |
| --- | --- |
| 最近读过哪个文件 | memory |
| 某个文件的短摘要 | memory |
| 工具失败后的下一步提醒 | memory process note |
| raw test log | EvidenceStore |
| verification pass/fail evidence | EvidenceStore |
| diff evidence | EvidenceStore |
| audit report evidence | EvidenceStore / audit artifact |

raw log 不应该进入 memory。traceback、stdout、stderr 这类长输出也不应该沉淀成 durable memory。

如果模型需要日志摘要，应该通过 evidence brief、`log_brief` 或 `log_failure_detail` 获取，而不是依赖 memory 保存完整日志。

## 12. 记忆和 SkillStore 的边界

SkillStore 也不是 memory。

二者区别是：

| 模块 | 保存什么 | 如何进入 prompt |
| --- | --- | --- |
| memory | 当前任务和跨轮事实 | `memory` / `relevant_memory` |
| durable memory | 长期稳定事实 | `relevant_memory` |
| SkillStore | 可复用操作经验和约束 | TaskPacket active skill constraints |

active skill 会记录：

* uses
* successes
* failures
* last_used

这些统计是 SkillStore 自己的状态，不属于 memory。

当 TaskPacket 编译时，SkillMatcher 会根据 user intent、workflow、recent files/path patterns 匹配 active skill。匹配成功后，SkillCompiler 只把步骤和验证要求编进 TaskPacket，不把整段 memory 或 raw trace 编进去。

所以 05 章可以顺带解释：

> memory 记事实，skill 记经过验证的做法；二者都会影响 prompt，但走不同通道。

## 13. Freshness 机制要修正确认

原 distilled 摘要里提到需要确认 freshness 是 mtime/size 还是全文 SHA-256。

Fusion 当前实现是全文 SHA-256：

```text
file_freshness(path)
  -> resolved.read_bytes()
  -> hashlib.sha256(...).hexdigest()
```

它的好处是判断准确；代价是大文件会有 I/O 成本。

因此修订时不要写成“mtime + size 轻量哈希”。应写成：

> 当前 freshness 使用文件内容 SHA-256，确保文件内容变化后旧摘要失效；这在准确性上更强，但未来如果面对超大仓库，可以考虑优化为分层或增量 freshness。

## 14. 和 04 / 06 章的关系

04 章讲 prompt 形态和缓存：

```text
prefix
memory
relevant_memory
history
current_request
```

05 章只展开其中的 `memory` 和 `relevant_memory` 来自哪里。

06 章讲上下文瘦身：

* history 如何裁剪
* tool output 如何裁剪
* section budget 如何收缩
* duplicate read 如何 collapse

05 章只讲 memory 本身怎么保存、失效和召回。

所以 05 章的边界可以这样说：

> 05 章不是讲整个 prompt 怎么压缩，而是讲哪些跨轮事实值得保存，以及这些事实如何避免过期、如何按需进入 prompt。

```text
Pico 的记忆主要是 task_summary、recent_files、file_summaries、episodic_notes。
```

```text
SkillForge 保留这四层轻量 working memory，并新增 `.skillforge/memory/` 下的 durable memory。working memory 解决当前 session 内的重复读取，durable memory 只保存用户明确要求长期保留且通过安全过滤的稳定事实。
```


## 16. 不要过度宣称的地方

写 05 章时要避免这些说法：

* 不要说 Fusion 已经实现大型向量记忆库。当前仍是轻量规则召回。
* 不要说 durable memory 自动总结所有对话。它需要用户明确持久化意图和格式化 final answer。
* 不要说 workflow state 存在 memory 里。workflow phase/budget/evidence 属于 WorkflowKernel / TaskPacket。
* 不要说 raw log 会进入 memory。raw log 属于 EvidenceStore。
* 不要说 SkillStore 是 memory 的一部分。SkillStore 保存经过验证和人工 promote 的可复用做法。
* 不要说 candidate skill 会直接进入 prompt。只有 active skill 会被 TaskPacket 编译。
* 不要说 freshness 是 mtime/size。当前实现是文件内容 SHA-256。

## 17. 建议放入修订版的讲解段

可以把 05 章开头改成下面这种口径：

> SkillForge 的记忆层不是一个大知识库，它首先解决的是本地 coding agent 的重复劳动问题：刚读过什么文件、这些文件有什么短摘要、哪些短结论下一轮还可能有用。它保留了 Pico 的轻量 working memory，并通过 freshness 防止过期文件摘要继续影响推理。

中段可以补：

> Fusion 在 working memory 旁边增加了 durable memory。只有当用户明确要求“记住/保存/沉淀”某些长期事实，并且最终回答中出现项目约定、决策、依赖或偏好这类受控格式时，系统才会把它们写入 `.skillforge/memory/`。这些长期笔记后续会和 episodic notes 一起参与 relevant_memory 召回。

workflow 连接可以写：

> memory 不负责保存 workflow 状态，但它会给 workflow 提供上下文。TaskPacket 编译时会读取 recent_files 作为路径信号，用来匹配 active skill；同时 relevant_memory 会把与当前请求相关的 episodic/durable notes 放回 prompt。这样记忆、workflow 和 skill 可以互相协作，但边界仍然清楚。

结尾可以强调：

> Fusion 版 05 章的重点不是“记得更多”，而是“记得更分层”：session working memory 负责短期任务事实，durable memory 负责长期稳定事实，EvidenceStore 负责验证证据，SkillStore 负责可复用做法。四者都可能影响后续 prompt，但不能混成一个概念。

## 18. 本章修订后的流程图文字版

如果重画 05 章图，可以按下面这条流程：

```text
SkillForge.ask(user_message)
  |
  v
set_task_summary(user_message)
  |
  v
工具执行
  |
  +--> read_file(path)
  |      -> remember_file(path)
  |      -> summarize_read_result()
  |      -> set_file_summary(path, freshness=sha256)
  |      -> append_note(kind=episodic)
  |
  +--> write_file / patch_file(path)
  |      -> remember_file(path)
  |      -> invalidate_file_summary(path)
  |
  +--> rejected / error / partial_success
         -> append_note(kind=process)

下一轮 ContextManager.build()
  |
  +--> render_memory_text()
  |      - task_summary
  |      - recent_files
  |      - fresh file_summaries
  |      - episodic note count
  |      - durable topic list
  |
  +--> retrieval_candidates(user_message, limit=3)
         - episodic_notes
         - durable memory topics

workflow mode
  |
  +--> _workflow_paths() reads recent_files
  +--> SkillMatcher matches active skills
  +--> TaskPacket receives active_skill_constraints
```

图里建议把 `LayeredMemory`、`DurableMemoryStore`、`EvidenceStore`、`SkillStore` 分成四个盒子。05 章只重点画前两个，后两个用虚线标注边界即可。
