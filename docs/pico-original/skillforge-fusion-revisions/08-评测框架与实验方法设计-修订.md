# 08-评测框架与实验方法设计-修订

## 1. 修订结论

08 章需要修订，而且修订幅度中等偏大。

原 Pico 08 章的核心思想仍然成立：一个 coding agent 项目不能只靠演示说“它能跑”，而要用固定 benchmark、隔离 fixture、自动 verifier、run artifact 和 metrics 聚合来证明“它在可重复条件下稳定变好”。这条主线应该完整保留。

但 SkillForge Pico Fusion 之后，评测对象变多了。原章主要评估普通 coding task、上下文瘦身、记忆收益、provider 差异和工具边界；Fusion 还引入了 workflow、EvidenceStore、checkpoint / resume 判定、completion gate、audit、handoff、SkillCandidate 隔离和 durable memory promotion / rejection。也就是说，08 章不能再只写“任务是否完成”，还要写“完成证据是否成立、恢复状态是否可信、经验是否可以被沉淀、哪些结论不能被过度推广”。

推荐把本章修订成：

> SkillForge 的评测层不是单一 pass rate，而是一组分层证据链。Harness regression 证明基础 runtime 合同稳定；context / memory / recovery ablation 证明具体机制的边际收益；security experiment 证明工具边界是否 fail-closed；provider experiment 只在真实模型可用时比较模型后端表现；workflow / evidence / audit / skill 相关能力则通过 evidence 记录、completion gate、audit report 和 promotion gate 的结构化测试来证明。

## 2. 原章应保留的主线

原章最值得保留的是“任务即合同”的评测思想。

一个 benchmark task 不只是一个 prompt，而是一份约束合同：

```json
{
  "id": "readme_intro_locked",
  "prompt": "...",
  "fixture_repo": "...",
  "allowed_tools": ["read_file", "patch_file"],
  "step_budget": 4,
  "expected_artifact": "...",
  "verifier": "python3 -c \"...\"",
  "category": "documentation"
}
```

这套结构的意义是：模型可以自由生成动作，但评测不会相信模型自述。最终是否通过，要看真实工作区、真实文件、真实 verifier 和 runtime stop reason。

原章中的三层结构也应保留：

1. `benchmarks/coding_tasks.json` 定义固定任务集合。
2. `BenchmarkEvaluator` 复制 fixture，启动 agent，跑任务，收集单任务结果。
3. `metrics.py` 读取 benchmark artifact 和 run artifact，生成聚合指标。

这三层合起来回答一个问题：系统变更以后，是不是在同一批任务、同一套约束、同一种统计口径下真的更稳了。

## 3. 路径和命名要替换

原文里的 Pico 口径要替换成 SkillForge 口径。

| 原 Pico 口径 | Fusion 修订口径 |
| --- | --- |
| `pico/evaluator.py` | `skillforge/evaluator.py` |
| `pico/metrics.py` | `skillforge/metrics.py` |
| `.pico/runs/...` | `.skillforge/runs/...` |
| `.pico/sessions/...` | `.skillforge/sessions/...` |
| `Pico.ask()` | `SkillForge.ask()` |
| `Pico.from_session()` | `SkillForge.from_session()` |
| `pico` CLI | `skillforge` CLI |
| `benchmark-v1.json` | `harness-regression-v2.json` 等 v2 artifact |

这里有一个要特别注意的点：评测模块本身不是主请求路径。用户平时调用 `skillforge` 做任务，不会自动跑完整 benchmark。评测层是旁路系统，它读取 runtime 产物、构造 fixture、运行 scripted 或真实 provider 实验，然后把结果聚合成可复盘数字。

## 4. Fusion 后的评测对象发生了什么变化

原 Pico 的评测对象大致是：

* 普通 coding task 是否完成。
* 工具边界是否拦住危险动作。
* 上下文压缩是否减少 prompt 长度。
* 记忆是否减少重复读取。
* provider 之间 pass rate / attempts / tool_steps 是否有差异。

Fusion 之后，评测对象扩展为：

* `SkillForge.ask()` 主循环是否仍能按合同完成任务。
* `TaskState`、`trace.jsonl`、`report.json` 是否完整记录运行状态。
* checkpoint 是否在正确触发点创建。
* resume 是否能区分 `full-valid`、`partial-stale`、`workspace-mismatch` 等状态。
* `ContextManager` 压缩后是否保留当前请求。
* working memory / relevant memory 是否降低重复读取。
* durable memory promotion 是否只吸收稳定事实，拒绝 secret-shaped 或 transient 信息。
* 工具边界是否能记录安全事件和错误类型。
* EvidenceStore 是否能写入 workflow / tool / log / diff / verification / audit / skill / handoff 等证据。
* completion gate 是否要求 verification / audit / handoff 等证据齐备。
* SkillCandidate 是否保持 quarantine，不能未经验证直接进入 active skill。

所以修订后的 08 章要从“任务完成评测”升级为“运行机制评测 + 证据完整性评测”。

## 5. 当前 benchmark contract 仍然怎么工作

`BenchmarkEvaluator.run_task()` 的基本流程可以这样讲：

```text
读取 benchmark task
  -> 复制 fixture repo 到干净工作区
  -> 在副本里创建 WorkspaceContext
  -> 创建 .skillforge/sessions 和 .skillforge/runs
  -> 用 FakeModelClient 或指定 model_client_factory 装配 SkillForge
  -> 根据 task setup 注入上下文压力 / checkpoint / stale state 等场景
  -> agent.ask(task["prompt"])
  -> 读取 TaskState、report.json、trace.jsonl
  -> 执行 verifier
  -> 计算 passed / failure_category
  -> 写入 harness artifact
```

它最关键的地方不是调用模型，而是创建一个干净、可重复、可验证的运行环境。

每个 task 都在 fixture 的物理副本上运行。这样一个任务修改了 `README.md`，不会污染下一次任务。这个设计对评测很重要，因为 agent 是会真实读写文件的，不能让前一次运行的副作用影响后一次运行。

## 6. PASS 判定仍然是硬性交集

原章的四条件交集应继续保留：

```text
passed =
  within_budget
  and verifier_passed
  and expected_artifact_exists
  and non_failure_stop_reason
```

含义分别是：

| 条件 | 说明 |
| --- | --- |
| `within_budget` | 工具步数没有超过 task 的 `step_budget` |
| `verifier_passed` | verifier 命令返回码为 0 |
| `expected_artifact_exists` | 期望产物在工作区中真实存在 |
| `non_failure_stop_reason` | agent 不是因为错误、超限、畸形输出等异常原因停机 |

这套判定的优点是 fail-closed。模型说“我完成了”不算完成，只有真实文件和 verifier 都通过才算完成。

Fusion 修订时可以强调：这个原则也延伸到了 workflow。workflow 下模型同样不能只说“已验证”或“已交接”，必须有 verification evidence、audit evidence、handoff evidence 等结构化证据，否则 completion gate / audit / skill distill 都应阻塞。

## 7. failure category 的作用

失败不能只写成 fail，因为 fail 不能告诉你系统哪里坏了。

原章的级联失败分类可以继续保留：

1. 期望产物不存在：`missing_artifact`
2. 步数超预算：`budget_exceeded`
3. verifier 失败：`verifier_failed`
4. stop reason 异常：`failure_stop_reason`
5. 其他：`unknown`

它的价值是定位问题。

例如：

* `missing_artifact` 往往说明模型没做出目标改动，或者工具没真正写入。
* `budget_exceeded` 说明任务能做，但探索效率差，可能是 prompt、记忆或工具说明不清。
* `verifier_failed` 说明文件可能改了，但语义没有满足测试。
* `failure_stop_reason` 说明 runtime 控制流出问题，比如 malformed retry、step limit 或 gate 阻塞。

Fusion 可以在这个基础上补充新的观测方向：当 stop reason 是 `completion_gate_blocked`、`audit_failed`、`skill_distill_failed` 或 `resume_load_error` 时，不应简单归到模型失败，而要解释为 runtime 的证据门禁或恢复机制在发挥作用。

## 8. Scripted Baseline 为什么仍然重要

`FakeModelClient` 不是为了模拟真实模型能力，而是为了把模型随机性拿掉。

在 scripted baseline 里，模型输出是固定的：

```text
第 1 次 complete() -> 固定 tool call
第 2 次 complete() -> 固定 final
```

这样可以测试：

* parser 能不能解析工具调用。
* `run_tool()` 能不能执行或拒绝动作。
* `TaskState` 是否正确更新。
* `RunStore` 是否写出 task_state / trace / report。
* verifier 是否能检测真实文件状态。
* checkpoint / resume / durable memory 是否按预期触发。

如果 scripted baseline 都不稳定，就不能把问题归因给大模型。它说明 harness 本身有 bug。

所以 08 章修订后要把实验分成两类：

| 类型 | 目的 |
| --- | --- |
| synthetic / scripted | 隔离模型随机性，验证 harness 机制本身 |
| real provider | 保留真实模型差异，评估端到端效果和成本 |

这两类不能混写。synthetic 通过率高，不等于真实 provider 一定通过；真实 provider 表现差，也不一定说明 harness 机制错了。

## 9. Fusion 当前固定回归任务已经覆盖的新点

当前 `benchmarks/coding_tasks.json` 不再只是几个普通文件修改任务，它已经加入了 Fusion 相关场景。

主要类别包括：

| 类别 | 代表任务 | 验证重点 |
| --- | --- | --- |
| documentation | `readme_intro_locked`、`readme_schema_note` | 普通 patch 合同 |
| text-edit | `sample_beta_locked`、`sample_gamma_locked` | 基础文件编辑 |
| tool-boundary | `invalid_patch_recovery`、`path_escape_recovery`、`repeated_read_recovery` | 参数错误、路径逃逸、重复调用后的恢复 |
| recovery | `context_reduction_checkpoint`、`freshness_reanchor_resume`、`workspace_mismatch_resume` | checkpoint、freshness mismatch、workspace mismatch |
| durable-contract | `durable_promotion_accept`、`durable_promotion_reject` | durable memory 的接纳与拒绝 |

这说明 Fusion 版 08 章不能再只说“固定任务有 6 个标准任务”。更准确的说法是：固定 regression tasks 已经被扩展为覆盖基础编辑、工具边界、恢复机制和 durable memory contract 的小型回归套件。

## 10. context ablation 证明什么

上下文实验不应该用 pass rate 做唯一指标，因为它的核心问题不是“模型会不会做题”，而是：

* prompt 是否变短。
* 当前请求是否被保留。
* memory / relevant memory / history 是否按策略裁剪。
* 不同历史长度、记忆负载、请求长度下压缩是否稳定。

Fusion 里 `run_context_stress_matrix()` 使用 12 组配置：

```text
history: short / medium / long
memory notes: low / high
current request: short / long
```

每组比较：

```text
full
no_context_reduction
```

核心指标是：

| 指标 | 意义 |
| --- | --- |
| `avg_full_prompt_chars` | 开启上下文治理后的平均 prompt 长度 |
| `avg_raw_prompt_chars` | 关闭上下文治理后的平均 prompt 长度 |
| `avg_prompt_compression_ratio` | 平均压缩率 |
| `max_prompt_compression_ratio` | 压力最大场景下的压缩上限 |
| `current_request_preserved_rate` | 当前用户请求是否完整保留 |

这组实验的正确解读是：它证明 context reduction 能在不裁坏当前请求的前提下减少冗余上下文。它不证明模型能力变强，也不证明真实 provider 的最终 pass rate 一定提升。

## 11. memory ablation 证明什么

记忆实验的核心不是“记忆让回答更漂亮”，而是“记忆是否减少重复读取和重复探索”。

Fusion 里有三组对照：

```text
memory_on
memory_off
memory_irrelevant
```

`memory_on` 代表记忆可用；`memory_off` 关闭 memory / relevant memory；`memory_irrelevant` 刻意注入无关记忆，测试召回质量和抗干扰能力。

核心指标包括：

| 指标 | 意义 |
| --- | --- |
| `repeated_reads` | follow-up 阶段是否又去读同一个文件 |
| `avg_tool_steps` | 是否减少工具步数 |
| `avg_attempts` | 是否减少模型尝试次数 |
| `correct_rate` | 记忆带来的回答是否仍然正确 |
| `memory_hit_rate` | 有多少任务能靠记忆避免重复读取 |

这组实验的正确解读是：结构化记忆能让 agent 在后续问题里复用已经建立的事实，减少重复读文件。它不等于“记忆永远可信”，因为 05 / 07 章已经强调 freshness 和 workspace fingerprint 会决定旧记忆是否还能用。

## 12. recovery ablation 是 Fusion 需要补讲的重点

原 Pico 07 章讲了 session / run artifact / resume，但 08 章原文对恢复评测讲得较轻。Fusion 版应该补上 recovery ablation。

恢复实验要回答的问题不是“能不能读回历史”，而是：

* 有 checkpoint 时，是否能恢复当前目标和下一步。
* 文件 freshness 变化时，是否能识别 `partial-stale`。
* workspace fingerprint 变化时，是否能识别 `workspace-mismatch`。
* 系统是否会误信已经过期或不匹配的旧状态。

推荐讲成：

```text
resume_enabled
resume_disabled
```

对比后看：

| 指标 | 意义 |
| --- | --- |
| `resume_success_rate` | 有效恢复状态是否能帮助继续任务 |
| `stale_reanchor_rate` | 文件过期时是否触发重新锚定 |
| `workspace_drift_detection_rate` | 工作区漂移是否被识别 |
| `resume_false_accept_rate` | 是否错误接受了不该信任的旧状态 |

其中 `resume_false_accept_rate` 很关键。好的恢复机制不是尽可能相信旧状态，而是在不确定时宁愿降级、重读、重建 checkpoint，也不要拿错旧状态继续执行。

## 13. security experiment 证明什么

工具安全实验不应该只看“最后任务有没有完成”，而要看危险动作是否被稳定拒绝，并记录为可统计事件。

Fusion 里 security scenario 覆盖：

* path escape read
* symlink escape
* search escape
* approval denied shell
* read-only write
* repeated identical call
* patch nonunique
* patch missing field
* timeout out of range
* empty delegate task

核心指标包括：

| 指标 | 意义 |
| --- | --- |
| `security_event_counts` | 各类安全事件被记录了多少次 |
| `tool_error_code_counts` | 具体工具错误码分布 |
| `tool_status` | 工具结果是 ok / error / rejected / partial_success |

这组实验的正确解读是：它证明工具边界在这些固定场景下能 fail-closed。它不等于完整沙箱安全，也不等于可以放心执行任意 shell。

原章最后提到 verifier 直接在宿主机上跑的风险，这一点仍然要保留。Fusion 增加了 `log_run`、环境 allowlist、raw log 落盘和 evidence 记录，但这不是 Docker sandbox。生产级 verifier 仍应放进隔离容器或更强 sandbox。

## 14. provider experiment 怎么讲才不混淆

provider experiment 是另一层问题。

固定 regression 和 ablation 多数可以用 `FakeModelClient` 做 deterministic 验证；provider experiment 则用 GPT / Claude / DeepSeek 等真实后端去跑同类任务，观察模型差异。

指标包括：

* `pass_rate`
* `avg_attempts`
* `avg_tool_steps`
* `cache_hit_rate`
* `avg_cached_tokens`
* `cached_token_ratio`

这里要非常谨慎：

* provider 结果受账号、base URL、模型版本、服务可用性、缓存策略影响。
* 一次 provider benchmark 不能证明某个模型永久更强。
* prompt cache 命中只能来自 provider 返回的 usage / metadata，不能只看本地 `prefix_hash`。
* synthetic benchmark 和 real provider benchmark 不能混成同一个 pass rate。

推荐写法是：

> Harness regression 证明运行时合同；provider experiment 证明在某个时间、某个 provider 配置、某批任务上的端到端表现。二者是互补关系，不是替代关系。

## 15. EvidenceStore 相关评测应如何补进 08 章

Fusion 新增 EvidenceStore 后，08 章应该补一个“证据完整性”的评测视角。

EvidenceStore 的目标不是让模型看更多文本，而是把关键事实落成可复盘记录：

```text
.skillforge/runs/<run_id>/evidence/
  index.json
  records/ev-*.json
  log/log-*.txt
```

评测应关注：

| 证据类型 | 应验证什么 |
| --- | --- |
| `workflow` | phase transition、TaskPacket、allowed tools 是否记录 |
| `tool` | 工具执行结果、状态、metadata 是否记录 |
| `log` | raw log 是否落盘，prompt-facing brief 是否受预算限制 |
| `diff` | 改动路径和摘要是否能支撑 audit |
| `verification` | pytest / verifier 结果是否结构化 |
| `audit` | 是否有 pass / fail / concerns 和 evidence refs |
| `skill` | candidate 是否来自已验证证据 |
| `handoff` | 交接摘要是否引用关键 evidence |

这部分当前更多由单元测试和 workflow E2E 测试支撑，而不是完全并入 `BenchmarkEvaluator` 的 JSON task schema。因此修订时不要写成“所有 benchmark task 都已经强制检查 evidence”。更准确的说法是：Fusion 的 evidence 机制已经进入 runtime 和 workflow 测试面，固定 benchmark 中部分任务通过 report / trace verifier 检查 checkpoint、resume、durable contract，workflow evidence 另由专门测试覆盖。

## 16. workflow / completion gate 怎么进入评测口径

workflow 模式下，完成不只是 `<final>`。

普通模式中，模型给出 `<final>` 且 stop reason 正常，可能就算一轮请求结束。workflow 模式中，runtime 还要检查当前 phase、allowed tools、evidence 和 gate 条件。

一个 `test_fix` workflow 的理想证据链大致是：

```text
intake / investigate
  -> workflow evidence
implement
  -> diff evidence
verify
  -> log_run
  -> log evidence
  -> verification evidence
audit
  -> audit evidence
skill_distill
  -> skill evidence / quarantined candidate
handoff
  -> handoff evidence
```

评测重点不是“模型有没有说自己验证过”，而是：

* 是否真的运行了 `log_run`。
* raw log 是否在 evidence/log 下。
* verification evidence 是否为 passed。
* audit 是否读取 evidence 并给出 pass / concerns / fail。
* gate 缺证据时是否阻塞完成。
* handoff 是否引用 evidence refs。
* SkillCandidate 是否默认 quarantine。

这就是 Fusion 相比原 Pico 08 章最重要的新增思路：评测不仅看结果文件，还看结果背后的证据链是否闭合。

## 17. SkillCandidate 和 promotion gate 的评测边界

Skill 相关能力不能写成“模型自动学会新 skill 并立即复用”。Fusion 的设计更保守：

1. workflow run 产生 evidence。
2. SkillDistiller 从已验证 evidence 中提炼 candidate。
3. candidate 写入 `.skillforge/skills/candidates/`。
4. candidate 默认 quarantine。
5. PromotionGate 检查证据、freshness、冲突、手动确认等条件。
6. 只有通过 gate 后才进入 active。

因此评测要看：

* 缺少 verification / audit / handoff 时，distill 是否拒绝。
* candidate 是否带 evidence refs。
* candidate 是否剔除 raw log 路径和 secret-shaped 内容。
* quarantine candidate 是否不会直接进入 prompt。
* active skill 使用后是否记录 usage / success / failure 统计。

这部分更像“经验沉淀机制的安全评测”，不是普通 task pass rate。

## 18. core report 的口径要补清楚

Fusion 里 `write_benchmark_core_report()` 生成的核心报告有一个重要边界：

> 这轮 benchmark 只收缩到 Harness regression、context ablation、working memory ablation 和 recovery ablation 四层，不把 provider、run aggregation 或 durable memory 的别的结论揉进来。

这个边界很值得写进 08 章。

原因是不同指标回答的问题不同：

| 报告层 | 回答的问题 |
| --- | --- |
| Harness Regression | runtime 合同是否稳定 |
| Context Ablation | 上下文治理是否减少 prompt 且保留当前请求 |
| Working Memory Ablation | 记忆是否减少重复读取 |
| Recovery Ablation | 恢复机制是否正确识别有效 / 过期 / 漂移状态 |
| Security Experiment | 工具边界是否 fail-closed |
| Provider Experiment | 真实模型后端表现如何 |
| Evidence / Workflow Tests | 完成证据链是否闭合 |

不要把这些揉成一个总分。总分看起来漂亮，但定位能力会变差。评测层最有价值的是让失败可以归因。

## 19. 本章应替换的关键讲解段

原文如果写：

> Pico 的评测框架通过 benchmark、FakeModelClient 和 metrics 证明系统优化收益。

Fusion 版建议替换为：

> SkillForge 的评测框架把系统能力拆成多条证据链。固定 benchmark 通过 fixture 副本、任务合同、step budget、verifier 和 run artifact 证明基础 runtime 稳定；context / memory / recovery ablation 分别证明上下文治理、结构化记忆和恢复机制的边际收益；security experiment 观察工具边界是否 fail-closed；provider experiment 只在真实后端可用时比较模型差异；workflow / evidence / audit / skill 相关能力则通过结构化 evidence、completion gate、audit report 和 promotion gate 来验证。这样最后的数字不是模型自述，而是文件、日志、trace、report 和 evidence 共同形成的可复盘结论。

原文如果写：

> pass rate 是最核心指标。

Fusion 版建议改为：

> pass rate 只适合回答固定任务是否完成，不能覆盖所有机制收益。上下文治理看压缩率和当前请求保留率；记忆看重复读取和工具步数；恢复看 resume success、stale reanchor、workspace drift detection 和 false accept；工具安全看 security event 和 error code；workflow 看 evidence 是否齐备以及 gate 是否正确阻塞。

## 20. 不要过度宣称的地方

修订 08 章时要避免这些说法：

* 不要说 fixed benchmark pass rate 证明真实 provider 一定稳定。
* 不要把 synthetic / scripted 结果和 real provider 结果混成一个总通过率。
* 不要说 `FakeModelClient` 能代表模型能力；它代表 harness 机制测试。
* 不要说当前 verifier 已经有生产级沙箱隔离；它仍然需要 Docker / sandbox 强化。
* 不要说 EvidenceStore 替代 trace / report；它是 workflow 和证据链的补充层。
* 不要说所有 benchmark task 都已经覆盖 workflow evidence gate；当前 evidence / workflow 更多由专门测试和 workflow demo 覆盖。
* 不要说 SkillCandidate 会自动变成 active skill；默认应 quarantine，promotion 需要 gate。
* 不要说 provider cache 命中可以从本地 prefix hash 推断；必须看 provider metadata。
* 不要说 durable memory promotion 证明所有长期记忆都可信；它只证明当前规则下稳定事实被接纳、敏感或 transient 信息被拒绝。

## 22. 推荐收口话术

可以用下面这段作为 08 章修订版总结：

> 08 章的重点不是展示 SkillForge 能跑一次，而是解释我们如何知道它真的变稳。固定 benchmark 把每个任务写成合同：fixture、允许工具、步数预算、期望产物和 verifier 都提前固定；Evaluator 在干净副本里执行任务，最后用文件状态、verifier、预算和 stop reason 的交集判定 pass。Fusion 在这条链路上进一步扩展了评测对象：上下文治理看压缩率和当前请求保留，记忆看重复读取和工具步数，恢复看 stale / drift / false accept，工具边界看 security event，workflow 看 evidence、audit、handoff 和 skill candidate 是否按门禁闭合。这样系统收益不是靠模型自评，而是靠 trace、report、evidence 和 metrics 一层层落地。
