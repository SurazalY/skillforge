# 00-全局总览-修订

## 1. 修订定位

这一章不建议重写成一个完全脱离 Pico 的新总览。更准确的处理方式是：

> 保留 Pico 原文的主控制流、状态面、证据面三层架构，把它改写为 SkillForge Pico Fusion 的迁移版总览，并补上 workflow、evidence、audit、verified skills 这些 Fusion 增量。

原 PDF 的 `00-全局总览` 讲的是 Pico 原项目：`pico` CLI、`Pico.ask()`、`.pico/` 工件目录，以及 `trace.jsonl` / `report.json` 为核心的复盘证据。SkillForge Pico Fusion 是在这个基础上 fork、rename、再加控制面和证据面扩展，因此这一章应当讲清楚两件事：

1. Pico 原来的系统骨架为什么仍然成立。
2. Fusion 后哪些名字、路径、边界和完成判定已经变化。

## 2. 原章应保留的核心

原章最有价值的是把 coding agent 讲成一条工程化执行链，而不是“模型 + 工具”的松散组合。这部分应保留：

* CLI 负责把启动参数、工作区、provider、session、approval 等装配成运行现场。
* Runtime 的 `ask()` 主循环负责感知、决策、行动、记录。
* Prompt 每轮重建，不是请求开始时拼一次就结束。
* 模型输出必须经过 `parse()`，只能进入 tool / final / retry 这些受控分支。
* 工具调用走统一网关，做注册、参数、路径、approval、重复调用和工作区变化检查。
* Session 面向“下次怎么继续干”，run artifacts 面向“刚才到底发生了什么”。
* `task_state.json`、`trace.jsonl`、`report.json` 是复盘主线，不是跑完后补写的装饰。
* evaluator / metrics / fake provider 让系统可以被比较、被回看，而不是只靠模型自述。

这套主线在 Fusion 里仍然成立，只是名字、目录和外层控制协议变了。

## 3. 必须修订的命名与路径

原文中所有 Pico 主路径都要在修订版里映射为 SkillForge 主路径：

| 原 Pico 口径 | SkillForge Pico Fusion 口径 | 说明 |
| --- | --- | --- |
| `pico` CLI | `skillforge` CLI / `python3 -m skillforge` | `pico` 不再作为正式入口 |
| Python 包 `pico` | Python 包 `skillforge` | 原模块路径应改写为 `skillforge.*` |
| `Pico.ask()` | `SkillForge.ask()` | 主循环语义保留，类名已迁移 |
| `.pico/` | `.skillforge/` | session、run、memory、skills、workflow evidence 均走新根目录 |
| `PICO_*` env | `SKILLFORGE_*` env | `PICO_*` 仅作为兼容 fallback，不是文档主路径 |

修订版里不要再把 `.pico/` 作为当前项目的主 artifact 目录。可以写成：

```text
.skillforge/
  sessions/
  runs/<run_id>/
    task_state.json
    trace.jsonl
    report.json
    evidence/
      index.json
      records/
      log/
  skills/
    active/
    candidates/
    archive/
  workflows/
  memory/
```

其中 `task_state.json`、`trace.jsonl`、`report.json` 是 Pico 原三件套迁移后的核心工件；`evidence/` 和 `skills/` 是 Fusion 后新增的证据与技能生命周期目录。

## 4. 三层架构的 Fusion 版写法

原章的“控制面、状态面、证据面”建议保留，但要扩展成 Fusion 版：

| 层 | Pico 原职责 | Fusion 后修订口径 |
| --- | --- | --- |
| 控制面 | CLI、runtime、context、tools、models 决定 agent 怎么跑 | 保留 `SkillForge.ask()` 主循环，并新增 workflow templates、Workflow IR、Static Validator、WorkflowKernel、TaskPacket、phase/tool budget |
| 状态面 | session、run artifacts、memory、checkpoint 决定系统记住什么、怎么恢复 | 根目录迁移为 `.skillforge/`，新增 workflow state、evidence index、skills candidate/active/archive 状态 |
| 证据面 | trace、report、evaluator、metrics 决定系统怎么复盘和评测 | 在原 trace/report 上新增 EvidenceStore、log evidence、verification evidence、audit report、handoff artifact、SkillCandidate evidence |

建议在本章明确一句：

> Pico 的三层架构提供了“能跑、能恢复、能复盘”的底座；Fusion 增加的是“有阶段、有证据、有审计、有可控经验沉淀”的外层协议。

## 5. 单次请求生命周期的修订版

原文的 9 步生命周期可以改成下面这版：

1. CLI 解析参数，决定工作目录、provider、model、approval、resume、可选 workflow。
2. `build_agent()` 装配 `WorkspaceContext`、`SessionStore`、具体 `ModelClient` 和可选 workflow 配置。
3. one-shot 或 REPL 将用户消息交给 `SkillForge.ask()`。
4. `SkillForge.ask()` 创建 run，写入第一版 `task_state.json`，并在启用 workflow 时初始化 workflow evidence。
5. 每一轮重新构建 prompt，把 prefix、memory、history、current request，以及必要的 TaskPacket 信息拼起来。
6. 模型返回 raw output，runtime 先 `parse()`，判断是工具调用、最终答案还是 malformed retry。
7. 如果是工具调用，统一进入 `run_tool()`，由工具网关做注册、参数、路径、approval、read-only、workflow phase policy 等检查。
8. 工具结果写回 session history、working memory、trace、task state；若是 log / verification / audit / handoff 相关动作，还会写入 evidence。
9. 模型给出 `<final>` 或命中 step / retry / workflow budget 后结束；写出 `report.json`，workflow 模式下还要检查 completion evidence gate。

注意：workflow 是 Fusion 的增强模式，不要写成所有普通 one-shot / REPL 路径都已经强制经过完整 phase gate。

## 6. 本章新增能力的讲法

### 6.1 Workflow

Fusion 后可以在总览中补一句：

> Workflow 不是替代 `SkillForge.ask()`，而是在原主循环外面增加任务阶段、允许工具、预算和完成门禁。

当前内建三类 workflow：

| Workflow | Phases | 用途 |
| --- | --- | --- |
| `repo_audit` | `intake -> investigate -> audit -> handoff` | 只读仓库审阅 |
| `code_change` | `intake -> plan_compile -> implement -> verify -> audit -> skill_distill -> handoff` | 通用代码修改 |
| `test_fix` | `intake -> investigate -> implement -> verify -> audit -> skill_distill -> handoff` | 失败测试修复 |

### 6.2 Evidence / Log

原 Pico 已有 `trace.jsonl` 和 `report.json`，Fusion 新增 `EvidenceStore`，把完成判定需要的证据结构化：

* log evidence
* verification evidence
* diff evidence
* audit evidence
* handoff evidence
* skill evidence

本章应强调：raw log 落盘，但不直接塞进 prompt；prompt 中只放 brief、failure detail 或 evidence reference。

### 6.3 Audit

Fusion 增加 deterministic audit，用于在 handoff 前检查硬条件：

* 是否有 diff。
* 是否有 verification pass。
* 是否触碰 `.git`、`.skillforge`、`.env` 等 protected path。
* SkillCandidate 是否仍在 quarantine。
* concerns 是否被真实记录。

面试讲法可以是：

> 原 Pico 能复盘一次运行；Fusion 进一步让完成判定 fail-closed。模型不能只说“我完成了”，必须拿结构化证据过 gate。

### 6.4 Verified Skills

Fusion 新增 skills 生命周期：

1. verified workflow run 产出 SkillCandidate。
2. candidate 默认进入 quarantine。
3. 人工执行 `skillforge skills promote <candidate-id>`。
4. PromotionGate 检查 schema、evidence、safety、freshness、utility、冲突和压缩度。
5. promote 后生成 active SkillCard。
6. 后续 TaskPacket 只注入 active skill，不注入 candidate / rejected / archived skill。

这一点可以放在全局总览末尾，作为“从一次执行到受控经验沉淀”的升级。

## 7. 不应夸大的地方

修订这一章时要避免以下说法：

* 不要说 Fusion 是从零重写；它是 Pico fork + rename + fusion 增量。
* 不要说 workflow 已经强制接入所有 `SkillForge.ask()` 路径；当前主要通过 `--workflow` 驱动。
* 不要说 skills 会自动进入长期 prompt；candidate 默认 quarantine，active 需要 manual promote。
* 不要说 raw log 会进入上下文；raw log 是 evidence artifact，不是 prompt 正文。
* 不要把 `skillforge-harness/` 写成当前实现底座；当前实现目录是 `skillforge-pico-fusion/`。
* 不要把 live smoke 写成永久保证；它依赖外部 provider 凭据和额度。

## 8. 本章修订后的推荐结论

可以把 00 章最后的收口改成：

> 如果用一句话概括，Pico 原本把“模型在真实仓库里持续工作”变成一条有状态、有边界、能恢复、能复盘、能评测的执行链；SkillForge Pico Fusion 在这条链上继续加了 workflow 阶段约束、结构化 evidence、deterministic audit 和 verified skills 生命周期，让 agent 不只是能完成一次任务，还能把完成条件、验证证据和可复用经验纳入受控闭环。

## 9. 推荐插入到整合版的位置

如果后续生成“整合阅读版”，建议本章结构如下：

1. Pico 原问题：为什么不是“模型 + 工具”。
2. Fusion 定位：Pico fork + rename + fusion 增量。
3. 三层架构：控制面 / 状态面 / 证据面。
4. 一条请求生命周期：普通 one-shot / REPL 路径。
5. Workflow 模式：phase、TaskPacket、budget、completion gate。
6. `.skillforge/` 目录树。
7. Evidence / Audit / Skills 的新增闭环。
8. 当前验证与边界：full regression、fake gate、live smoke 依赖凭据、workflow 非全路径强制。

这样既保留原 Pico 文档的学习价值，又不会把 Fusion 后的事实讲乱。
