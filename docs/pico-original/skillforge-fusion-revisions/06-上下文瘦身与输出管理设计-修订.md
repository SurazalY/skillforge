# 06-上下文瘦身与输出管理设计-修订

## 1. 修订结论

这一章需要修订，但原章的主体结构仍然成立。

Pico 原来的上下文瘦身设计，核心是分层控制：长输出先裁剪，memory 自己限额，relevant memory 只召回少量，history 按新旧压缩，最后再由 `ContextManager` 按 section budget 做总装箱。这条主线在 SkillForge Pico Fusion 里仍然保留。

Fusion 需要补充的地方主要有四个：

* `ContextManager` 已经是 `skillforge/context_manager.py` 的独立模块。
* workflow TaskPacket、checkpoint text、evidence briefs、active skill constraints 会作为 prefix extras 进入最终 prompt，因此也要参与预算控制。
* `log_run` 的 raw log 不直接进入 prompt，长日志通过 EvidenceStore 落盘，再用 `log_brief` / `log_failure_detail` 按需取短内容。
* prompt 压缩触发后，runtime 会创建 `context_reduction` checkpoint，让“上下文被压过”这件事可恢复、可追踪。

一句话版本：

> Pico 06 章讲的是“不要让旧历史和长输出撑爆 prompt”；Fusion 版 06 章还要讲“workflow/evidence/skills 新增的动态上下文也必须受预算约束，raw log 只能进证据层，不能直接进 prompt”。

## 2. 原章应保留的主线

原章这条四层瘦身链路仍然可以保留：

```text
source outputs
  -> clip / summarize
  -> memory limits
  -> relevant_memory limits
  -> history rendering
  -> section budgets
  -> final prompt
```

这套设计的价值也仍然成立：

> 系统不是粗暴从整段 prompt 末尾一刀切，而是知道自己正在压缩哪一类上下文。

原章中的这些数值仍然基本对齐当前实现：

| 机制 | 当前值 |
| --- | ---: |
| `MAX_TOOL_OUTPUT` | 4000 |
| workspace doc snippet | 1200 |
| git status snippet | 1500 |
| `WORKING_FILE_LIMIT` | 8 |
| `EPISODIC_NOTE_LIMIT` | 12 |
| `FILE_SUMMARY_LIMIT` | 6 |
| `RELEVANT_MEMORY_LIMIT` | 3 |
| history recent window | 6 |
| default total budget | 12000 |

所以 06 章不是要重写为新机制，而是要在原机制旁边补上 Fusion 的新上下文来源。

## 3. 第一层：入口处先裁长输出

入口裁剪仍然从 `skillforge/workspace.py` 的 `clip()` 开始：

```text
MAX_TOOL_OUTPUT = 4000

clip(text, limit=MAX_TOOL_OUTPUT)
  -> text within limit: return as is
  -> text over limit: return prefix + truncated marker
```

这层的目标是防止长工具输出在系统内部无限流动。

当前常见入口裁剪包括：

| 内容 | 上限 |
| --- | ---: |
| 工具返回值 | 4000 |
| 工作区白名单文档片段 | 1200 |
| `git status --short` | 1500 |
| trace 中的工具结果摘要 | 500 |
| `run_started` 中的用户请求摘要 | 300 |
| evidence payload 中的紧凑字段 | 200 / 300 等场景化上限 |

`read_file` 还有一层额外压缩：

```text
summarize_read_result(result, limit=180)
```

它只取前几行非空内容并裁到短摘要，用于写入 `file_summaries`，避免完整文件内容进入长期上下文。

## 4. Fusion 新增的日志入口边界

原 Pico 06 章讲了 shell 输出、工具输出和 history 膨胀。Fusion 需要额外强调日志证据边界。

在 Fusion 中，验证命令有两条路：

```text
run_shell
  -> 返回裁剪后的命令输出
  -> 进入 history

log_run
  -> 执行命令
  -> raw log 写入 EvidenceStore
  -> 返回 evidence_id / status / summary
```

这意味着：

* raw log 不直接进入 prompt。
* prompt 只看 evidence id、summary、brief 或 failure detail。
* `log_brief(evidence_id, max_chars)` 会按预算返回摘要。
* `log_failure_detail(evidence_id, failure_id / failure_index)` 只返回某个失败点的结构化细节。

这层是 Fusion 版上下文治理的关键新增点。

原来 06 章说“长日志不能撑爆 prompt”，Fusion 版要改成：

> 长日志首先不应该进入 prompt。它应该进入 EvidenceStore，prompt 只拿可预算的摘要和必要失败细节。

## 5. 第二层：memory 自己先限额

05 章已经详细讲了 memory，这里只保留和瘦身有关的部分。

memory 仍然有几组硬上限：

| 字段 | 上限 |
| --- | ---: |
| `recent_files` | 8 |
| `episodic_notes` | 12 |
| `file_summaries` 渲染数 | 6 |
| `task_summary` | 300 字符 |
| note text | 500 字符 |
| file summary | 500 字符 |

这层的作用是让 memory 保持“仪表盘”形态，而不是长成第二份 history。

Fusion 增加了 durable memory，但它也不是无限展开：

* `memory` section 只展示 durable topic 列表。
* `relevant_memory` 只召回少数 durable notes。
* raw log、traceback、stdout、stderr 不应被沉淀成 durable memory。

因此 durable memory 没有破坏 06 章的瘦身逻辑。它只是多了一个可控召回来源。

## 6. 第三层：Relevant Memory 只带少量

`ContextManager.build()` 中仍然默认只召回 top 3：

```text
RELEVANT_MEMORY_LIMIT = 3
selected_notes = self.agent.memory.retrieval_candidates(user_message, limit=3)
```

召回来源现在包括：

* session 内 `episodic_notes`
* `.skillforge/memory/topics/*.md` 中的 durable notes

但不管来源是什么，进入 prompt 前都要过同一段 budget：

```text
relevant_memory budget = 1200
```

如果 note 很长，`_render_relevant_memory()` 会计算每条 note 的平均预算：

```text
per_note_budget = usable_budget / note_count
```

然后对每条 note 做 `_tail_clip()`。

这个设计继续保留原章的判断：

> 相关记忆不是越多越好，而是少量、相关、可解释，并且不能让单条长笔记挤掉其他笔记。

## 7. 第四层：History 按新旧分层

history 仍然是最容易膨胀的部分。

当前 `ContextManager._render_history_section()` 仍然采用最近窗口：

```text
recent_window = 6
```

最近 6 条历史保留更多细节：

```text
line_limit = 900
```

更旧的历史压得更狠：

```text
line_limit = 60
```

对于旧的 `read_file`，还会做两件事：

* 同一路径重复读取只保留一次，重复项计入 `collapsed_duplicate_reads`。
* 如果 memory 里有该文件摘要，就用 `path -> summary` 替代旧工具输出，计入 `reused_file_summary_count`。

对于旧的其他工具，会尽量压成一行摘要，计入 `summarized_tool_count`。

所以 history 的瘦身不是简单裁剪，而是三种策略叠加：

```text
近因优先
重复读取折叠
旧工具摘要化
```

## 8. 第五层：Section Budget 装箱

最终 prompt 由 `ContextManager` 按固定顺序组装：

```text
prefix
memory
relevant_memory
history
current_request
```

默认总预算：

```text
DEFAULT_TOTAL_BUDGET = 12000
```

默认 section budget：

| section | 默认预算 |
| --- | ---: |
| `prefix` | 3600 |
| `memory` | 1600 |
| `relevant_memory` | 1200 |
| `history` | 5200 |
| `current_request` | 不裁剪 |

默认 floor：

| section | 默认 floor |
| --- | ---: |
| `prefix` | 1200 |
| `memory` | 400 |
| `relevant_memory` | 300 |
| `history` | 1500 |

如果没有显式覆盖 floor，运行时也会按：

```text
max(20, budget // 4)
```

计算每个 section 的保底值。

超预算时，削减顺序仍然是：

```text
relevant_memory -> history -> memory -> prefix
```

`current_request` 不进入削减流程。

这一点非常重要：当前用户请求是本轮最硬的输入，不能为了省上下文把它裁坏。

## 9. Fusion 新增：TaskPacket 也进入预算

04 章已经讲过，Fusion 的 workflow 会把 TaskPacket 渲染到最终 prompt 前部。

在 `ContextManager.build()` 里，这些内容会作为 prefix extras 拼到 `prefix` section 前面：

```text
checkpoint text
Workflow task packet:
  user intent
  workflow / phase
  budgets used
  allowed tools
  evidence briefs
  active skills
PromptPrefix.text
```

这意味着 TaskPacket 不会绕过预算控制。

它虽然出现在 prompt 前部，但仍属于 `prefix` section 的 raw text，最终会受 `prefix` budget 和 floor 约束。

这点要写清楚，否则读者可能以为 workflow 信息是额外无限注入的。正确说法是：

> Fusion 把 workflow task packet 放进 prompt 前部，但它仍然要和 prefix 一起接受 section budget 管理。

## 10. Evidence Briefs 的瘦身语义

TaskPacket 中的 evidence briefs 也是上下文瘦身的一部分。

它们不是完整 evidence record，也不是 raw artifact，而是类似下面的短信息：

```text
- ev-123 (log): 1 failed in 0.23s
- ev-456 (diff): patch_file changed src/app.py
```

这样模型能知道“有什么证据存在”，但不会把完整日志、完整 diff、完整 trace 都塞进 prompt。

如果模型需要更多细节，应该走工具：

```text
log_brief
log_failure_detail
read_file
search
```

而不是依赖 prompt 一次性带完全部证据。

这就是 Fusion 的证据上下文策略：

```text
prompt carries brief
tools retrieve detail
EvidenceStore keeps raw
```

## 11. 上下文压缩会创建 checkpoint

Fusion 里还有一个细节：如果本轮 `prompt_metadata` 里出现 `budget_reductions`，runtime 会创建 checkpoint：

```text
trigger = "context_reduction"
```

这让上下文压缩不只是 metadata 里的数字，而是进入恢复链路。

它的意义是：

* 之后 resume 时知道这一轮曾经发生过上下文压缩。
* 如果压缩导致信息不足，可以从 checkpoint 和 trace 里追溯。
* 这和 freshness mismatch / workspace mismatch 一样，属于运行时重要状态变化。

所以 06 章修订时应补一句：

> 上下文瘦身不是静默发生的；当预算削减真的触发时，系统会把它写进 prompt metadata，并创建 context_reduction checkpoint。

## 12. Metadata 现在记录什么

`ContextManager._metadata()` 会记录很多诊断字段。

整体层面：

* `prompt_chars`
* `prompt_budget_chars`
* `prompt_over_budget`
* `section_order`
* `section_budgets`
* `budget_reductions`
* `reduction_order`

每个 section：

* raw chars
* budget chars
* rendered chars

relevant memory：

* selected_count
* selected_notes
* selected_sources
* selected_kinds
* selected_durable_count
* rendered_count

history：

* raw chars
* rendered chars
* older_entries_count
* collapsed_duplicate_reads
* reused_file_summary_count
* summarized_tool_count

current request：

* text
* raw chars
* rendered chars
* section chars

这些 metadata 会进入 trace / report，用来回答：

* 这轮 prompt 为什么变短？
* 哪个 section 被压缩了？
* 是否折叠了重复 read_file？
* 是否复用了 file summary？
* 当前请求是否完整保留？

## 13. 和 04 / 05 的关系

04 章讲 prompt 形态：

```text
prefix + memory + relevant_memory + history + current_request
```

06 章讲这些 section 长起来以后怎么被压住。

05 章讲 memory 从哪里来：

```text
task_summary / recent_files / file_summaries / episodic_notes / durable topics
```

06 章讲 memory 如何限额、如何作为 section 被裁剪。

03 章讲工具和日志边界：

```text
run_shell / log_run / log_brief / log_failure_detail
```

06 章讲这些工具输出为什么不能直接无限进入 prompt。

所以 06 章可以定义为：

> 它不是讲上下文从哪里来，而是讲上下文一旦变长，系统如何分层收缩，并且尽量保住当前请求和关键规则。

```text
长日志会被裁剪后进入 history。
```

修订为：

```text
普通 shell 输出会被裁剪后进入 history；Fusion 中用于验证的长日志应优先通过 log_run 写入 EvidenceStore，prompt 只接收 evidence id、summary、log_brief 或 log_failure_detail，不直接携带 raw log。
```

```text
prefix 主要包含系统规则、工具和 workspace。
```

```text
PromptPrefix 仍包含系统规则、工具和 workspace；但 ContextManager 的 prefix section 还可能临时拼入 checkpoint text 和 workflow task packet。这些动态内容也会进入 prefix section 的预算控制。
```

原文如果写：

```text
相关记忆只从 episodic_notes 召回。
```

修订为：

```text
相关记忆会从 session episodic_notes 和 durable memory topics 中召回，但最终仍受 RELEVANT_MEMORY_LIMIT=3 和 relevant_memory section budget 控制。
```

```text
测试文件是 tests/test_memontext_managery.py。
```

```text
应核对为 context manager / memory 相关测试，例如 tests/test_context_manager.py 和 tests/test_memory.py；原文中的 test_memontext_managery.py 很可能是拼写错误。
```

## 15. 不要过度宣称的地方

写 06 章时要避免这些说法：

* 不要说已经 token-aware。当前主要仍是字符数 `len(text)` 预算。
* 不要说系统能语义理解每一句重要性。当前主要是规则、窗口、摘要和 section budget。
* 不要说 raw log 会进 prompt。raw log 应留在 EvidenceStore。
* 不要说 TaskPacket 不受预算限制。它作为 prefix extras 进入 prefix section，仍受 budget 影响。
* 不要说 current request 会被裁剪。当前请求不进入 section reduction。
* 不要说 prompt 一定能被压到预算以下。如果所有可裁 section 都到 floor 后仍超预算，metadata 会标记 `prompt_over_budget`。
* 不要说 relevant_memory 越多越好。它默认只召回 3 条，并对单条 note 做预算裁剪。

## 16. 建议放入修订版的讲解段

可以把 06 章开头改成下面这种口径：

> SkillForge 的上下文治理不是在最后对 prompt 粗暴截断，而是从内容进入系统开始分层控制。工具输出先被裁剪，read_file 结果会被压成文件摘要，memory 自身有数量和长度上限，相关记忆只召回少数，history 按新旧压缩，最后 ContextManager 再按 section budget 做总装箱。

中段补上 Fusion 新增：

> Fusion 新增 workflow 和 evidence 后，上下文来源更多了，但不是无限进入 prompt。TaskPacket、evidence briefs 和 active skill constraints 会进入 prompt 前部，同时仍受 prefix section budget 管理；raw log 则不进入 prompt，而是落入 EvidenceStore，模型通过 log_brief 或 log_failure_detail 按需取短内容。

预算部分可以写：

> 当最终 prompt 超过总预算时，系统按 `relevant_memory -> history -> memory -> prefix` 的顺序收缩，并为每个 section 保留 floor。当前用户请求不参与裁剪。触发 budget reduction 后，runtime 会在 metadata 中记录具体削减项，并创建 `context_reduction` checkpoint，方便后续恢复和排查。

结尾可以强调：

> Fusion 版 06 章的重点不是“把所有东西压短”，而是“让不同价值密度的上下文走不同通道”：raw log 进证据层，文件内容进短摘要，旧历史进压缩 transcript，当前请求保持完整，workflow 任务合同进入受预算约束的前部上下文。

## 17. 本章修订后的流程图文字版

如果重画 06 章图，可以按下面这条流程：

```text
输入与工具结果
  |
  +--> workspace docs / git status
  |      -> clip at source
  |
  +--> read_file result
  |      -> tool result clip
  |      -> summarize_read_result
  |      -> file_summaries
  |
  +--> run_shell result
  |      -> clip
  |      -> history
  |
  +--> log_run result
         -> raw log to EvidenceStore
         -> evidence_id + summary to prompt/history

ContextManager.build()
  |
  +--> prefix section
  |      - checkpoint text
  |      - workflow task packet
  |      - PromptPrefix.text
  |
  +--> memory section
  |      - task / recent files / fresh file summaries
  |
  +--> relevant_memory section
  |      - top 3 episodic/durable notes
  |
  +--> history section
  |      - recent window detailed
  |      - older history compressed
  |      - duplicate read_file collapsed
  |
  +--> current_request
         - never reduced

Budget reduction if over 12000 chars
  |
  +--> relevant_memory
  +--> history
  +--> memory
  +--> prefix
  |
  v
prompt_metadata
  - budget_reductions
  - section rendered chars
  - collapsed reads
  - reused file summaries
  - current_request preserved

if budget_reductions:
  -> create context_reduction checkpoint
```

图里建议把 `EvidenceStore` 画成日志旁路，把 `TaskPacket` 画成 prefix section 的动态输入。这样能直观看出 Fusion 不是把更多东西塞进 prompt，而是给不同类型内容分配了不同通道。
