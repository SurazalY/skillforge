# 01-代码仓库上下文设计-修订

## 1. 修订结论

这一章不需要大改。

Pico 原来的 `WorkspaceContext` 仓库基线设计，在 SkillForge Pico Fusion 中基本保留。Fusion 没有把这一层升级成全仓索引、目录树扫描、RAG 或 Git diff 摘要；它主要做的是命名迁移和外围接入。

可以把本章修订口径压成一句话：

> SkillForge 继续沿用 Pico 的轻量仓库基线：启动时采集 cwd、repo_root、branch、dirty status、recent commits 和少量关键项目文档，让模型先知道自己身处什么仓库；Fusion 只把包名、CLI、artifact 目录和 prefix 文案迁移到 SkillForge 口径。

## 2. 原章应保留的内容

这些设计仍然成立：

* 不预加载整仓代码，避免 prompt 被无关文件塞满。
* 启动时通过 `WorkspaceContext.build(cwd)` 建立仓库第一印象。
* 仓库基线仍包含 `cwd`、`repo_root`、`branch`、`default_branch`、`status`、`recent_commits`、`project_docs`。
* 项目文档仍只扫描白名单：`AGENTS.md`、`README.md`、`pyproject.toml`、`package.json`。
* 每份项目文档仍截断到约 `1200` 字符。
* 每轮 prompt 前仍通过 `refresh_prefix()` 重新采样工作区，并用 `fingerprint()` 判断是否需要重建 prefix。
* 这一层定位仍然是“导航”，不是“知识库”。

## 3. 需要替换的 Pico 口径

| 原 Pico 写法 | 修订为 SkillForge 写法 |
| --- | --- |
| `pico/cli.py` | `skillforge/cli.py` |
| `pico/workspace.py` | `skillforge/workspace.py` |
| `pico/runtime.py` | `skillforge/runtime.py` |
| `pico` / `python -m pico` | `skillforge` / `python -m skillforge` |
| `.pico/` | `.skillforge/` |
| `Pico.ask()` | `SkillForge.ask()` |

其中最具体的一处代码差异是：原来 workspace 忽略 `.pico`，现在忽略 `.skillforge`。这属于 artifact 命名迁移，不是仓库上下文策略变化。

## 4. Fusion 后可以补一句的内容

本章可以轻量补充 workflow / TaskPacket 的关系，但不要展开太多：

> WorkspaceContext 仍负责提供稳定仓库基线；workflow / TaskPacket 会影响当前 phase 可用工具、证据摘要和 active skills 是否进入 prompt，但不改变 WorkspaceContext 的基础采样策略。

也就是说，01 章讲的是“模型进入仓库前先拿什么基线”，不是 workflow evidence 或 skills 生命周期的主场。

## 5. 不要写成已完成的点

原 Pico 文档里提到的几个未来改进，在当前 Fusion 中仍不应写成已完成：

* 不要说已经有轻量目录树摘要。
* 不要说已经扩展文档白名单到 `Cargo.toml`、`go.mod`、`Makefile`、`pytest.ini` 等。
* 不要说已经有 Git diff 摘要、改动规模、upstream 偏移或 stash 状态。
* 不要说 workspace 层已经做 RAG、向量检索或全仓索引。

这些仍然可以作为“后续可补”的方向保留。

## 6. 推荐收口话术

可以把本章最后改成：

> SkillForge 在仓库上下文这一层基本继承 Pico 的轻量设计：先给模型一份便宜、稳定、可刷新、可解释的仓库基线，而不是预加载整仓。它让模型第一步知道自己在哪、仓库是否 dirty、最近有什么提交、哪些项目文档值得先看。Fusion 的变化主要是命名和目录迁移，以及后续 prompt 会和 workflow / TaskPacket 的控制信息拼接，但 WorkspaceContext 本身仍保持小而稳。
