# 框架与对标复用指引 (reuse-guidelines)

本指引整理了后续 Agent 在针对新智能体项目编写产品文档、架构说明书或面试准备材料时，如何参考本资料包的骨架、表达方式和论证结构。

---

## 1. 推荐的对标阅读顺序

为了让后续 Agent 降低上下文开销，推荐按以下路径顺序加载资料：

```text
步骤 1: distilled/AGENT_GUIDE.md (快速获取 Pico 核心逻辑与资料包大纲映射)
  │
  ├───> 步骤 2: distilled/source-toc.md (快速定位物理行号分布及转换限制)
  │
  ├───> 步骤 3: distilled/analysis/writing-style.md (了解写作风格和论证参考)
  │
  └───> 步骤 4: distilled/chapters/ 下的具体模块设计章节 (需要对标某子系统时，定向按需阅读)
```

> [!IMPORTANT]
> **后续 Agent 避免每次任务无脑读取 270KB 级源 Markdown。** 
> 只有在遇到具体行号代码对齐争议、排版有严重乱码歧义时，方可触发对 `source.md` 特定段落的读取。

## 2. 建议复用的文档骨架 (骨架模板)

后续针对新项目的各系统模块编写文档时，建议参考以下“四段式骨架结构”：

```markdown
# [模块/子系统标题]

## 1. 解决的核心问题与安全风险
* 列出该模块如果不进行受控干预，大模型运行会引发什么后果或安全问题（如：重复读文件、路径越界破坏主机环境等）。

## 2. 核心架构设计与控制逻辑
* 通过数据结构定义和精炼的 python 控制流，讲解系统是如何进行硬性校验、隔离以及推进的（突出 Fail-closed 安全契约）。

## 3. 工程折中方案 (Trade-offs)
* 坦白陈述当前设计的局限与降级，并站在系统工程的角度进行合理解释（如为什么没有使用重型方案以保留调试灵活性）。

## 4. 实验数据与指标闭环
* 罗列在该模块优化开启和关闭对照下的量化成效（包含具体的尝试次数、步骤缩减率、正确率等事实数据）。
```

---

## 3. 适合复用/迁移的表达与方法
* **“TL 拟人化隐喻”表达法**：在阐述长链路控制时，适合复用将智能体框架比作“工程团队 TL 明确拆解任务和验收合同”的表达，有助于提升文档的宏观系统感。
* **“Freshness 新鲜度校验”逻辑**：在设计任何缓存、记忆或仓库感知模块的文档时，复用“提取物理哈希 -> 动态刷新 -> 指纹比对失效”的逻辑和词汇。
* **级联失败归档表**：在评测或审计章节的编写中，复用级联分类判断结构，将运行失败科学地分类为 `missing_artifact`、`budget_exceeded`、`verifier_failed`，提高评测的可回溯性。

---

## 4. 只能参考、不能照搬的边界
* **具体的实验测试数据**：Pico 文档中出现的 16.19% 压缩率、重复读文件从 60次降到0次等具体数字，是基于特定任务和环境得出的实验事实。后续写新项目时，**只能复用其对照实验的设计逻辑，数据本身必须替换为新项目的真实测量数据**。
* **硬编码常数限制**：如 `WORKING_FILE_LIMIT = 8`、`MAX_TOOL_OUTPUT = 4000` 属于 Pico 针对当前小规模 Mock 仓的硬编码设定，新项目中不可生硬套用。
* **特定的模型 Provider 命令**：如 `--provider openai --model gpt-5.4`、注册 Right Code Key 等，属于原作者教程中的调试环境。生产环境文档中应替换为真实的生产级 LLM 后端与模型名称。

---

## 5. 触发回看源 Markdown 或原 PDF 的条件
* **时序与流向可视化**：凡是涉及“全局架构图”、“Pico ask 控制主循环图”、“上下文分层打包图”、“工具安检网关图”、“Checkpoint/Resume 漂移判定时序图”时，由于 Markdown 中图片占位缺失，**必须物理打开 `pico项目文档/2-pico.pdf` 查看其拓扑连线**。
* **代码块行号及 XML 损坏争议**：当 Markdown 中因转换出现粘连乱码时，需回看原 PDF 确认正确的代码格式。
