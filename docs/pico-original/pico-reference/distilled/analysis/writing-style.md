# 写作风格分析指南 (writing-style)

此文档旨在对 Pico 项目原始 Markdown 的写作风格特征进行横向剖析，并为后续 Agent 编写新文档时提供文风及表达上的参考。

---

## 1. 文体定位
* **文体属性**：**技术方案白皮书与面试备考指南的结合**。
* **主要特征**：原文档并非单调的软件 API 接口文档，而是将“架构设计细节、系统折中思考 (Trade-offs)、对比实验数据与面试技术辩护”融为一体。其叙述风格偏向实战，语气务实、冷静。

---

## 2. 写作风格核心要素

### 2.1. 标题命名与分层
* **特征**：原章节多使用显式数字序号进行层级划分（如 `1-`、`2-` 以及内部小节 `2.1.` 等），展现出较强的逻辑承接关系。
* **参考**：后续编写新章节时，建议参考这种结构化序号标题。主标题和二级标题之间应有明确的承接关系，善用修饰标签（如 `【重要】`、`【更新中】`）来提示内容状态。

### 2.2. 短平快推进与 Bullet Points
* **特征**：全篇避免了过于冗长的自然语言叙述。段落多为 1-2 句话的独立句，或是以无序列表（Bullet Points）和表格对技术参数、职责进行归类。
* **参考**：单段建议控制在短长范围内。凡是涉及多个步骤、多项字段、多点原因的表述，建议转换为 Bullet Points 或 Table 排版，以提高阅读时的扫描效率。

### 2.3. 数据指标落脚
* **特征**：规避泛泛而谈的定性描述。所有核心工程论点均落地到具体的**代码文件名、类名、数据结构字段、物理目录、以及实验对比数据（如压缩率、重复读取次数等）**。
* **参考**：在说明系统优化时，建议给出实测或预计的量化指标支撑。谈及具体逻辑时，应指明其在代码中的对应位置（如 `pico/workspace.py` 里的 `clip()` 函数）。

### 2.4. 问题-风险-妥协-验证的闭环逻辑
* **特征**：原文档在阐述核心模块（如上下文管理、记忆系统等）时，论证逻辑较固定：
  1. *提出痛点*：在长链路代码开发中，AI 面临何种失控风险（例如：重复读、路径越界逃逸、上下文超预算）。
  2. *安全约束*：为了防备这个风险，我们在 runtime 控制环或网关处做了何种硬性物理防御。
  3. *妥协折中 (Trade-offs)*：坦承由于算力/预算等限制做出的降级决策（例如：未预加载全仓、未引入重型语义检索等）。
  4. *实验验证*：给出实验对照数据证明成效。
* **参考**：后续写新模块介绍时，建议参考这一论证闭环，先交代风险，再引出检验校验，最后用实验数据闭环。

### 2.5. 句式与说明方式
* **特征**：
  * 多使用主动宣告式句式，例如：“其实我的理解是...”、“我们这里刻意没有一上来就做...”、“这个设计体现的是...”。
  * 善用直观的物理比喻，例如用“后厨调度调度系统”比喻 Agent Harness 框架，用“工程团队 TL 明确拆解任务与验收”比喻 Code Agent 的执行管理。
* **参考**：可参考使用主动宣告式句式。设计概念较为抽象时，寻找一个通俗的“物理比喻”先行，以降低理解门槛。

## 3. 后续新文档模仿参考表

| 维度 | 建议写法 (Good Case) | 避免倾向 (Bad Case) |
| :--- | :--- | :--- |
| **段落** | 单段控制在 2 句话内，善用 `*` 进行分点罗列 | 密密麻麻的一整段自然语言叙述 |
| **数据** | 提供具体的百分比、尝试次数、缩减行数等实验事实 | 仅使用“效果显著提升”、“性能表现极佳”等体感词汇 |
| **术语** | 指向明确的代码类名、文件相对路径、Git 物理事实 | 仅使用泛化的“模型接口”、“输入数据”等模糊称呼 |
| **逻辑** | 先抛出“AI 乱动会引发的风险”，再引出硬性校验防御 | 一上来只罗列功能清单，不交代安全防御和 trade-offs |
| **口吻** | 以冷静的系统TL视角进行设计解释与面试辩护准备 | 过于吹捧方案的先进，或使用缺乏自信的被动语式 |
