# 05-结构化的会话记忆

## 1. 基础定位
* **原章节标题**：`5-结构化的会话记忆`
* **源 Markdown 位置**：行 2275 - 2580
* **本章在整份文档中的作用**：
  规范并定义 Pico 的轻量级分层工作记忆系统（Working Memory）。打通记忆模块与工具执行链、多轮提示词组装的关系，防止大语言模型陷入“重复读文件、重复确认已知事实”的低效循环中。

---

## 2. 核心内容摘要
* **记忆系统的痛点背景**：
  在多轮长链路代码仓库维护任务中，模型由于缺乏跨轮事实的结构化记忆沉淀，经常会去反复读取相同文件或通过工具调用重新确认刚刚拿到过的事实，造成 token 的浪费和步骤预算的超标。
* **分层记忆的四层职责**：
  * `task_summary`（任务摘要）：在每次 `ask()` 开始时将用户原始消息进行短摘要化（截断在 300 字符），在历史会话因为超预算被截断时充当任务的稳定主线锚点。
  * `recent_files`（最近接触文件）：以队列形式维护最近读取/修改过的文件路径列表（硬上限限制 `WORKING_FILE_LIMIT = 8`），自动进行去重。
  * `file_summaries`（文件局部短摘要）：核心组件。模型使用 `read_file` 读取完长文件后，不将全文存入记忆，而是由 `summarize_read_result()` 压缩为极短的文件摘要存入，从而避免长文件累加导致 prompt 迅速膨胀。
  * `episodic_notes`（过程笔记）：跨轮会话笔记。在 `retrieval_candidates()` 中基于 Tag 命中、关键词重叠度、新旧时间、插入顺序等轻量匹配规则（不借助向量检索），动态召回与当前请求关联最密切的笔记，放入 `relevant_memory` 区块。
* **新鲜度校验与缓存失效算法 (Freshness)**：
  为了避免文件被修改后记忆依然保留过期事实，引入 Freshness 机制：
  * **哈希新鲜度比对**：在 `file_summaries` 记录中附带文件当时内容的指纹签名 `freshness = file_freshness(path, workspace_root)`。
  * **动态失效**：在每次 Prompt 渲染前，重新计算被缓存文件的物理哈希，一旦对不上物理文件指纹，则判定该文件已在外部被改动，旧的摘要宣布失效，不再渲染至本轮 Prompt 中。
  * **主动注销**：执行写修改工具 `write_file` 或 `patch_file` 后，运行时主动调用 `invalidate_file_summary` 清除缓存。

## 4. 关键数据与图表描述
* **记忆依赖消融实验指标对比（12个真实任务）**：
  本章给出了严密的实验对照数据：
  * **重复读取次数**：记忆开启时仅为 `3` 次，记忆关闭时为 `8` 次。
  * **平均工具步数**：开启时为 `0.25`，关闭时为 `0.67`。
  * **任务正确率 (Pass Rate)**：开启时为 `100%`，关闭时降为 `66.7%`。
  * **Irrelevant 对照组**：测试塞入无关信息后发现对系统无明显收益，排除了“因 prompt 变长而偶然表现变好”的随机影响。

## 5. 对标与复用指引
* **值得对标的结构**：
  * **“面试口径话术”结尾**：总结本章节的技术取舍（如为什么没有使用重型向量库以保证纯规则的可解释性）与真实实验收益，直接服务于开发者的面试辩护。
* **值得复用的写法**：
  * “在 12 个真实记忆依赖任务中，将重复读文件次数从 8 次降到 3 次，平均工具步数从 0.67 降到 0.25，任务正确率从 66.7% 提升到 100%。”（用于技术价值论证）
* **不应机械照搬的地方**：
  * 静态召回算法 `retrieval_candidates` 基于简单的关键词重叠度与 Tag 匹配，在大型多任务项目（代码规模达数十万行）下容易由于同名函数或重名文件造成严重的检索污染。建议在大项目中升级为混合检索（BM25 + Semantic Embedding）。
* **需要回看确认的细节**：
  * **`file_freshness` 函数提取算法**：需要打开物理仓库核查 `pico/memory.py`，确认文件指纹是采用基于磁盘 `mtime` 和大小的轻量哈希，还是计算全文 SHA-256，因后者可能在面对大文件时造成 I/O 性能下降。
