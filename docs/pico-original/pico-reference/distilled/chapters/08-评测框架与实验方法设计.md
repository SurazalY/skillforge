## 2. 核心内容摘要
* **评测体系三层架构**：
  1. **固定任务集合 (Benchmark Contract)**：定义于 `benchmarks/coding_tasks.json`。每项任务是一条严格的执行合同 (Contract)，限制了 Prompt、allowed_tools 权限、step_budget 步数、期望生成文件及判定通过的 verifier 自动化脚本。
  2. **执行引擎 (`BenchmarkEvaluator`)**：调度并执行任务，负责物理工作区隔离与校验。
  3. **指标分析 (`metrics.py`)**：负责消融实验统计与聚合汇总。
* **物理区副本隔离与防污染**：
  为避免不同测试任务互相干扰、污染测试样本，`BenchmarkEvaluator.run_task()` 启动前，通过 `shutil.copytree` 将只读的 fixture 仓库复制到一个干净的临时物理工作区副本，并在该副本上启动任务，实现干净的单次测试隔离。
* **硬性 PASS 判定算法（四条件交集）**：
  单次评测通过并不是看大模型的回复，而是严格的物理交集计算：
  `passed = within_budget and verifier_passed and expected_artifact_exists and non_failure_stop_reason`
  * `within_budget`：工具调用步数在限制预算内。
  * `verifier_passed`：约定的 `verifier` 自动化验证脚本（Python/Shell）在副本工作区执行的返回码 (returncode) 必须为 0。
  * `expected_artifact_exists`：约定的期望产出文件被物理创建或更新。
  * `non_failure_stop_reason`：Agent 正常以 `<final>` 停机，而非超时或运行中途报错。
* **级联失败归档分类 (Failure Category)**：
  任务未通过时，依次级联分类原因，输出到聚合指标：
  1. 期望文件不存在 -> `missing_artifact`
  2. 步数超预算 -> `budget_exceeded`
  3. verifier 退出码非 0 -> `verifier_failed`
  4. 终止原因异常 -> `failure_stop_reason`
* **Scripted Baseline 挡板机制**：
  内置 `FakeModelClient` 读取确定的 Mock 输出（`SCRIPTED_MODEL_OUTPUTS`），以彻底隔离大模型的网络和随机性，专门测试评估器、验证脚本以及运行控制流本身的可靠性。
* **细分优化对应细分指标评估**：
  * 对上下文瘦身优化 -> 评估 `prompt_chars` 缩减率。
  * 对记忆系统优化 -> 评估“重复读取文件次数减少”及“减少的工具步数”。
  * 只有在对比 Provider 时，才宏观统计 `pass_rate` 和平均尝试次数。

## 5. 对标与复用指引
* **值得对标的结构**：
  * **“任务即合同 (Task as Contract)” 的评测思路**：将评测目标、条件、允许工具权限、步骤上限与校验程序写成单一 JSON 的对标方式非常严谨。
* **值得复用的写法**：
  * “不同机制要用不同细分指标证明，不能把模型能力、系统能力和运行观测混成一个总分。”（较透彻的评测方法论）
* **不应机械照搬的地方**：
  * **`copytree` 物理拷贝工作区**：在当前 Mock 小型仓下拷贝很快。若面对 GB 级大仓，每次任务拷贝会导致 I/O 崩溃。复杂项目中，应升级为 Git Worktree 挂载或 Docker 卷挂载。
  * **同步串行 Evaluator**：任务多时，串行执行较耗时，应当使用进程池实现并行调度。
  * **Verifier 的系统级命令执行安全性**：当前的 verifier 直接在本地宿主机上跑，若模型生成了破坏性脚本（如 rm -rf），由 evaluator 运行会破坏宿主机。生产中 verifier 必须在隔离的 Docker 容器中执行。
