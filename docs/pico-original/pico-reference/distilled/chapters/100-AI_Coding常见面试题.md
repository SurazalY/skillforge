## 2. 六大核心考题与标准解答思路
* **Q1：高质量的 Agent Skill 应该包含哪些设计要素？**
  * *解答要点*：
    1. *触发条件明确*：让 Agent 知道什么场景下该调用本 Skill；
    2. *职责单一且边界清晰*：一个 Skill 只干一件事，且明确规定“不能干什么”以防越权；
    3. *操作步骤清晰*：提供具体的可操作流程，而不是抽象的概念性指导；
    4. *显式资源引用*：列出可能依赖的外部脚本、文档和 API 路径；
    5. *带边界示例 (Bad/Good Cases)*：必须提供成功的示范以及针对极值、异常分支失败的对照示例；
    6. *可测试性*：包含对 Skill 规程本身的验证手段。
* **Q2：设计优秀 Prompt 的 6 要素是什么？**
  * *解答要点*：
    1. *角色与定位明确*；
    2. *任务目标具体（尽量指标化）*；
    3. *提供充分且非冗余的上下文*；
    4. *设立清晰的硬约束与负向提示词 (Negative Prompt)*；
    5. *约定严格的输出格式约束*；
    6. *配置明确的验收标准 (Verifier)*，并允许模型遇到无法解决的问题时选择澄清或拒绝盲目猜测。
* **Q3：如何在团队开发工作流中防止 AI 生成代码时的“幻觉”与“失控”？**
  * *解答要点*：建立“多阶段受控”工作流：
    1. *任务细分*：限制单次 AI 修改的边界与规模；
    2. *方案先行 (Plan First)*：大任务强制要求 AI 先出设计文档，人批准后再动手；
    3. *小步快跑迭代*：每次修改一个模块，立刻执行本地静态分析、lint 和单测验证，报错信息自动回灌；
    4. *人机 CR*：AI 修改必须通过 Git diff 接受人类严格 Review；
    5. *CI 护栏与灰度*：CI 自动化单测把关，最终走小流量灰度。
* **Q4：如何利用 AI 建立自动化的 Code Review 机制？**
  * *解答要点*：
    1. *上下文提取*：将 PR 的完整变更、涉及的被改动文件及依赖接口送入 AI；
    2. *对照 Checklist*：让 AI 对照安全（SQL注入/并发安全）、业务逻辑、并发与事务、代码规范这四张 checklist 扫描；
    3. *输出标准建议结构*：要求 AI CR 评论必须包含“问题具体行号 + 原因分析 + 潜在影响 + 推荐修改的代码 diff”；
    4. *人机确认*：AI 仅做第一道初筛并打标，由资深工程师做最终批准。
* **Q5：如何防止 AI 编写“弱测试（无效单测）”？**
  * *解答要点*：
    1. *禁止逃避测试*：严禁 AI 删除失败的旧单测，或滥用 `skip`、`todo` 标签跳过测试；
    2. *禁止无效断言*：禁止使用如 `expect(res).toBeTruthy()` 或只测 `assert True` 等对业务逻辑无实质约束力的断言；
    3. *禁止 mock 被测主体*：严禁 mock 被测函数本身或其核心内部逻辑；
    4. *首写失败复现*：若是 bug 修复，强制要求 AI 必须先编写出一个能物理复现该 bug 的“失败单测”，再实施修复以证明测试的敏感度；
    5. *多条件断言*：断言必须包含具体的业务边界状态及极值。
* **Q6：生产环境发生故障，如何引导 AI 进行排查？**
  * *解答要点*：
    1. *特征提取*：提取脱敏日志中的关键字及 Trace ID；
    2. *时序还原*：对比故障点前后的部署变更记录，建立故障时序时间线；
    3. *现象-假设-证据-验证循环*：引导模型按此标准科学路径推进，防止AI漫无目的地猜测；
    4. *辅助生成调查工具*：让 AI 生成特定的 SQL 查询、日志过滤脚本或监控面板配置，获取一手证据；
    5. *故障根因总结*：故障解决后，由 AI 辅助写出 Postmortem（故障复盘报告）。

## 3. 面试表达风格与对标
* **结构要素化表达**：回答“AI CR”或“弱测试”时，分条陈述，有逻辑递进，给人以极强的 SOP 方法论体感。
* **Good/Bad 对比**：通过展示“坏的 CR 做法”与“好的 CR 做法”对比，展示极强的实践经验。
