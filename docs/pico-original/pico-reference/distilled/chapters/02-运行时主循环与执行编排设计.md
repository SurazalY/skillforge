# 02-运行时主循环与执行编排设计

## 1. 基础定位
* **原章节标题**：`2-运行时主循环与执行编排设计`
* **源 Markdown 位置**：行 1172 - 1562
* **本章在整份文档中的作用**：
  详解 Pico 的运行时控制中心（即 Runtime 编排层），展示一条用户请求是如何通过主循环机制一步步被推进、解析和记录成可回放执行链的。它是整个框架的核心驱动大脑。

---

## 2. 核心内容摘要
* **从请求到 Run 的生命周期**：
  一次用户请求对应一轮独立的 Run，其运行权由 `Pico.ask(user_message)` 驱动。
  1. **现场初始化**：写入任务摘要、更新会话历史、创建 `TaskState`，并在 `.pico/runs/<run_id>/` 下建立独占的运行目录，写出首版 `task_state.json` 以便任务跟踪。
  2. **感知-决策-行动-记录循环**：进入主 While 循环（限制条件为工具执行步数 `tool_steps < max_steps` 且尝试次数 `attempts < max_attempts`）：
     * **感知**：重新采样工作区状态，构建当前轮次的 Prompt 文本及 Metadata 元数据。
     * **决策**：请求 LLM，拿回一轮 Raw Output。
     * **行动**：解析 LLM 返回的动作。
     * **记录**：把这轮发生的事情（如工具执行结果、重试记录、状态变化）回写状态并追加写到 Trace 流。
* **两个关键的状态计数指标**：
  * `attempts`：统计模型请求被调用的总次数（包括各种无效的输出、XML 格式损坏后的重试）。
  * `tool_steps`：统计进入真正执行并产生外部副作用的工具执行步数。
  * **诊断意义**：若 attempts 很高而 tool_steps 极低，代表大模型出现严重的格式混乱、陷入无限自我循环或重试中。
* **Prompt 逐轮重建的必要性**：
  Prompt 在 Runtime 里不是静态的，而是在每一轮重新执行 `_build_prompt_and_metadata()` 动态拼装。因为上一轮的工具返回结果、物理工作区改动、以及会话历史、更新的记忆都在实时波动，必须重新将其投影为 Prompt 状态。
* **输出解析器 (`parse()`) 状态机逻辑**：
  对 LLM 返回的文本做精确过滤，不关心中间的废话，只提取动作：
  * **Tool 分支**：解析到匹配的 XML 标签 `<tool>...</tool>`（内包 JSON 参数）或 `<tool name="...">...</tool>` 格式，返回 `("tool", payload)`。
  * **Final 分支**：解析到结束标签 `<final>...</final>`，或者在没有工具调用且有实质文本时默认作为答案，返回 `("final", raw_text)`。
  * **Retry 分支**：未匹配到有效动作或格式损毁时，主动返回 `("retry", retry_notice)`，触发主循环 attempts 递增并提供格式纠正说明。
* **工具接回主循环 (`run_tool`)**：
  解析为 Tool 分支后，统一由 `run_tool(name, args)` 收口，在安全边界内进行权限和路径校验，其结果作为新状态重灌回下一轮 Prompt。

## 5. 对标与复用指引
* **值得对标的结构**：
  * **“感知-决策-行动-记录”循环模型**：这是智能体循环的标准结构，后续在设计任何有状态 Agent 框架时，此控制环描述结构都必须作为核心逻辑对标。
* **值得复用的写法**：
  * “模型返回的是文本，runtime 需要的是动作。”（深刻的动作提炼）
  * “Prompt 在 runtime 里不是一份固定文本，更像当前执行状态的投影。”（提示词工程架构化定位）
* **不应机械照搬的地方**：
  * 纯文本 XML 字符串匹配 `"<tool>" in raw` 属于粗暴的字符串检测，极易在模型回复的思维链（CoT）中误触。生产系统中应使用真正的带状态流式解析器（Streaming XML Parser）或者真正的多阶段 JSON schema 捕获。
