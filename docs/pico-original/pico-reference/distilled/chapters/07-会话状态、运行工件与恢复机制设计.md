# 07-会话状态、运行工件与恢复机制设计

## 1. 基础定位
* **原章节标题**：`7-会话状态、运行工件与恢复机制设计`
* **源 Markdown 位置**：行 2928 - 3262
* **本章在整份文档中的作用**：
  设计 Pico 的数据状态模型与持久化机制，实现“状态数据（Session）”与“审计证据（Run Artifact）”的解耦，为 Agent 的中断恢复（Resume）与事后行为回放评测提供可靠的文件系统基架。

---

## 2. 核心内容摘要
* **“数据”与“审计证据”的解耦哲学**：
  * **Session (会话状态)**：服务于“下一次任务如何接着执行”。仅保留必要的业务记忆与对话链。
  * **Run Artifact (运行工件)**：服务于“刚才运行中物理上发生了什么”，以便开发者审计、评测与复盘。
* **Session 存储设计 (`SessionStore`)**：
  * 物理路径：`.pico/sessions/<session_id>.json`。
  * 关键字段：`id` (唯一会话标识)、`created_at` (时间戳)、`workspace_root` (工作区物理路径)、`history` (多轮对话记录)、`memory` (结构化工作记忆)。
  * 实现：基于纯 JSON 读写，无重型数据库依赖。
* **Run Artifact 三件套设计 (`RunStore`)**：
  * 每次 `ask()` 启动时为任务分配独立目录：`.pico/runs/<run_id>/`。
  * **核心工件三大文件**：
    1. `task_state.json`：`TaskState` 状态快照。包含 `status` (运行状态)、`tool_steps` (工具步数)、`attempts` (重试次数)、`stop_reason` (停机原因)、`final_answer` (最终答案)。回答“当前跑到哪了”。
    2. `trace.jsonl`：逐事件的时间线追加日志。**采用流式追加写 (Append-only)**，记录 `run_started`、`prompt_built`、`model_requested`、`model_parsed`、`tool_executed` 和 `run_finished`。确保 Agent 崩溃或被强制中止时，日志数据完整不丢失。回答“过程发生了什么”。
    3. `report.json`：运行结束后的聚合指标摘要，记录输入输出 token、预算元数据及任务最终状态，为实验和消融汇总提供第一手机器可读的统计原料。
* **中断恢复与漂移检测控制流 (Resume)**：
  * 通过 CLI 参数 `--resume <session_id>` 或 `--resume latest` 触发。
  * **恢复逻辑**：从 JSON 中反序列化出 `history` 和 `memory` 灌回新建的 `Pico` 实例。重新注入外部的 `model_client` 与 `workspace` 物理对象。它恢复的是**会话级数据状态**而非内存中运行的**物理进程状态**。

## 5. 对标与复用指引
* **值得对标的结构**：
  * **“Session 与 Run Artifact 解耦”的文档表述**：非常适合移植到任何具有长生命周期的复杂后台应用设计文档中。
* **值得复用的写法**：
  * “恢复的是会话数据状态，而不是内存中运行的物理进程/连接状态。”（较清晰的底层机制说明）
  * “`trace.jsonl` 采用追加写，保证 Agent 中途挂掉时 trace 数据不丢失。”
* **不应机械照搬的地方**：
  * **单 JSON 持久化会话历史**：对于极长的复杂任务会话，JSON 文件可能会变得较臃肿，导致磁盘 I/O 延迟大、内存爆满。实际生产项目中，应改用关系型数据库（如 SQLite 或 PostgreSQL）存储。
  * **缺乏版本控制**：当前工件无 schema 版本。代码升级字段更改后，历史 report 可能因兼容问题导致解析崩溃。应当引入 `schema_version` 字段。
* **需要回看确认的细节**：
  * **敏感数据脱敏逻辑**：文档提到 `secret` 会在 trace 和 report 里被脱敏，但没有详述脱敏的具体实现。如需实现安全设计，必须回看源码中的脱敏机制。
