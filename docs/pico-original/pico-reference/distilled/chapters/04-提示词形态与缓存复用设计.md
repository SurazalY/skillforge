# 04-提示词形态与缓存复用设计

## 1. 基础定位
* **原章节标题**：`4-提示词形态与缓存复用设计`
* **源 Markdown 位置**：行 1929 - 2274
* **本章在整份文档中的作用**：
  设计 Pico 前缀缓存系统，将 Prompt 划分为“稳定前缀 (Stable Prefix)”与“动态内容”两部分。通过对稳定前缀的 Hash 缓存和失效判断，减少长链路多轮会话中的重复计算开销，降低大模型 API 调用成本。

---

## 2. 核心内容摘要
* **稳定前缀与动态段的分离设计**：
  * **稳定前缀 (PromptPrefix)**：包含系统规则 (System Rules)、工具白名单与调用示例 (Tools Specs)、工作区基线摘要 (Workspace Base Line)。
  * **动态段**：包含会话历史 (History)、分层记忆 (Memory & Relevant Memory) 与当前轮次用户请求 (Current Request)。
* **前缀对象结构 (`PromptPrefix`)**：
  在 `pico/runtime.py` 中定义，不仅包含前缀 `text`，还包含：
  * `hash`：对前缀全文的 SHA-256 哈希签名。
  * `workspace_fingerprint`：当前时刻的工作区状态指纹。
  * `tool_signature`：当前时刻工具注册表签名的哈希。
  * `built_at`：记录前缀构建的时间戳。
* **失效判断逻辑 (`refresh_prefix`)**：
  在每一轮 Prompt 组装前执行。如果比对发现：
  * Git 分支变化、`git status` 状态改变、近期 commits 变化、或者 `README.md` / `AGENTS.md` 等白名单文档内容被修改，会导致重新采样的 `WorkspaceContext` 的 `fingerprint` 与原前缀存储的 `workspace_fingerprint` 不匹配。
  * 此时，前缀宣布失效，触发前缀文本重建并生成新的 Hash 签名；若无变化，则复用原前缀，避免无谓的字符串序列化开销。
* **Prompt Cache 在模型适配层的打通**：
  Pico 主控制循环中：
  1. 通过 `prompt_metadata` 获取前缀签名 `prefix_hash`。
  2. 若模型后端适配器支持缓存（即 `supports_prompt_cache` 设为 True），则将 `prompt_cache_key = prefix_hash` 和 `prompt_cache_retention = "in_memory"` 注入请求参数中传递。
  3. **后端支持自适应识别**：在 `OpenAICompatibleModelClient` 中根据 `base_url` 是否包含 `openai.com` 或 `right.codes` 动态使能缓存；本地 Ollama 默认不使能。
* **缓存命中的闭环审计**：
  在模型返回响应后，适配器从响应体的 `usage` 结构中抽取 `cached_tokens` 等字段。将其封装至 completion metadata，最终落盘在 `trace.jsonl` 和 `report.json` 中，以便研发统计真实的 `cached_tokens` 节省率和缓存命中率。

## 5. 对标与复用指引
* **值得对标的结构**：
  * **“前缀缓存与物理指纹绑定”设计**：通过工作区指纹 (`workspace_fingerprint`) 与模型调用缓存主键 (`prompt_cache_key`) 绑定，确保前缀内容与本地环境一致，这一对标结构极有深度。
* **值得复用的写法**：
  * “稳定部分被认真复用，动态部分还是按轮重建。”
  * “别自己切到没有缓存的 provider，除非你就是想测别的后端。”（偏向用户的实用警示）
* **不应机械照搬的地方**：
  * 将 `prompt_cache_retention` 强制硬编码为 `"in_memory"` 并不通用。对于 Anthropic 兼容接口或其他有更长缓存周期选项（如持久缓存等）的后端，硬编码会降低控制自由度。
