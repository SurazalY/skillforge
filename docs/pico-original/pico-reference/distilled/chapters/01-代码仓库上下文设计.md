# 01-代码仓库上下文设计

## 1. 基础定位
* **原章节标题**：`1-代码仓库上下文设计`
* **源 Markdown 位置**：行 941 - 1171
* **本章在整份文档中的作用**：
  解决 Code Agent 进入代码仓库后首先应获取何种上下文（仓库基线）的问题，建立模型进行第一步判断的认知导航。在不预加载全仓代码（保留上下文空间并控制成本）的前提下，实现安全可控、不失真的环境感知。

---

## 2. 核心内容摘要
* **面临的核心挑战**：
  * 全仓预加载较昂贵，大项目会瞬间塞爆 Prompt 空间，引入大量干扰噪声。
  * 若仅给用户一句话的输入，模型对外界一无所知，连从哪里开始读取、是否在 Git 分支、是否包含未提交代码都无法判断，极易导致幻觉和乱读。
* **Pico 的折中设计——仓库基线 (Workspace Base Line)**：
  在 `pico/cli.py` 启动时运行 `WorkspaceContext.build(cwd)`，只收集以下最低限度的仓库事实并渲染：
  * `cwd`：告知当前启动所在的子目录。
  * `repo_root`：通过 `git rev-parse --show-toplevel` 物理确定仓库边界和工具范围。
  * `branch` & `default_branch`：感知当前工作分支与主线分支的差异。
  * `status`：通过 `git status --short` 获取当前未提交的修改状态，以此知晓环境是否 dirty。
  * `recent_commits`：获取 `git log --oneline -5` 提供近期的提交背景。
  * `project_docs`：扫描并截取高价值项目文档。
* **白名单项目文档扫描策略**：
  定义在 `pico/workspace.py`。默认只扫描工作区及根目录下的 4 个重要入口文件：`AGENTS.md` (规则与规范)、`README.md` (项目结构与入口)、`pyproject.toml` (Python 依赖与工具链)、`package.json` (Node 依赖与脚本)。
  * **预算安全**：每份文档均会被截断保留前 `1200` 字符，避免某份超长 README 独占整个 prompt 配额。
* **Prefix 动态刷新与轻量缓存机制**：
  工作区摘要被拼装在 stable prefix 里。在每一轮主循环 prompt 组装前，runtime 自动调用 `refresh_prefix()`：
  * 重新进行 `WorkspaceContext.build(self.root)` 采样。
  * 通过 `fingerprint()` 比较前后两次仓库状态签名。只有在分支、未提交改动、白名单文档被实质修改导致 fingerprint 变化时，才重新渲染前缀文本；否则继续复用旧前缀文本，避免频繁的字符串拼接开销。

## 3. 展开顺序与关键术语
* **信息展开顺序**：
  1. 指明 Code Agent 首次进入仓库所面临的信息量多与少的矛盾背景。
  2. 详解仓库基线的具体字段表格与设计缘由。
  3. 分析白名单文档的发现、截断策略及代码实现。
  4. 剖析 Workspace 摘要与 stable prefix 的拼装、通过 fingerprint 签名的刷新与轻量缓存刷新逻辑。
  5. 辨析为什么不能“无脑整仓预加载”。
  6. 归纳当前设计边界（无目录树、Git 视角较轻等）及未来面试改进方向。
* **关键术语**：
  * `WorkspaceContext`
  * `Workspace Base Line` (仓库基线)
  * `fingerprint` (工作区状态指纹)
  * `refresh_prefix`
  * `project_docs`

## 5. 对标与复用指引
* **值得对标的结构**：
  * **“设计边界 -> 面试如何防守 -> 改进方案”**的文档逻辑：这在面对复杂工程实现时极有说服力，展现了设计者知其然、知其所以然。
* **值得复用的写法**：
  * “仓库上下文这一层先做导航，不做知识库。”（极佳的定位语）
  * “扫描位置同时覆盖 `repo_root` 和 `cwd`，从子目录启动时，也能顺手把本地文档带上。”
* **不应机械照搬的地方**：
  * 硬编码的 `DOC_NAMES = ("AGENTS.md", "README.md", "pyproject.toml", "package.json")` 仅适用于 Python 和 JavaScript 仓库。对 C++、Go、Rust 项目，需要动态识别其核心项目说明文件（如 `go.mod`、`Cargo.toml`、`CMakeLists.txt`）。
* **需要回看确认的细节**：
  * 原文档中 `WorkspaceContext.text()` 的具体格式渲染样式（例如，它是以 XML 标签包着，还是纯 JSON 表示），可能需要回看源 MD 行 990 之后的字段渲染部分以获得更一致的风格。
