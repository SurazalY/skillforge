## 2. 核心技术问答与扩展设计（干货骨架）
* **Q1：横向体验过哪些 AI 编程工具？它们有什么差异？**
  * *回答骨架*：
    * **Claude Code**：模型推理逻辑极强，但执行流程对用户完全是黑盒（抽卡体验）；
    * **Codex**：像老练且较保守的工匠，风控极严，稍有不慎即拒绝执行；
    * **Kimi Code**：擅长查找和整合中文文档与本地库；
    * **Trae (字节)**：界面极佳，但处理多文件重构等长链路任务时依然容易失控。
* **Q2：为什么同一个大模型，在不同 Agent 框架下任务表现差异巨大？**
  * *回答骨架*：表现差异不来自于“大模型智商”，而来自于 Harness 的配套设计：
    1. *上下文构造分布*：是否有类似于 `CLAUDE.md` 的前置规则约束；
    2. *编排精细度*：是线性循环还是图编排，报错信息是否能够回灌给大模型以形成反馈闭环；
    3. *决策机制*：是允许模型大步修改，还是逼迫其“小步迭代、频繁验证”；
    4. *安全护栏*：越界拦截是否会返回清晰的报错引导，还是直接生硬阻断导致模型迷失。
* **Q3：用 Code Agent 进行长链路开发，你有什么工程隐喻（TL 隐喻）？**
  * *回答骨架*：**使用 Code Agent 就像带一个工程研发团队。**
    作为团队 TL，你不能去微管理（Micro-manage）AI 的每一行代码，这会导致 token 爆炸且逻辑混乱。TL 应该做的是：明确划分每个人（子 Agent）的能力边界，制定严密的任务验收合同 (Verifier)，做好数据隔离，并检查执行结果。
* **Q4：如果要在 Pico 中引入 Skill 机制与 MCP 协议，你会怎么设计？**
  * *设计骨架*：
    * *职责定位*：Skill 是提示词与操作规程资源（属于**“怎么做”**）；MCP 是工具和端点连接协议（属于**“能调什么”**）。
    * *实现步骤*：
      1. 抽象 `ToolProvider` 接口，解耦本地工具与外部工具；
      2. 建立 `SkillRegistry` 进行动态规程加载；
      3. 实现 `MCPToolProvider`，将外部 MCP 服务端暴露的端点工具动态映射为本地工具白名单，并无缝复用已有的路径越界校验和 Approval 审批链。
* **Q5：如何实现 `/btw` 旁路会话问答？**
  * *设计骨架*：
    * *目的*：允许用户在任务中途随时插问一个无关问题，而该问题只作解答，不污染主任务的 history 历史和记忆状态。
    * *实现*：引入轻量子会话 `side-question`。共享父会话的当前记忆与工作区快照，但以只读模式（`read_only=True`）启动一个临时的 Pico 实例，生命周期仅限于该单次问答，其问答信息绝对不写回主 Session JSON 中。
* **Q6：你是如何学习新技术并保持技术敏感度的？**
  * *回答骨架*：建立闭环信息 SOP：
    1. *源头过滤*：优先看顶会论文、官方技术博客等一手资料，排除自媒体杂音；
    2. *AI 辅助建构*：利用 AI 快速整理新框架的 API 结构和核心权衡点；
    3. *输出闭环*：亲自动手写 demo 库、写技术分享，在物理实践中验证理解；
    4. *压缩复盘*：将技术沉淀转化为规范资产。

## 3. 面试表达风格与亮点
* **团队 TL 的角色拟人化隐喻**：在面试中谈及管理 agent 的心得时，以“研发团队管理”类比，瞬间将求职者从普通螺丝钉拉升到具有 Leader 视角的管理人才维度。
* **清晰的概念边界划分**：在面试中能够一眼划分出 Skill（规程）与 MCP（能力）、Session（历史）与 Checkpoint（恢复现场）的区别，显示出极强的系统思维。
