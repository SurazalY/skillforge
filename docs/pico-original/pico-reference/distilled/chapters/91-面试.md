## 2. 核心技术问答（骨架与干货数据）
* **Q1：请做一下这个项目的自我介绍（3分钟版本）**
  * *话术骨架*：
    * *项目定位*：面向本地代码仓库维护与长链路任务开发的轻量级 Code Agent Harness 框架。
    * *痛点问题*：商业竞品（如 Claude Code）对开发者属于黑盒（无法拦截危险动作、且存在严重的隐私泄露隐患）。普通大模型在真实仓库中存在长会话 prompt 膨胀、重复读取文件、状态丢失及安全不可控等问题。
    * *架构贡献*：我从零实现了控制面（ask主循环）、状态面（session与独立工件存储）、证据面（硬性四条件判定 benchmark）三层架构。
    * *核心收益数据*：在 12 组对照变量上，将平均 prompt 长度由 `6964` 压缩至 `5418`（压缩率 `18.01%`）；在记忆依赖任务中将重复读文件从 8 次降到 3 次，任务正确率从 `66.7%` 提升至 `100%`。
* **Q2：为什么不用现成的 LangGraph、AutoGPT 等框架，而是自己手写？**
  * *话术骨架*：
    1. *高可控与轻量化*：商业落地要求少依赖、易调试。手写控制环能将错误直接暴露在 runtime 或具体的工具层，方便直接定位。
    2. *图编排开销过重*：当前 Pico 的控制环采用线性 While 循环（感知-决策-行动-记录）已完全够用，不需要复杂的图状态转移。
    3. *自定义安全与协议*：我们需要在底座上实现非常定制化的路径防逃逸、Approval 审批和流式追加 trace，第三方图框架会对这些底层的灵活修改产生限制。
* **Q3：这个项目有哪些不足，如果让你继续改进，你的三步走规划是什么？**
  * *话术骨架*：
    * *第一步：引入过程评测指标 (Process Evaluation)*：目前的评估只看最终是否 Pass，这属于结果指标。未来将引入过程指标（如统计中间无谓的重试率、工具调用重复率），在过程中揪出模型的不良倾向。
    * *第二步：安全规则层抽取独立*：将当前散落在 tools.py 和 runtime.py 中的安全护栏（路径校验、命令环境变量白名单）抽离为可动态配置的独立 Policy Rules 层。
    * *第三步：Tracing 标准化与集成*：将自定义的 JSONL 结构转换为 OpenTelemetry 等行业标准，以便接入大盘审计。
* **Q4：你觉得让 AI 在真实仓库生成代码，最大的挑战是什么？**
  * *话术骨架*：
    * 核心是一个“带状态的执行系统问题”。最大的挑战有四点：系统当前状态的精准表达（如何不膨胀地把仓库、文件和记忆灌进去）、修改动作的精准度（Pico 通过 patch_file 唯一命中解决）、多轮执行的稳定性（防死循环和格式崩溃）、外部验证的闭环（Verifier 的强验收）。

## 3. 面试表达风格与对标
* **模仿点**：
  * **渐进式的规划思维**：回答“未来改进”时，采用“第一步、第二步、第三步”的清晰演进路径，体现出架构师深思熟虑的演进思路。
  * **行业竞品敏锐度**：主动与业界标杆（Claude Code, Trae, Codex）进行痛点对比。
