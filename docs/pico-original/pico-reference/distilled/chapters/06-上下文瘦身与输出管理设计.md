# 06-上下文瘦身与输出管理设计

## 1. 基础定位
* **原章节标题**：`6-上下文瘦身与输出管理设计`
* **源 Markdown 位置**：行 2581 - 2927
* **本章在整份文档中的作用**：
  设计多轮对话中的上下文控制与裁剪架构（Context Budget Control），防止超长的工具输出、详细的历史记录和过程日志超出大模型上下文预算上限。它是避免 prompt 膨胀及关键指示被噪声稀释的系统防线。

---

## 2. 核心内容摘要
* **分层治理与源头裁剪四道防线**：
  1. **第一层：工具长输出源头裁剪**：在数据入口端，所有工具返回的文本执行 `clip(text, limit=4000)`，超出 `4000` 字符直接截断并标注 `...[truncated {chars}]`。
  2. **第二层：记忆模块自身额度控制**：对记忆内部的数据结构施加硬截断。`recent_files` 限制为 8 项，`file_summaries` 限制为 6 项。
  3. **第三层：相关记忆召回限额与尾部剪切**：限制相关笔记召回数 `RELEVANT_MEMORY_LIMIT = 3`。为防止某条长笔记独占额度，平均分配配额并做尾部裁剪 (`_tail_clip`)。
  4. **第四层：历史会话分层压缩**：在渲染会话历史时按新旧区分。最近 6 轮为 `recent_window`（保留详细交互，工具输出限 `900` 字符），超出 6 轮的旧历史予以高度折叠（工具输出限 `60` 字符，多轮对话压缩为一行，重复的 `read_file` 按路径去重）。
* **Section 预算控制算法（装箱机制 Packing）**：
  * 将 Prompt 划分为 5 个 Section，分配初始默认配额（总预算 12000 字符）：
    * `prefix` (前缀手册)：3600 字符。
    * `memory` (工作记忆)：1600 字符。
    * `relevant_memory` (召回笔记)：1200 字符。
    * `history` (会话历史)：5200 字符。
    * `current_request` (当前新指令)：不裁。
  * **削减回退顺序 (Reduction Order)**：如果组装后的总字符数超过 12000，系统根据静态优先级依次扣减配额并裁剪：
    `relevant_memory -> history -> memory -> prefix`
  * **保底 floor 逻辑**：各 Section 裁剪时，不能裁为 0，默认最低保留其初始预算的四分之一（即 `max(20, budget // 4)`），从而保证各部分事实的最低可见度。

## 4. 关键数据与图表描述
* **入口裁剪上限规范**：
  * 工具返回值限制：`4000` 字符。工作区文档片段限制：`1200` 字符。`git status` 限制：`1500` 字符。
* **实验成效数据**：
  * 在 12 组真实的长上下文对照实验配置下，平均 prompt 长度由 `6964` 压减为 `5418`，平均压缩率达到 `18.01%`，最高可压缩 `35.63%`，同时保持 `current_request` 百分之百不被裁坏。

## 5. 对标与复用指引
* **值得对标的结构**：
  * **“层层防御”的设计框架**：从入口、机制、组件到顶层联合装箱裁剪的文档结构非常有条理。
* **值得复用的写法**：
  * “这套设计的价值，不在于 prompt 一定会更短，而在于系统知道自己在删什么。”（极富系统设计深度的总结）
* **不应机械照搬的地方**：
  * **基于字符数 (Char-based) 的度量**：系统裁剪当前基于 `len(text)` 字符数，对于大模型在多语言环境下的 Token 计数极不一致。后续必须将其改造为 Token-aware 的计算（引入 Tiktoken 等计数器），否则可能会由于 Token 数超预算导致请求失败。
  * **静态的削减优先级**：硬编码了最先裁剪 `relevant_memory`。如果在高记忆依赖的任务中，这会导致系统迅速遗忘关键事实。应当支持按任务类型动态设定。
